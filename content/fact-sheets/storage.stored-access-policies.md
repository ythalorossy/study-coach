# Configure stored access policies

## Key concepts

- A stored access policy is a named, server-side constraint set that lives on an Azure Storage container — a blob container, file share, queue, or table — and it groups one or more service SAS tokens so they can be controlled together. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- The policy governs three things: the SAS start time, the expiry time, and the permissions. Because those values are held server side, you can change them or revoke the SAS after it has already been handed to a client. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- A service SAS that references a stored access policy inherits that policy's start time, expiry time and permissions, so the token cannot outlive or exceed the policy it points to. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Stored access policies apply to a **service SAS** only. A user delegation SAS and an account SAS must always be ad hoc SAS tokens. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Azure Storage has three SAS types — user delegation SAS, service SAS and account SAS — and each is authorized differently: user delegation SAS by Microsoft Entra ID, service SAS by Shared Key, account SAS by Shared Key. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A service SAS delegates access to a resource in only one storage service: Blob Storage (including Data Lake Storage and `dfs` endpoints), Queue Storage, Table Storage, or Azure Files, and it is signed with the storage account key. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- An account SAS is also signed with the storage account key but spans one or more storage services, and it adds service-level operations (for example **Get/Set Service Properties** and **Get Service Stats**) plus read, write and delete operations a service SAS does not permit. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A user delegation SAS is signed with a user delegation key created from Microsoft Entra credentials; to get that key the calling security principal needs an Azure role including the `Microsoft.Storage/storageAccounts/blobServices/generateUserDelegationKey` action. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A SAS is a token of query parameters appended to the resource URI; Azure Storage checks the parameters and signature on each request and returns error code 403 (Forbidden) when verification fails. Tokens are generated client side and are not tracked or counted by the service. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A SAS takes one of two forms: an **ad hoc SAS**, where start time, expiry and permissions are embedded in the URI and any SAS type may be used that way, or a **service SAS with a stored access policy**, where the constraints come from the policy on the container. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))

## Settings and limits

- Maximum of **five stored access policies per container**; going beyond that limit is not supported. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Recommended pattern: set the stored policy expiry very far in the future (or infinite) and regularly update it to move it farther out, so long-lived SAS tokens do not quietly expire. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Creating or updating the policy uses the REST operation **Set Container ACL**, and it must be authorized with **Shared Key** using the account access keys in a connection string — authorizing **Set Container ACL** with Microsoft Entra credentials is not supported. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- With the .NET client library version 12 you create the policy through `BlobContainerClient.SetAccessPolicy` or `BlobContainerClient.SetAccessPolicyAsync`, after calling `CreateIfNotExistsAsync` on the container. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- Each entry is a `BlobSignedIdentifier` with an `Id` (the policy name referenced by the SAS) and a `BlobAccessPolicy` holding `StartsOn`, `ExpiresOn` and `Permissions`; the sample uses `Id = "mysignedidentifier"` with `Permissions = "rw"`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- The method call sets the container's access policy from the list of `signedIdentifiers` you pass, so a single call both creates the new policies and sets the container's policy collection. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- The documented sample produces a policy effective for one day: `StartsOn = DateTimeOffset.UtcNow.AddHours(-1)`, `ExpiresOn = DateTimeOffset.UtcNow.AddDays(1)`, `Permissions = "rw"`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- Servers and clients can disagree about the current time by around a quarter hour in either direction, so back-date the start time by about 15 minutes or leave it out entirely so the SAS works immediately everywhere. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- When you call through a REST version older than `2012-02-12`, a standalone SAS token is capped at one hour of validity, and requesting a longer window makes the request fail outright. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A storage-account **SAS expiration policy** defines a recommended upper validity interval; it applies to service SAS and account SAS, and creating one longer than the recommendation produces a warning plus an entry in Azure Storage logs when Azure Monitor logging is enabled. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Some tools such as AzCopy require date/time values in the format `'+%Y-%m-%dT%H:%M:%SZ'`, which includes seconds. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Sample code catches `RequestFailedException` and logs `e.ErrorCode` and `e.Message`, then cleans up with `DeleteAsync` on the container. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- Code samples for the stored access policy under the .NET 11.x SDKs are deprecated; use the version 12 `SetAccessPolicyAsync` approach instead. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))

## Compare and choose

- If the requirement is revocability without rotating keys, choose a **service SAS + stored access policy**: a policy gives you the option to revoke permissions for a service SAS without regenerating the storage account keys. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- If revocation is not needed, choose an **ad hoc service SAS or account SAS with a near-term expiry**, so a leaked token is useful only briefly; this is especially important when you cannot reference a stored access policy. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- If the strongest security is the priority, choose a **user delegation SAS** whenever the scenario allows: it is secured with Microsoft Entra credentials instead of the account key, and Microsoft recommends it for SAS scenarios. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Choose an **account SAS** only when you truly need multi-service or service-level delegation; a service SAS is narrower and confined to one service. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Grant the least privilege possible: use a read-only SAS where that suffices, and scope read access to a single object rather than read/write/delete across every object — this also limits damage if the SAS leaks. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- For audit-style correlation, use the signed fields `sip` (signed IP), `st` (signed start) and `se` (signed expiry) — for example a unique expiry per client — because there is no direct way to see which clients accessed a resource. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- If every blob in a container just needs to be world-readable, skip the SAS entirely and make the container **Public** instead; likewise, for operations where SAS risk outweighs benefit, route writes through a middle-tier service that does authentication, validation and auditing. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A SAS is mandatory in some copy cases: blob-to-file or file-to-blob copies always require one even inside the same account, while cross-account blob or file copies require one for the source and optionally for the destination. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Distribute tokens only over HTTPS; anything sent over plain HTTP can be captured by a man-in-the-middle and reused exactly as the intended client. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Clients that call storage repeatedly through a SAS should auto-renew well before expiry, leaving time for retries if your SAS-issuing service is temporarily unavailable. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))

## Gotchas

- A common wrong answer is "stored access policies work with account SAS or user delegation SAS" — they do not; both of those types must be ad hoc, and the limit of five policies per container applies to the container resource holding them. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Creating the policy needs the storage account key (Shared Key authorization in a connection string), so an Entra-only setup or an identity without access to the keys cannot define the policy even if the app can otherwise read and write blobs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-stored-access-policy-define-dotnet))
- Because the policy is enforced at request time, an inadvertent deletion or change of a stored access policy instantly breaks every service SAS bound to it and clients see 403 (Forbidden); watch for spikes of these failures in Azure Monitor and storage analytics logs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- An "infinite" or far-future expiry is only safe if someone keeps extending it — if the policy is never rolled forward, every SAS bound to it starts failing at expiry. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- A SAS expiration policy on the account is only a recommendation: exceeding it is not blocked, it just warns the generator and writes a log entry when Azure Monitor logging is on. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Starting the validity window at the current moment causes intermittent failures for the first minutes on some requests because of clock skew; subtract a margin or omit the start time. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- Restricting the SAS does not limit spend — write plus read access lets a holder upload a 200 GB object and fetch it over and over, and every byte of that traffic is billed to the account owner. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- SAS generation cannot be audited and no API counts how many exist: anyone able to generate a token can do it without the account owner's knowledge, and you must track the count yourself; blocking Shared Key authorization for the account prevents account-key-signed SAS for blob and queue workloads. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
- The `?` delimiter before the query string is not part of the SAS token, so when you build a URL from a portal, PowerShell, Azure CLI or SDK output you may need to append it yourself. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-sas-overview))
