# Perform backup and restore operations by using Azure Backup

## Key concepts

- Azure Backup keeps independent, isolated copies of a VM in a Recovery Services vault and manages the recovery points for you; from the VM blade you pick **Select existing** or **Create new** under **Recovery Services vault**, choose a policy, then **Enable Backup** to bind the policy to the VM. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- **Policy sub type** sets the cadence: **Standard** backs up once a day at a time you choose and keeps recovery points 30 days, while **Enhanced** backs up every four hours at that time and keeps daily backup points for 30 days. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- Enabling backup does not create a recovery point yet - an initial backup runs, and until it finishes **Last backup status** shows **Warning (Initial backup pending)**; select the policy name to see when the next scheduled run is due. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- For an extra copy use **Backup** > **Backup now**, set how long the new recovery point is retained with the calendar control, then **OK**; portal notifications and **View all jobs** confirm the triggered job. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- To protect several VMs, create the Recovery Services vault yourself and configure backup for multiple VMs from the vault instead of repeating the per-VM **Backup** flow. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- Azure Backup installs its own extension on the VM agent: Marketplace images already run the agent, but custom images or on-premises migrations may need it installed by hand, and the extension is patched automatically afterwards. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- Recovery points exist as snapshot tier and vault tier (a **Vault-Standard** recovery point is vault tier), and what you may restore cross-region, cross-subscription or cross-tenant depends on that tier. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- The restore catalogue is **Create a new VM**, **Restore disk**, **Replace existing**, plus **Cross Region Restore**, **Cross Subscription Restore**, **Cross Zonal Restore** and **Cross Tenant Restore** (preview). ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Item-level recovery (ILR) pulls single files out of a recovery point by mounting it read-only with a signed script (iSCSI target inside a TLS 1.2 tunnel), so no VM or disk restore is needed. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))

## Settings and limits

- A vault created from the VM blade takes the VM's region and resource group, and neither can be changed once backup is enabled that way. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- The restore staging storage account must be in the vault's region - only accounts there are listed and you create one if none exists; ZRS redundancy is supported, blob storage is not because the premium account it requires is excluded for cost optimization. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Premium storage accounts are not supported when restoring non-premium VMs, and premium accounts configured with network rules are not supported for managed VM restores. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- When you create a VM from a **Vault-Standard** recovery point, VHD files are also copied for disks under 4 TB or for VMs with fewer than 16 disks; they are then moved to managed storage, so delete them to avoid extra charges. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Cross-region RPO: the primary region can be up to 24 hours behind with the **Standard** policy, replication to the secondary region can take up to 12 hours, and the worst-case secondary RPO stays up to 36 hours even with **Enhanced** because vaulting is daily. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- In a cross-region restore the staging account must sit in the region the vault treats as secondary (a vault in East US 2 with Geo-Redundancy means staging in Central US). ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Cross-region restore covers **Create a VM** and **Restore Disks** only - no VHDs are produced when the source has more than 16 disks, **Replace existing** is unsupported, Ultra Disk machines are excluded, and a triggered cross-region job cannot be cancelled. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Cross Subscription Restore** is on by default and toggled at **Vault** > **Properties** > **Cross Subscription Restore**, where it can be enabled, disabled or permanently disabled; permanent disable is irreversible, and moving the vault to another subscription while it is off breaks restores to the original subscription. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Cross Zonal Restore** works only for managed VMs, needs a vault with ZRS or CRR redundancy, and targets the logical zone of the restoring subscription; it is unsupported for encrypted VMs and for snapshot-tier points. The **Availability Zone** picker appears only when the source VM is zone-pinned and unencrypted, the point is vault tier, the plan is **Create new** or **Restore disks**, and the vault is ZRS in-region or CRR-enabled with a zone-capable paired region. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- For managed-identity restores pick a system- or user-assigned identity in the **Restore configuration** pane; it must already be associated with the vault, or you grant the **VM restore operator** role on the staging storage account and the target resource group. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- ILR only covers VMs deployed with the Resource Manager model and protected to a Recovery Services vault, and it cannot read files out of an encrypted VM backup; the eligible disk families run from the HDD and SSD tiers up through Premium SSD v1 to the newer Premium SSD v2 and Ultra generations. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- ILR ceiling: keep the total recovery at 10 GB or less and expect roughly 1 GB of transfer per hour. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- The script host must match the protected VM's OS generation (Server 2025/2022 with Windows 11 or 10, 2019/2016 with Windows 10, 2012 R2 with 8.1, 2012 with 8, 2008 R2 with 7) and needs bash 4+, Python 2.6.6+, .NET 4.6.2+ and TLS 1.2. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- Outbound access for the script: `download.microsoft.com` or the `AzureFrontDoor.FirstParty` service tag on port 443, the recovery endpoint `https://pod01-rec2.GEO-NAME.backup.windowsazure.com` (plus `.cn`, `.us` and `.de` sovereign variants) or the `AzureBackup` service tag on port 3260, DNS on port 53, and `*.microsoft.com`, `*.windowsazure.com`, `*.windows.net` on port 443. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- The ILR script is read-only, needs elevated administrator rights and is valid for only 12 hours; its password is shown only when the script is generated and the file is Microsoft-signed. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))

## Compare and choose

- **Create new** is the fastest route to a running VM from a recovery point - you set the VM name, resource group and VNet, and the new VM must be in the same region as the source; if the SKU is unavailable there, Azure Backup still restores the disks into the resource group you specified. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Restore disk** fits special configurations - multiple NICs, internal or external load balancers, reserved IPs, an availability set, or Hybrid Use Benefit (**License Type** set to **Windows_Server**) - and it produces a downloadable ARM template you can edit and deploy, or use with PowerShell to build the VM. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Replace existing** requires the VM to still exist: Azure Backup snapshots it first and stores that snapshot in the vault under the retention policy, then swaps the disks, leaving the original disk in the resource group for you to delete. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Replace existing** also works with linked resources such as user-assigned managed identity or Key Vault, but it is unsupported for classic VMs, unmanaged VMs and generalized VMs, and it cannot cross subscriptions. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Pick **Cross Region Restore** for a full or partial outage of the primary region - vault-tier data only and no **Replace existing**; pick **Cross Subscription Restore** when the target subscription differs, since snapshot-tier points stay in the protected VM's subscription and a vault-tier point can be restored to a subscription other than the protected VM's only if Cross Subscription Restore is enabled on the vault (the default target is the protected VM's subscription). ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- **Cross Tenant Restore** (preview) restores vaulted recovery points of managed VMs into another tenant after you map the source and target vaults; only alternate location restore is supported, so snapshot-tier points, original-location restore, Confidential VMs, ADE-encrypted VMs and archive-tier points are excluded. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Use ILR when you only need a few files back and a full VM or disk restore for bulk data - ILR is read-only, capped around 10 GB and runs at roughly 1 GB per hour. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- With **Replace existing**, proceed only when the job's **Transfer Data to Vault** subtask shows success; otherwise restore the latest recovery point with **Create new**. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))

## Gotchas

- Enabling backup from the VM blade locks in the vault's region and resource group, so create the vault yourself if you need different ones. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- Configuration success is not backup success: check for **Warning (Initial backup pending)** until the first recovery point exists. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- A missing VM agent stops the backup extension from installing, so install the agent first on custom or migrated VMs. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-first-look-arm))
- **Deploy Template** fails when the staging account's SAS has **Allow storage account key access** disabled, so deploy the template another way. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- A VM created by **Create new** keeps the SKU the source had when the recovery point was created - later SKU changes are not carried over; and leave NSG rules alone until the restore has finished. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- A portal-restored VM has no availability set and gives you no way to pick one; use **Restore disk** plus the template or PowerShell instead. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- VM NICs are not recreated for machines that have a Public IP and NAT gateway, and a restored SQL VM must be registered again with the SQL provider. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Legacy recovery points of VMs that used unmanaged disks restore only as managed disks, only from the vault tier, and are unavailable for unmanaged encrypted VMs. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- A cross-region restore brings back CMK-enabled VMs that were not backed up in a CMK-enabled vault as non-CMK VMs in the secondary region. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Restoring the last domain controller in a domain, or working in an isolated network, calls for forest recovery rather than a single VM restore; for one DC in a multi-domain forest, restore the disks and build the VM with PowerShell. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
- Run the ILR script on another machine if the protected VM uses dynamic disks (spanned, striped, mirrored or RAID-5 volumes), Windows Storage Spaces, LVM or RAID arrays, or has more than 16 disks or disks over 4 TB - a separate D2v3 VM is recommended. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- Proxies commonly break the iSCSI/3260 path, so run the script on a host with direct outbound access; on Linux it also needs `open-iscsi` and `lshw`, and the script is English-only, so the system locale should be English. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- Always finish with **Unmount Disks** in the **File Recovery** menu, otherwise the next backup of that machine can fail with `UserErrorUnableToOpenMount`; on Linux also run `python scriptName.py clean` to clear orphaned mount points, and never use `mount -a` - mount each logical volume with `sudo mount <LV path> <mountpath>`. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-restore-files-from-vm))
- Subscribe to **Azure Monitor alerts for Azure Backup** so failed restores alert you instead of failing silently. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-arm-restore-vms))
