# Use Azure Network Watcher and Connection Monitor

## Key concepts

- **Network Watcher** bundles monitoring, diagnostics, metrics, and log control for Azure IaaS resources such as VMs, VNets, Application Gateway, and Load Balancer, not for PaaS monitoring or web analytics. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- Creating or updating a virtual network enables **Network Watcher** for that VNet's region with no resource impact or charge; subscriptions that opted out must enable it manually. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- Tools group into **Monitoring** (**Topology**, **Connection monitor**), seven diagnostic tools (**IP flow verify**, **NSG diagnostics**, **Next hop**, **Effective security rules**, **Connection troubleshoot**, **Packet capture**, **VPN troubleshoot**), and **Traffic** (**Flow logs**, **Traffic analytics**). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- **Topology** maps resources and their relationships across subscriptions, resource groups, and locations — configuration, not performance. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- **Connection monitor** is the continuous, end-to-end connectivity service for Azure and hybrid endpoints: it aggregates packet loss and latency for TCP, ICMP, and HTTP checks and adds per-hop metrics. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- A region-specific **Connection monitor** resource contains **Test groups**; each group holds sources, destinations, and **Test configurations**, whose product becomes **Test** records reporting failed-check percentage and RTT (3 × 2 × 2 = 12 tests). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Sources must be observable: Azure VMs and scale sets require the **Network Watcher Agent** VM extension, and on-premises hosts require the **Azure Arc** agent plus the **Azure Monitor Agent**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Destinations can be Azure VMs, scale sets, Arc-enabled hosts, URLs, FQDNs, or IPv4/IPv6 addresses, and destination endpoints never need a monitoring extension. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Measurements land in the monitor's **Log Analytics workspace** and appear as **Azure Monitor Metrics**; **Network Performance Monitor** must be enabled there for logs to upload correctly. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- **Connection monitor (classic)** is deprecated and unavailable, so only the current unified experience can be created. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))

## Settings and limits

- Create from **Network Watcher** → **Monitoring** → **Connection monitor** → **Create**; the **Basics** pane collects **Connection Monitor Name**, **Subscription**, **Region**, and **Workspace configuration**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Workspace configuration** keeps the default workspace or takes a custom one; for a custom workspace clear the default-workspace checkbox and pick its subscription and region. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- The **Region** you choose limits Azure sources to VMs and scale sets created in that same region. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- Every group on the **Test groups** pane needs **Test group Name**, **Sources**, **Destinations**, and **Test configurations**; the **Disable test group** box starts cleared and stops all monitoring in that group. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- The **Azure endpoints** tab lists only resources bound to the monitor's region, arranged **Subscription** > **Resource group** > **VNET** > **Subnet** > **VMs with agents**, and **Group by** re-roots that tree. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- Selecting a VNet, subnet, VM, or scale set stores its resource ID as the endpoint, and by default every VM in that VNet or subnet joins monitoring; narrow it with specific subnets, agents, or the scope property. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- The **Non-Azure endpoints** tab lists Arc hosts already running the **Azure Monitor Agent**; its **Subnet** view picks individual IPs, and adding several subnets creates a custom network named **OnPremises_Network_1**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- The **External Addresses** tab offers Office 365 and Dynamics 365 test URLs, and **Add Endpoint** takes a name plus a URL, IP, or FQDN. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- A **Test configuration** sets **Test configuration name**, **Protocol** (**TCP**, **ICMP**, **HTTP**), **Destination port**, **Test Frequency**, and **Success Threshold**; pick **HTTP** with port **443** for HTTPS. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Create TCP test configuration** appears only when **HTTP** is selected and clones the same sources and destinations into a second configuration named `<name of test configuration>_networkTestConfig`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Disable traceroute** applies to TCP and ICMP only and stops topology and hop-by-hop RTT discovery; **Listen on port** is TCP-only, opens the destination port, and cannot work across regions. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Test Frequency** offers 30 seconds, 1 minute, 5 minutes, 15 minutes, and 30 minutes, plus **custom** from 30 seconds to 30 minutes; a 30-second value means at least one check per period. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Success Threshold** has two parts: **Checks failed**, a percentage equal to packet loss for TCP/ICMP and no-response requests for HTTP, and **Round trip time** in milliseconds. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- Coverage for VNets, subnets, and scale sets is picked manually as **Low**, **Below Average**, **Average**, **Above Average**, or **Full**, each an approximate percentage of instances monitored. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Limits: 100 connection monitors per subscription per region, 20 test groups per monitor, 100 sources and destinations per monitor, and in the portal path a monitor allows only 2 test configurations. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- **Network Watcher** allows 1 instance per region per subscription; the overview also lists 10,000 packet-capture sessions per region per subscription and 1 concurrent VPN troubleshoot operation. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- A test is **Pass** within thresholds and **Fail** when a threshold is breached or failed checks hit 100% with no threshold; **Warning** starts past 80% of the threshold, and defaults are 750 ms RTT for TCP/ICMP and 10% failed checks. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- **Indeterminate** means the Log Analytics workspace holds no data, while **Not Running** means the test group was disabled. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Current monitors expose `ChecksFailedPercent`, `RoundTripTimeMs`, and `TestResult` under `Microsoft.Network/networkWatchers/connectionMonitors`, where `TestResult` encodes 0 = Indeterminate, 1 = Pass, 2 = Warning, 3 = Fail; older monitors also expose `ProbesFailedPercent` and `AverageRoundtripMs`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Azure Monitor retains metrics for 30 days by default while Log Analytics keeps data as long as you configure; the 1-minute minimum granularity aggregates sub-minute probes. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- On the **Create Alerts** pane, **Create alert** enables metric-alert fields, **Condition name** uses the `Test Result(preview)` metric so the rule fires on test failure, **Action group name** takes an email (creating **NPM Email ActionGroup**) or an existing group, and **Enable rule upon creation** sets whether the rule starts active. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))

## Compare and choose

- Use **Connection monitor** for continuous reachability, latency trending, and alerting; use **Connection troubleshoot** for a one-off test from a VM, scale set, Application Gateway, or Bastion host to a VM, FQDN, URI, or IPv4 address, even though its output resembles Connection monitor's. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- Use **Topology** to understand resource relationships and **Connection monitor** to measure actual end-to-end performance and per-hop behaviour. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- Choose the current **Connection monitor** over **Connection monitor (classic)**: only the new experience offers unified Azure and hybrid monitoring, many sources probing many destinations, unified topology, HTTP status-code checks, and compound-resource coverage (automation with PowerShell, the Azure CLI and Terraform is available in both versions). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Against **Network Performance Monitor**, the new Connection monitor adds cross-workspace monitoring, HTTP status-code checks, compound resources such as VNets and on-premises custom networks, connectivity metrics with dimensions, and automation; NPM allows cross-subscription and cross-region but not cross-workspace work. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Public, government, Mooncake, and air-gapped cloud support exists in NPM, classic, and current Connection monitor alike, so that criterion separates none of them. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Source agents differ by location: Azure VMs and scale sets need the **Network Watcher Agent** VM extension, while on-premises hosts need the **Azure Arc** agent and then the **Azure Monitor Agent**, because the **Log Analytics agent** is no longer accepted for on-premises sources. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Choose **HTTP** when valid response codes define success, **TCP** for port-level reachability and optional port opening, and **ICMP** for ping-style checks; TCP and ICMP are the protocols that collect traceroute hop data. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Keep records in **Log Analytics** for custom queries, correlation, export to Excel or Power BI, and long retention; use **Azure Monitor Metrics** for metric alerts and its 30-day default metric window. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- For a one-shot filtering verdict use **IP flow verify** (VM) or **NSG diagnostics** (VM, scale set, Application Gateway); for ongoing connectivity use **Connection monitor**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview))
- Pick the view matching the question: **Connection monitor** for monitor-wide trends, **Test groups** for group trends, **Test** for one source-destination pair, and **Reason** for the breached threshold. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))

## Gotchas

- Migration from classic or NPM maps existing monitors to **Connection monitor** > **Test Group** > **Test**, leaves agents and firewall settings untouched, and migrates alerts automatically, but dashboards and integrations that used the old metrics need manual edits. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- During that migration `ProbesFailedPercent` becomes `ChecksFailedPercent` and `AverageRoundtripMs` becomes `RoundTripTimeMs`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- The portal auto-enables monitoring extensions on selected endpoints; on-premises hosts still need the **Azure Arc** agent, and the **Azure Monitor Agent** replaces the **Log Analytics agent** dependency. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- Enable **Network Performance Monitor** in the target workspace first: **Network Watcher** → **Monitoring** → **Connection monitor** → **+ Enable Non-Azure**, choose subscription and workspace, select **Create**, then verify **NetworkMonitoring(yourWorkspace)** under **Classic** > **Legacy solutions**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- Endpoint status is reevaluated only every 24 hours, so a VM deallocated or switched off mid-cycle stays **Indeterminate** until the cycle ends, the same applies to scale-set instances scaled down, and coverage-level selection is safer than naming individual instances. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- A scale set configured for manual upgrades must be upgraded after the **Network Watcher Agent** extension is installed; auto-upgrade scale sets need no extra step, and consenting to auto-upgrade during creation removes the manual task. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
- Topology merges traceroute with an internal logical route, so Azure-side hops often show no latency values; hop-level issue selection is unavailable for on-premises networks. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- With two connected gateways where one sits outside the source's region, topology reports 'no route learned'; this is a known display defect and connectivity is unaffected. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-overview))
- The **Review + create** pane shows no **Current Cost/Month** for the monitor, yet Log Analytics ingestion and Azure Monitor alert charges apply, and a new monitor takes about 5 minutes to appear on the **Connection Monitor** dashboard. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-monitor-create-using-portal))
