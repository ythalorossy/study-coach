# Create and configure a file share in Azure Files

## Key concepts
- Azure Files delivers fully managed file shares reachable from cloud and on-premises clients over the Server Message Block (SMB) and Network File System (NFS) protocols, with no extra client software needed ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-introduction)).
- SMB targets Windows, Linux, and macOS clients and suits general-purpose shares and hybrid lift-and-shift scenarios, while NFS targets Linux only and is positioned for Linux workloads, containers, and HPC ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-introduction)).
- The FileREST API is exposed on all platforms so applications can read and write share data alongside standard file system I/O ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-introduction)).
- Two management models exist: classic file shares live inside a storage account deployed through the Microsoft.Storage resource provider (SMB and NFS), while the Microsoft.FileShares resource provider deploys file shares as top-level Azure resources, currently for NFS only ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- A single file share exposes either SMB or NFS, not both, but SMB and NFS shares can coexist inside the same storage account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- SMB uses Win32-style semantics with case-insensitive, case-preserving names, Windows-style ACLs, and Kerberos or NTLMv2 authentication ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- NFS uses POSIX semantics with case-sensitive names, UNIX-style permissions, host-based authentication, and supports hard links and symbolic links ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Identity-based authentication is the recommended way to access SMB shares, with options being on-premises AD DS, Microsoft Entra Domain Services, Microsoft Entra Kerberos for hybrid and cloud-only identities, and AD-based Kerberos auth for Linux clients ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- The storage account key still works as an SMB credential (account name as username, key as password) but bypasses share ACLs, grants full share access, and uses NTLMv2, so it is treated as an admin operation ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- All data is encrypted at rest using service-side encryption (SSE); classic shares can use customer-managed keys, but Microsoft.FileShares shares must use Microsoft-managed keys ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- The Azure portal enables Azure Backup by default when you create a new file share, using a Recovery Services Vault in the same region and subscription; NFS shares do not support Azure Backup ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- A private endpoint assigns a private static IP inside your virtual network and works across peered networks, other regions, and ExpressRoute; a service endpoint restricts access to specific subnets at no extra cost but uses a dynamic IP that can change on a zone outage ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)) ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).

## Settings and limits
- Classic file shares are deployed into a storage account whose **kind** is FileStorage (for provisioned SSD/HDD shares) or StorageV2 (for HDD pay-as-you-go shares) ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- The portal's **File share billing** field exposes three models: **Pay-as-you-go** (HDD only, StorageV2), **Provisioned v1** (SSD only, FileStorage), and **Provisioned v2** (SSD and HDD, FileStorage, recommended for new deployments) ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- FileStorage provisioned v2 SKUs are PremiumV2_LRS, PremiumV2_ZRS, StandardV2_LRS, StandardV2_ZRS, StandardV2_GRS, and StandardV2_GZRS; provisioned v1 SKUs are Premium_LRS and Premium_ZRS; pay-as-you-go SKUs are Standard_LRS, Standard_ZRS, Standard_GRS, and Standard_GZRS ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- On the **Basics** tab, **Primary service** should be set to **Azure Files**, which is required to enable the provisioned v2 billing model ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- The **Performance** radio button chooses **Standard** for HDD or **Premium** for SSD, and selecting **Premium** is required for the **Require Encryption in Transit for NFS** checkbox to appear ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Require Encryption in Transit for SMB** and **Require Encryption in Transit for NFS** set per-protocol encryption that overrides the storage account-level **Secure transfer required** setting for SMB and NFS traffic ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Enable soft delete for file shares** is on by default with **Days to retain deleted file shares** defaulting to 7 days; soft-deleted shares are billed for their used capacity even in provisioned models ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Enable storage account key access** controls whether shared keys can be used to mount the share or call FileREST ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Default to Microsoft Entra authorization in the Azure portal** controls whether the portal browses shares using Entra identity rather than shared keys ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Minimum TLS version** applies to FileREST requests; SMB doesn't use TLS, and for NFS the AzNFS mount helper uses TLS 1.2 or 1.3 ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Storage account names must be 3-24 characters, lowercase letters and numbers only, and globally unique; the account name is the SMB server name when mounting ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- File share names must be all lowercase letters, numbers, and single hyphens, must start and end with a lowercase letter or number, and cannot contain two consecutive hyphens ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- A provisioned v2 share needs **Provisioned storage (GiB)**, then either **Recommended provisioning** of IOPS and throughput or **Manually specify IOPS and throughput**, plus a **Protocol** choice (SMB by default, or NFSv4.1) ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- A provisioned v1 share needs only **Provisioned storage (GiB)** and a **Protocol**; IOPS and throughput are derived from the provisioned storage ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- A pay-as-you-go HDD share needs only a name and an **Access tier** (transaction optimized, hot, or cool) and supports SMB only ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- NFSv4.1 uses TCP port 2049, so clients and any NSG rules associated with permitted subnets must allow outbound (and for VNet rules, inbound) traffic on that port ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Snapshots are read-only, point-in-time, incremental copies; a file share supports up to 200 snapshots that can be retained for up to 10 years ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Azure Backup for SMB shares provides grandfather-father-son (GFS) daily, weekly, monthly, and yearly retention, auto-enables soft delete, and applies a delete lock to the storage account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).

## Compare and choose
- Pick **Provisioned v2** for new deployments of either SSD or HDD because it is the recommended billing model across both media tiers ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Pick **Provisioned v1** only when you need an SSD share and want to stay on the older v1 billing model; it cannot host HDD shares ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Pick **Pay-as-you-go** only for HDD SMB shares where you want to pay per stored GiB and per transaction rather than provisioning IOPS and throughput; it requires a StorageV2 account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Pick **SSD** for I/O-intensive workloads needing single-digit millisecond latency such as databases, web hosting, and dev environments; SSD is also the only tier that supports NFS ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Pick **HDD** for cost-effective general-purpose file shares when low latency is not critical, such as team shares cached on-premises through Azure File Sync ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Pick **LRS** for lowest-cost single-region durability (three copies in one storage cluster), **ZRS** for zone resilience (three copies across three availability zones), **GRS** for cross-region async replication (six copies total), and **GZRS** to combine ZRS in the primary region with GRS-style async replication to a secondary region ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- SSD file shares support only **LRS** and **ZRS**, while HDD file shares support all four redundancy options ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Pick a **private endpoint** for NFS or for SMB over VPN/ExpressRoute when you need a static IP, cross-region peering, or on-premises routing; standard Private Link data processing rates apply ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Pick a **service endpoint** for NFS when you only need to restrict access to specific VNet subnets, do not need a static IP, and can tolerate a possible remount on a zone outage; there is no extra charge ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Pick identity-based authentication (Microsoft Entra Kerberos, AD DS, or Microsoft Entra Domain Services) over the storage account key for SMB to get per-user ACLs instead of full administrator access; reserve the storage account key for legacy needs only ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Pick the **Microsoft.FileShares** resource model (NFS only today) when you want per-share networking, billing, and security managed on the file share without first creating a parent storage account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).

## Gotchas
- A file share cannot expose SMB and NFS at the same time; pick the protocol at share creation ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- You cannot change a share's media tier after creation; moving between HDD and SSD requires creating a new share and copying the data ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- The **Enable hierarchical namespace** and **Enable network file system v3** checkboxes are Azure Blob-only: they are disabled for FileStorage accounts but can still be checked on StorageV2 accounts even when **Primary service** is set to **Azure Files**, and they have no effect on file shares ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Azure Files does not support read access to the secondary region on RA-GRS or RA-GZRS accounts without performing a failover, so enabling read access on those accounts has no effect on file shares ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- **Secure transfer required** applies only to FileREST; the per-protocol **Require Encryption in Transit** settings control SMB and NFS encryption, whether or not you select them ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Unchecking **Require secure transfer for REST API operations** allows legacy SMB 2.1 clients in the same region and unencrypted SMB 3.x or HTTP FileREST, but SMB 2.1 clients from outside the share's Azure region are rejected ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Soft delete is on by default and soft-deleted shares are still billed for used capacity, so a long retention period increases cost ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Azure Backup is enabled by default in the portal but only works for SMB shares and requires a Recovery Services Vault in the same region and subscription; NFS shares cannot use Azure Backup ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)).
- Service endpoint IPs can change during a zone outage, forcing clients to remount; private endpoints avoid this because they use a static private IP ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/create-classic-file-share)) ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Many ISPs block port 445 for outbound internet traffic, so on-premises SMB access usually requires a VPN or ExpressRoute combined with a private endpoint ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Mounting with the storage account key uses NTLMv2 and bypasses share ACLs, giving the mount full administrator rights over every file and folder; do not use this for end-user access ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Customer-managed encryption keys are not supported on Microsoft.FileShares shares; those shares must use Microsoft-managed keys ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- Defender for Storage malware detection by full file hash applies only to REST API uploads and does not inspect SMB or NFS traffic ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
- ZRS for SSD file shares is available only in a subset of Azure regions, so you must confirm regional support before choosing that SKU ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-planning)).
