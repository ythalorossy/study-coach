# Configure private endpoints for Azure PaaS

## Key concepts

- A private endpoint is a network interface that takes a private IP address from your virtual network and connects you privately to a service powered by Azure Private Link, effectively bringing that PaaS service into your VNet. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- A read-only network interface is created automatically for the lifetime of the endpoint and is assigned a dynamic private IP from the chosen subnet; that IP does not change during the endpoint's lifecycle. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Connectivity is one-way and client-initiated: only clients targeting the private endpoint can open connections, and the service provider has no routing configuration to reach into customer networks. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Reachable peers are the same virtual network, regionally peered VNets, globally peered VNets, on-premises environments over **VPN** or **Express Route**, and other services powered by Private Link. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Placement rule: the private endpoint must be deployed in the same region and the same subscription as its virtual network, while the private-link resource itself may live in a different region. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- The platform validates traffic against one specific private-link resource and subresource, so each subresource needs its own endpoint — for Azure Storage you need separate endpoints for `blob` and `file`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- A private endpoint adds a private IP path but does not by itself block public traffic; pair it with service-level controls such as **Public network access** set to **Disabled** or IP firewall rules. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Both the subscription holding the private-link resource and the subscription holding the private endpoint must be registered with the Microsoft network resource provider (`Microsoft.Network`). ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))

## Settings and limits

- Endpoint properties: **Name** (unique within the resource group), **Subnet** (where the private IP is assigned), **Private-link resource** (resource ID or alias), **Target subresource**, **Connection approval method** (**Automatic** or **Manual**), **Request message** (used to identify a manual request), and the read-only **Connection status**. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- **Connection status** has four values — **Approved**, **Pending**, **Rejected**, **Disconnected** — and only endpoints in the **Approved** state can send traffic. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Automatic approval requires the permission `Microsoft.<Provider>/<resource_type>/privateEndpointConnectionsApproval/action` on the target resource; without it you must request manually and the endpoint stays **Pending**. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- The private-link resource owner can review, approve, reject, or delete a connection in any state; deleting the connection puts the endpoint in **Disconnected** (informative only), after which only the endpoint owner can delete the endpoint resource. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Portal **Resource** tab: **Connection method** = *Connect to an Azure resource in my directory*, then pick **Subscription**, **Resource type** (for example `Microsoft.Web/sites`), **Resource**, and **Target subresource** (for example `sites`). ([Learn](https://learn.microsoft.com/en-us/azure/private-link/create-private-endpoint-portal))
- Portal **Virtual network** tab: choose **Virtual network** and **Subnet**, set **Network policy for private endpoints** to **edit** and tick **Network security groups** and **Route Tables** in the subnet policy, then pick **Private IP configuration** = dynamically allocated or statically allocated (**ipconfig-1**, for example **10.0.0.10**). ([Learn](https://learn.microsoft.com/en-us/azure/private-link/create-private-endpoint-portal))
- Static IP configuration is unsupported for **Azure Kubernetes Service (AKS)**, **Azure Application Gateway**, **HD Insight**, **Recovery Services Vaults**, and third-party **Private Link** services. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- NSG, UDR and ASG support on the endpoint NIC is opt-in per subnet; effective routes and security rules are not shown for that NIC in the portal, and NSG flow logs are unsupported for inbound traffic destined for a private endpoint. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- NSG rule scaling for endpoints: sources × destinations × port ranges must stay at or below 250K (50×50×100 = 250K is valid, 100×100×100 = 1M is invalid), and source port filtering is interpreted as a wildcard `*`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- An application security group may hold at most 50 members (IP configurations) per ASG coupled to the NSG on the endpoint subnet; connection failures can occur beyond that. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- With user-defined routes, SNAT traffic destined for a private endpoint so return traffic is honoured through an NVA; the `disableSnatOnPL` tag on the NVA removes that need. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Regional limits: NSG, UDR and ASG support for private endpoints is unavailable in **West India**, **Australia Central 2**, **South Africa West** and **Brazil Southeast**; NSG support is additionally unavailable in all Government regions and all China regions. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Private endpoints can only be created on a General Purpose v2 (GPv2) storage account. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Recommended private DNS zones for Storage: `blob`/`blob_secondary` → `privatelink.blob.core.windows.net`, `table` → `privatelink.table.core.windows.net`, `queue` → `privatelink.queue.core.windows.net`, `file` → `privatelink.file.core.windows.net`, `web` → `privatelink.web.core.windows.net`, `dfs` → `privatelink.dfs.core.windows.net`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Other commonly tested zones: Key Vault → `privatelink.vaultcore.azure.net`, Key Vault HSM → `privatelink.managedhsm.azure.net`, SQL Database → `privatelink.database.windows.net`, SQL Managed Instance → `privatelink.{dnsPrefix}.database.windows.net`, Cosmos DB `Sql` → `privatelink.documents.azure.com`, Web/Function Apps → `privatelink.azurewebsites.net` plus `scm.privatelink.azurewebsites.net`, Event Hub and Service Bus → `privatelink.servicebus.windows.net`, API Management → `privatelink.azure-api.net`, App Configuration → `privatelink.azconfig.io`, Redis → `privatelink.redis.cache.windows.net`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Cosmos DB subresources each map to their own zone: `Sql` → `privatelink.documents.azure.com`, `SqlDedicated` → `privatelink.sqlx.cosmos.azure.com`, `MongoDB` → `privatelink.mongo.cosmos.azure.com`, `Cassandra` → `privatelink.cassandra.cosmos.azure.com`, `Gremlin` → `privatelink.gremlin.cosmos.azure.com`, `Table` → `privatelink.table.cosmos.azure.com`, `Analytical` → `privatelink.analytics.cosmos.azure.com`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Zone-name placeholders: `{regionCode}` is a short code such as `eus` or `ne` (used by Backup, Site Recovery, Automation), `{regionName}` is the full region name such as `eastus` or `northeurope` (used by AKS, Container Apps, Data Explorer, Batch), and Managed Prometheus uses a plain `{region}`; list them with `az account list-locations -o table`. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Sovereign clouds use different suffixes: Government uses `.us` and `usgovcloudapi.net` (for example SQL → `privatelink.database.usgovcloudapi.net`, Key Vault → `privatelink.vaultcore.usgovcloudapi.net`), and China uses `.cn` (for example Cosmos DB → `privatelink.documents.azure.cn`). ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))

## Compare and choose

- Approval method: choose **Automatic** when you own or have permission on the target resource (permission `Microsoft.<Provider>/<resource_type>/privateEndpointConnectionsApproval/action`); choose **Manual** otherwise so the resource owner can approve, reject, or leave the request **Pending**. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Connecting by **alias** — the moniker a service owner publishes for a custom Private Link service behind a standard load balancer — requires the manual method, with the manual request parameter set to **True** during creation. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Prefer a single private endpoint per private-link resource per network; extra endpoints for the same resource are allowed but can produce duplicate DNS entries and resolution conflicts. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Several endpoints for one service may sit on the same or different subnets of the same VNet, but each needs its own matching private DNS zone. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- DNS approach: the host file is recommended for testing only, a **Private DNS zone** linked to the VNet is the standard production option, and **Azure Private Resolver** is the optional third choice. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- For Web/Function Apps create records in `privatelink.azurewebsites.net` for the app and `scm.privatelink.azurewebsites.net` for SCM/Kudu; when you already use Azure private DNS zones, do not deploy the SCM one as a separate zone. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- For Container Registry use `privatelink.azurecr.io` and let entries be added automatically rather than deploying `{regionName}.data.privatelink.azurecr.io` as an additional zone. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- For the web-app scenario, the App Service plan must be **Basic**, **Standard**, **PremiumV2**, **PremiumV3**, **IsolatedV2**, or **Functions Premium** (Elastic Premium). ([Learn](https://learn.microsoft.com/en-us/azure/private-link/create-private-endpoint-portal))

## Gotchas

- A successful public DNS lookup proves only that a resource with that name exists: the `privatelink.<service>.<region>.<suffix>` CNAME chain is deliberately resolvable from the internet. It does not confirm a private endpoint is attached, reveal the private IP, or grant data-plane access; with **Public network access** **Disabled** or a firewall denial, the service rejects the connection regardless of DNS. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Never attach one existing private DNS zone to two different private endpoints of the same service type: the initial A record is deleted and resolution breaks for both; create a zone per endpoint and don't mix records for several services in one zone. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Don't override a zone that is actively used to resolve public endpoints unless you add DNS forwarding to public DNS, otherwise clients cannot resolve at all. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- A private DNS zone for a resource type answers **NXDOMAIN** for public resources that already have private endpoint connections, unless you enable fallback to Internet on the VNet link or add a manual A record — and a manual A record won't update if the public IP changes. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Private endpoint DNS configurations are only generated automatically if you use the recommended zone names from the service tables. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Azure File Shares connected over the public endpoint must be remounted after you move to the private endpoint. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns))
- Denying outbound traffic on a private endpoint is not a valid scenario, because the service provider never originates traffic to the endpoint. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- When a private endpoint is combined with NSG filters, Azure Cosmos DB may require all destination ports to be open. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- An endpoint in **Pending**, **Rejected**, or **Disconnected** state silently passes no traffic — check **Connection status** rather than assuming the private IP works. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))
- Portal defaults to remember: the endpoint's NIC is named **private-endpoint-nic**, the **DNS** tab is left at its defaults, and with a static **10.0.0.10** in **subnet-1** the name `webapp-1.azurewebsites.net` resolves to `webapp-1.privatelink.azurewebsites.net` at **10.0.0.10** inside the VNet. ([Learn](https://learn.microsoft.com/en-us/azure/private-link/create-private-endpoint-portal))
