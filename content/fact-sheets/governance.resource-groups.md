# Manage resource groups

## Key concepts

- A resource group is a container that holds the related resources of an Azure solution; you decide its membership, and the recommended rule is to put resources with the same lifecycle together so they are deployed, updated and deleted as a unit. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Each resource can exist in only one resource group at a time, but you can add or remove resources whenever you like and move a resource from one group to another. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Resource groups are resources themselves, alongside subscriptions, management groups and tags, which is why a group can be tagged, locked, used as an RBAC scope and deleted like any other resource. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Azure has four management scopes — management groups, subscriptions, resource groups and resources — and settings placed at a higher scope are inherited by every scope below it. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- The region you give a resource group is where its metadata is stored, not where its resources run: resources inside one group can sit in different regions, though using the same location is recommended. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- Pick the group location near where your control plane operations originate, because Resource Manager routes ARM control plane calls for the group's resources through that location; data plane traffic such as an HTTP request to a web app or reads/writes on a storage account bypasses it. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- The portal exposes a resource group scope, so every group has a Metrics blade (CPU and other metrics), a Deployments blade (history of ARM template and Bicep deployments targeting that group), a Policy blade (policies enforced on it) and a Diagnostics settings blade (errors and warnings). ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- Azure Resource Manager is the single management service behind every tool: it authenticates and authorizes each request and then forwards it to the correct Azure service, which is why the portal, PowerShell, the Azure CLI, REST APIs and SDKs give consistent results. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Deleting a resource group deletes every resource inside it, so lifecycle-based grouping turns cleanup into a single action. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Tags applied to a resource group are not inherited by the resources it holds, so tag-driven reporting needs the tags applied to the resources themselves. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- When two or more operations update the same resource at once, Resource Manager lets one succeed and fails the others with a 409 error so the final state is always conclusive. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))

## Settings and limits

- Creating a group in the portal needs three values — Subscription, Resource group (name) and Region (for example Central US) — then Review + create; it takes only a few seconds and the bell icon's "Go to resource group" notification opens the new group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- Locks are created from the group's **Locks** blade with **Lock name**, **Lock type** and **Notes**; the portal lock types are **Read-only** and **Delete**, and they stop other people accidentally deleting or modifying critical resources. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- One resource group can hold up to 800 instances of a given resource type, although a small number of types are exempt from that cap. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- A single move operation fails immediately with an error above 800 resources, and even a smaller move can fail by timing out, so split large moves into several operations. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- During a move both the source and the destination resource group are locked for up to four hours: you cannot create, delete or update resources in them, but existing resources stay fully operational with no downtime for anything depending on them. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- A move changes the resource ID, whose format is `/subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/{resourceProviderNamespace}/{resourceType}/{resourceName}`, so any dashboard, script or template holding the old value must be updated. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Only top-level resources go in the move request — child resources such as `Microsoft.Compute/virtualMachines/extensions` travel with their parent and cannot be moved on their own. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- The account performing the move needs **Microsoft.Resources/subscriptions/resourceGroups/moveResources/action** on the source resource group and **Microsoft.Resources/subscriptions/resourceGroups/write** on the destination. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Role assignments do not travel with a resource: an assignment scoped to the moved resource or its child is left orphaned, is eventually removed automatically by the system, and must be recreated after the move. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- For a cross-subscription move both subscriptions must be active and in the same Microsoft Entra ID tenant; compare them with `az account show --subscription <name> --query tenantId` or `(Get-AzSubscription -SubscriptionName <name>).TenantId`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Across subscriptions the resource and its dependent resources must already sit in the same resource group and be moved together, for example a virtual machine together with its managed disks; the documented pattern is consolidate dependents into one group, move them all to the target subscription, then optionally redistribute them into separate groups there. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- The destination subscription must already be registered for the resource's provider — check with `az provider list` and register with `az provider register --namespace Microsoft.Batch` — otherwise the move fails saying the subscription isn't registered for a resource type. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Check the destination subscription's quota before moving, because a move consumes capacity in the target subscription. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Access control on a group is handled with Azure RBAC roles, while protections against accidental deletion or modification come from resource locks — the two are separate controls applied at resource group scope. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- Resource Manager runs separate instances in every Azure region and is spread across availability zones, keeps working during maintenance, and is best reached through the global endpoint `management.azure.com`; new API capabilities reach the portal within 180 days and support for protocols older than TLS 1.2 ended on March 1, 2025. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))

## Compare and choose

- The portal **Move** button offers three distinct targets: move to a new resource group, move to a new subscription, or move to a new region, and the regional option is handled by Azure Resource Mover rather than by a resource group move. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Choose the region option when the goal is a different physical location, because an ordinary move only changes the associated resource group (and subscription) and never alters a resource's region. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- You cannot move a resource group itself to another subscription; move all of its resources into a resource group in the target subscription instead, and remember that tags, role assignments and policies are not carried over and must be applied manually on the new group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- To test a move without performing it, use the validate operation — `az resource invoke-action --action validateMoveResources`, `Invoke-AzResourceAction`, `ResourceManagementClient.resources.begin_validate_move_resources`, or `POST https://management.azure.com/subscriptions/<subscription-id>/resourceGroups/<source-group>/validateMoveResources?api-version=2019-05-10` — because validation also runs automatically when you submit a real move. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- In REST validation a 202 means the request was accepted but the outcome isn't decided yet (poll the `location` URL after the `retry-after` seconds), a 204 means validation succeeded, and a failure returns an error such as `ResourceMoveProviderValidationFailed`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Once validated, run the actual move with `az resource move --destination-group <name> --ids <id1> <id2>` (add `--destination-subscription-id` for a subscription change), `Move-AzResource -DestinationResourceGroupName <name> -ResourceId <ids>`, `begin_move_resources`, or the `POST .../moveResources` REST operation. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Pick the policy scope by how widely it should reach: assigned at subscription scope it applies to every resource group and resource in that subscription, while assigned at resource group scope it applies only to that group and its resources and to no sibling group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))
- Group by lifecycle, not by convenience — resources that must be deployed, updated and deleted together belong in one group, while related resources on different cycles go in separate groups and can still reference each other across group boundaries, such as a web app pointing at a database elsewhere. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview))

## Gotchas

- A resource group's region is not where its workload runs — it is only where the group's metadata is stored, so placing the group in a compliance region never forces its resources into that region. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal))
- A **Read-only** lock on the source, the destination resource group or the subscription blocks the move entirely. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- The four-hour lock is the maximum window, not the expected duration: when it expires Resource Manager unlocks both groups, resources that succeeded end up in the destination group and resources that failed stay in the source group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- A move has two phases — resources move first, then dependent resource providers are notified — so a provider failing either phase can keep both groups locked for the full four hours while Resource Manager retries the failed steps. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- A moved resource keeps its dependency on its own child resources, but dependencies on other resources can break and must be configured again afterwards. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Error **MissingMoveDependentResources** means a dependent resource is neither already in the destination nor listed in the request; a typical virtual machine move also needs `virtualMachines` and `disks` from Microsoft.Compute, plus `networkInterfaces`, `publicIPAddresses`, `networkSecurityGroups` and `virtualNetworks` from Microsoft.Network, and the storage account. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Error **MoveCannotProceedWithResourcesNotInSucceededState** blocks the move when anything isn't in a Succeeded state; if the source or target group holds a virtual network, every resource that depends on it — directly or indirectly, even resources outside both groups — is checked. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Error **RequestDisallowedByPolicy** comes from pre-move policy validation, for example an organizational policy that denies creating a key vault in the target resource group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- A virtual network gateway cannot move separately from its virtual network, so both must already be in the same resource group and be moved together. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Not every resource type supports a move, and on Azure Stack Hub you cannot move resources between groups at all; Azure App Services, the classic deployment model, networking, Recovery Services vaults and virtual machines each have their own move limitations to check first. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- Because a move rewrites resource IDs, anything hard-coding the old ID — portal custom dashboards, scripts, templates — breaks silently, and the portal makes you acknowledge this before it starts the move. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
- The source and destination groups cannot join another move while one is running, so you can't move resources to or from a third group at the same time. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/move-resource-group-and-subscription))
