# Troubleshoot load balancing

## Key concepts

- An Azure Load Balancer health probe checks whether app instances are up by sending them a request; protocols are TCP, HTTP and HTTPS, and the probe config plus its responses decide which backend pool instances get new connections. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Every load balancing rule needs a health probe; a probe only takes effect once at least one rule references it, which is listed in its **Used by** property. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Probe state gates inbound traffic only: a failed probe makes the load balancer stop sending new connections to that instance, while outbound connectivity is unaffected. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Probe properties are **Name**, **Protocol**, **Port**, **Interval (seconds)**, **Threshold** and **Used by**; the **Port** must be one the VM really listens on. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- A TCP probe opens with a three-way handshake and closes with a four-way close; it fails when the listener stays silent through the timeout window or returns a TCP reset. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- An HTTP/HTTPS probe issues an HTTP GET on the configured path (relative paths allowed; HTTPS adds TLS); it fails on any status other than 200 (e.g. 403, 404, 500), on no answer within the timeout, or on a TCP reset. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- An endpoint is marked healthy once a probe succeeds after the VM boots, and only healthy endpoints are eligible for new flows. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- HTTPS probes need certificates whose whole chain uses a signature hash of at least SHA256. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Allow probe traffic inbound: IPv4 probes always originate from `168.63.129.16`, IPv6 probes use link-local `fe80::1234:5678:9abc`, and the `AzureLoadBalancer` service tag permits probe traffic by default in NSGs. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Standard Load Balancer exposes per-endpoint and per-backend-endpoint probe status through Azure Monitor; Basic Load Balancer (retired) has no Azure Monitor log support. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- The service troubleshooting hub lists the common scenarios: no outbound connectivity from Standard internal load balancers, no inbound connectivity to Standard external load balancers, changing the backend port of an existing load-balancing rule, traffic still flowing after a VM leaves a backend pool, and a load balancer in a failed state. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-troubleshoot))
- Standard load balancer diagnostics come from two pillars: multi-dimensional metrics and alerts in Azure Monitor, plus the **Resource health** page under **Monitor** > **Service health**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))

## Settings and limits

- **Interval** defaults to 5 seconds in the portal but 15 seconds via ARM templates, REST API, CLI or PowerShell; the minimum is 5 seconds. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- HTTP/HTTPS probes have a built-in 30-second timeout; TCP probes have no separate timeout and fail once the interval elapses and the next probe is sent. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- An interval longer than the 30-second HTTP/S timeout (e.g. 120 s) makes the probe time out and fail; a shorter interval fails as soon as it completes with no response, and the next probe goes out immediately. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- **Threshold** counts consecutive successes or failures to flip instance state: with TCP threshold 2 an instance needs 2 consecutive replies to start taking traffic and 2 consecutive failures/timeouts to be removed. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- For HTTP probes an explicit 200 or non-200 response marks the probe up/down immediately and resets the threshold, so the threshold only applies when the probe times out for silence. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- SKU behaviour differs: Standard (TCP, HTTP, HTTPS) keeps all TCP flows going when every probe is down, while Basic (TCP, HTTP only) lets all TCP flows expire. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- One instance down: new TCP connections reach the remaining healthy endpoints and established TCP connections continue, while existing UDP flows move to another healthy pool instance. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- All instances down: no new flows are sent; Standard preserves established TCP flows when the pool has more than one backend instance, Basic terminates them, and existing UDP flows terminate in both. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- HTTPS probes do not support mutual authentication with a client certificate, and HTTP probes cannot use hostnames as probe backends. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- HTTP probes may not target ports 19, 21, 25, 70, 110, 119, 143, 220 and 993, and TCP timestamps can throttle traffic enough to make probes time out. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- The retired Basic tier also refuses scale set backends: you cannot pair Basic Load Balancer health probes with a virtual machine scale set. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Recommended metric aggregation: **Average** for **Data Path Availability**, **Health Probe Status**, **Allocated SNAT Ports** and **Used SNAT Ports**; **Sum** for **SYN Count**, **SNAT Connection Count**, **Byte Count** and **Packet Count**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- **Max** and **Min** aggregations are unavailable for SYN count, packet count, SNAT connection count and byte count, and **Count** is not recommended for data path availability or health probe status — use **Average**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- **Data Path Availability** can take up to 10 minutes to appear in Azure Monitor after a load balancer is created or updated, and it is only produced for frontend IP configurations that have load balancing rules. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Metrics are sampled once per minute, so a five-minute time aggregation with **Sum** (for example SNAT allocation) displays five times the true total — use a time aggregation above one minute with **Sum** or **Count**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- **Resource health** is evaluated every two minutes from data path availability: **Available**, **Degraded** (under 90% but over 25% health for at least two minutes), **Unavailable** (under 25% health for at least two minutes) and **Unknown** (no data path availability data for 10 minutes). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Recommended alert shape: **Average** aggregation, five-minute look-back window, 95% threshold, plus an optional action group for automated repair. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Inbound alerting uses two rules: data path availability split by frontend port and frontend IP with a condition of less than or equal to 0, and health probe status split by backend IP address and backend port using **Average**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Outbound alerting uses **SNAT Connection Count** filtered on **Connection State = Failed** with **Total** aggregation split by backend IP (threshold greater than zero), and **Used SNAT Ports** split by backend IP and protocol with **Average** (e.g. low severity at 75% of allocated ports, high severity at 90–100%). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))

## Compare and choose

- Standard vs Basic: choose Standard for HTTPS probes, HA Ports rules, multi-dimensional metrics and Azure Monitor integration, and because it keeps established TCP flows alive when all probes are down; Basic is retired and drops them. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- **Data Path Availability** vs **Health Probe Status**: the first judges Azure's regional data plane and frontend reachability, the second judges your app's health as configured; charting both separates platform faults from config/app faults. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- TCP vs HTTP/HTTPS probe: TCP covers a plain listener check; HTTP/HTTPS lets the application return its own verdict, and because the probe port may equal the service port, failing the probe is a deliberate way to drain new connections. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- For a UDP application still use a TCP, HTTP or HTTPS probe matching the matching listener; for **HA Ports** rules on Standard, one probe must reflect the status of the whole instance. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- **Used SNAT Ports** vs **Allocated SNAT Ports**: comparing them per backend instance shows exhaustion risk — **Average** gives per-instance values, **Sum** gives the load balancer total, and **Azure NAT Gateway** adds outbound capacity. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- To rehearse a probe failure, block the probe with an NSG rule on the destination port or source IP — but only in testing, since blocking the probe IP or port in production is unsupported. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- For an NVA, probe the appliance itself rather than the VMs it proxies to, and make it answer on the NIC that received the probe; verify with `az network watcher flow-log list` and a packet capture filtered on `168.63.129.16`. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))

## Gotchas

- Never place the Microsoft-owned range containing `168.63.129.16` in your virtual network — it collides with the health probe source address and breaks the scenario. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Blocking the load balancer health probe IP or port with NSG rules is unsupported and makes NSG rules take effect late, so probe results stop reflecting real backend availability. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Probe definitions are neither mandatory nor validated by Azure PowerShell, CLI, ARM templates or the API; probe validation happens only in the Azure portal, so check rules by hand. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- A flapping probe keeps an endpoint out of rotation longer before it returns to healthy — the extra delay is intentional policy, not a defect. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- With several NICs, respond on the interface the probe arrived on, which may need per-interface source NAT inside the VM. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Never translate or proxy a probe to another instance (e.g. an NVA forwarding to VMs behind it): one unhealthy VM then marks the appliance down and can cascade into an application outage. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Inbound NAT rules need no health probe, unlike load balancing rules. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
- Deallocated VMs are not probed and their metrics stop being reported, showing as a dashed line or an error in the portal. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Empty backend pools mean no valid data paths, so data path availability is missing and alerts on that metric never fire. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Byte counts aren't spread evenly across backend instances — expected, because the load balancing algorithm works on flows. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Bandwidth metrics such as byte count, packet count and SYN count miss traffic reaching an internal load balancer via a UDR, for example from an NVA or firewall. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-standard-diagnostics))
- Dual-stack load balancers need an NSG rule for the IPv6 health probe to function. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview))
