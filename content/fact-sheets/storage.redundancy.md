# Configure Azure Storage redundancy

## Key concepts

- A storage account is the single Azure resource that holds blob containers, file shares, tables and queues, and one **Redundancy** setting governs all of its services — every resource in the account shares the same redundancy, so put workloads with different needs in separate accounts. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- **Locally redundant storage (LRS)** keeps three copies in one datacenter in the primary region, giving at least 99.999999999% (11 9s) durability per year; it is the cheapest option and covers node, server, rack, drive and server failures only. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy)) ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- **Zone-redundant storage (ZRS)** writes synchronously to three or more availability zones in the primary region, giving at least 99.9999999999% (12 9s) durability; a write succeeds only after data lands in all three zones, or in all available zones if one is temporarily down. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- **Geo-redundant storage (GRS)** replicates with LRS in the primary and then copies asynchronously to the paired secondary region, where LRS is used again; **Geo-zone-redundant storage (GZRS)** does the same but uses ZRS in the primary. Both target at least 99.99999999999999% (16 9s) durability. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- The only difference between GRS and GZRS is how the primary region is replicated; in the secondary region both always use synchronous LRS, which protects against hardware failure but not regional disaster on its own. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- The secondary region is the fixed pair of your chosen primary region and cannot be changed; a region must support availability zones and have a paired region to offer GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- **RA-GRS** and **RA-GZRS** add read access to the secondary endpoint, so apps can keep reading during a primary outage; without the RA prefix the secondary copy is unreadable until a failover promotes it. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- With read access enabled, the secondary endpoint adds the suffix `-secondary` to the account name — for example `myaccount-secondary.blob.core.windows.net` — and the same account access keys work for both endpoints. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Redundancy is not backup: Azure Storage runs cyclic redundancy checks (CRCs) and checksums to repair corruption, but all replicas always hold the same current state, so deletes and overwrites are applied to every copy at once. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Changing an existing account's replication has three routes: change the geo-redundancy and read-access settings directly, run a **conversion** to add or remove zone redundancy, or do a **manual migration** to a new account when the first two are unsupported or you need a fixed completion date. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Geo-redundancy and read access can be toggled in one operation, but any change that also touches zone redundancy must be a separate two-step conversion, and the two steps can run in either order. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))

## Settings and limits

- In the portal, change redundancy on the storage account under **Data management** > **Redundancy**, edit the **Redundancy** setting and select **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Changing the setting in the portal causes no application downtime, including changes that need a conversion. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Converting to zone redundancy requires no downtime and no data loss; HNS-enabled accounts may pause for under 30 seconds while switching resiliency level, after which requests complete automatically, and endpoints, keys and SAS tokens stay the same. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- A **customer-initiated conversion** is preferred over a support request and can be started and tracked from the portal, PowerShell or the Azure CLI; it typically begins within 72 hours but has no completion SLA. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Conversion status on the **Redundancy** page moves from **Submitted for conversion** to **In Progress**, then **Completed** or **Failed**; a failure requires a Microsoft support request to diagnose. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- A **support-initiated conversion** uses a new support request with **Issue type** **Technical**, **Service type** **Storage Account Management**, **Problem type** **Data Migration** and **Problem subtype** **Migrate to ZRS, GZRS, or RA-GZRS**; the **Solutions** page checks eligibility by target replication type and account names. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Once a zone-redundancy conversion finishes, let a full day pass before touching the redundancy setting again, so background work can settle; a jump from LRS to GZRS therefore needs two operations on separate days — LRS to ZRS first, then ZRS to GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Boot diagnostics blocks zone redundancy: every attempt to add it (LRS to ZRS, GRS to GZRS) fails, and boot diagnostics on premium or zone-redundant accounts gives `StorageAccountTypeNotSupported` at VM start, so disable it first and resubmit. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Conversions are blocked when NFSv3 protocol support is enabled for Azure Blob Storage or when the account holds Azure Files NFSv4.1 shares with public endpoints; to convert the latter, disable public endpoint access, convert, then reconfigure endpoints. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- The archive tier is supported on LRS, GRS and RA-GRS accounts only, so moving archived blobs requires relocating or selectively rehydrating them before converting to ZRS, GZRS or RA-GZRS; an LRS account with archive blobs can go to GRS/RA-GRS only after rehydration. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Service support: Blob Storage (including Data Lake Storage), Queue and Table support all six options; Azure Files supports LRS, ZRS, GRS, GZRS but never RA-GRS/RA-GZRS; managed disks and Elastic SAN are LRS/ZRS only. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Account type support: standard general-purpose v2 (`StorageV2`) supports everything, premium block blobs (`BlockBlobStorage`) and SSD file shares (`FileStorage`) support LRS/ZRS (plus GRS for `StorageV2`), premium page blobs are LRS only, and legacy v1 (`Storage`) and legacy blob (`BlobStorage`) accounts cannot use ZRS or GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- A v1 account must be upgraded to v2 before a conversion, ZRS Classic accounts are deprecated and can't be converted to or from LRS/GRS/RA-GRS, and a block blob account always needs a manual migration. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Availability SLAs: LRS, ZRS, GRS and GZRS give at least 99.9% read and write availability; RA-GRS and RA-GZRS give at least 99.99% read availability; cool, cold and archive access tiers drop the 99.9% figure to 99%. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Cost order, cheapest to most expensive: LRS, ZRS, GRS, RA-GRS, GZRS, RA-GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Adding zone redundancy has no one-time charge but raises ongoing storage cost; adding geo-redundancy incurs a one-time egress charge plus egress on every later write; removing geo-redundancy is free but deletes the secondary copy. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Dropping read access (RA-GRS to GRS or LRS) still bills the account as RA-GRS for an additional 30 days after conversion. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Failback after failover is done with PowerShell or Azure CLI version 2.30.0 or later. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))

## Compare and choose

- Outage coverage: a node failure is survived by every option; loss of an entire datacenter is survived by everything except LRS; a region-wide primary outage is survived only by GRS/RA-GRS/GZRS/RA-GZRS; readable secondary copies during a primary outage require RA-GRS or RA-GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Restoring writes after a primary region outage always requires an account failover, even with GRS or GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Pick LRS when the data can be rebuilt, when data governance forbids replication outside the region, or for unmanaged disks. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Pick ZRS for high availability inside the primary region, for Azure Files (no remount of file shares is needed when a zone goes down) and for Azure Data Lake Storage; Microsoft recommends ZRS plus geo-replication for high-availability apps. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Pick GRS for protection against regional disaster when the app doesn't need to read the secondary copy, and GZRS when it also needs zone resilience in the primary region. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Pick RA-GRS or RA-GZRS for business-critical apps that must keep reading through a primary endpoint outage; Microsoft recommends **RA-GZRS** for maximum availability and durability. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Failover choices: **customer-managed planned failover** (swap regions to test DR, no data loss, account becomes GRS and keeps geo-redundancy), **customer-managed unplanned failover** (primary endpoints down, some data loss, account becomes LRS and loses geo-redundancy, original primary copy is deleted), and **Microsoft-managed failover** (region scope, catastrophic events only, cannot be triggered per account). ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Failover support by account: planned and unplanned customer-managed failover work on v2, v1 and legacy blob accounts for GRS/RA-GRS and on v2 only for GZRS/RA-GZRS; Microsoft-managed failover covers all types for GRS/RA-GRS but only v2 for GZRS/RA-GZRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- If you can't fail over — because the account type or features don't support it — copy data instead with `AzCopy` or Azure PowerShell and repoint the application at the healthy account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))

## Gotchas

- An unplanned failover turns GZRS into LRS in the new primary, so re-enabling geo-redundancy re-replicates everything and costs egress again; archived blobs must be rehydrated first, at extra cost. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- You cannot convert a post-failover LRS account to ZRS or GZRS — use a manual migration to add zone redundancy. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Enabling geo-redundancy looks instantaneous, but failover cannot be started until initial synchronization between the two regions finishes. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- Some features are unsupported for customer-managed failover: object replication as source or destination, and change feed and point-in-time restore for planned failover. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Unplanned failover can lose data and create file-level inconsistencies with a hierarchical namespace, change feed, or point-in-time restore, which also resets the earliest restorable point to the failover completion time. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Use the **Last Sync Time** property to estimate data loss: anything written after it may not exist in the secondary, and for HNS accounts it covers metadata such as ACLs too. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- During failover the DNS entries for the storage endpoints are updated automatically and your data is inaccessible throughout that window. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- The resource provider doesn't fail over, so management operations must still run in the original primary region and the **Location** property keeps returning that original region afterwards. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Virtual machines don't fail over with the account — recreate them in the new primary; unmanaged disk leases block failover, so shut the VM down first, and any temporary-disk data is lost. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Never use failover as a migration strategy; migrate data instead. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Don't rely on Microsoft-managed failover for your DR plan, and don't fail over storage accounts used as Azure File Sync cloud endpoints. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- Storage accounts with premium block blobs can't be failed over, and premium block blob accounts don't support geo-redundancy at all. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-disaster-recovery-guidance))
- A manual migration can cause application downtime, so prefer a conversion for high-availability workloads; you must migrate manually when moving regions, using a block blob account, or avoiding rehydration of archived blobs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
- With ZRS, applications should retry transient faults with exponential back-off while Azure repoints DNS, and a temporary zone outage can otherwise surface as application errors. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy))
- Accounts using smart tier have extra dependencies for redundancy conversions and failover scenarios. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/redundancy-migration))
