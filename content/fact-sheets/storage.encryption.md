# Configure storage account encryption

## Key concepts

- Azure Storage encrypts data at rest automatically with service-side encryption (SSE) using 256-bit AES-GCM, and the implementation is FIPS 140-2 compliant; it is on for every storage account, cannot be disabled, and carries no extra charge. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- Coverage is total: block, append and page blobs (including the **archive** tier), Azure Files, queues, tables, disks and even object metadata, across standard and premium performance tiers, hot/cool access tiers, all redundancy options, and both primary and geo-replicated secondary regions. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- A new storage account is protected with Microsoft-managed keys by default, and Microsoft rotates them to meet its own compliance rules; if your organization must control and audit rotation, Microsoft recommends moving to customer-managed keys instead. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- Customer-managed keys (CMK) do not encrypt your data directly: Azure Storage uses the CMK to wrap the account encryption key, so only the protection of that key changes, data stays encrypted the whole time, and the new protection takes effect immediately with no extra action. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Encryption scopes move the key scope from the whole account (the default) down to a single container or one blob, letting you draw secure boundaries between data that shares one storage account but belongs to different customers. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Infrastructure encryption adds a second layer of 256-bit AES encryption underneath the service layer, so data is encrypted twice with two different algorithms and two different keys; this guards against one algorithm or key being compromised. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- The infrastructure layer always relies on Microsoft-managed keys and always uses a separate key from the service layer, while the service layer can use either Microsoft-managed or customer-managed keys from Key Vault. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))

## Settings and limits

- The key vault or Key Vault Managed HSM holding the key must have soft delete enabled and purge protection enabled, and the key must be an RSA or RSA-HSM key of size 2048, 3072 or 4096. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- The managed identity that the storage account uses must hold at least the `wrapkey`, `unwrapkey` and `get` permissions on the key. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- At account-creation time you must supply a user-assigned managed identity for CMK; on an existing account you may use either a user-assigned or the system-assigned managed identity. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- The key vault or managed HSM is allowed to sit in a different Microsoft Entra tenant, region and subscription than the storage account, and managed HSM exposes the same APIs and management interfaces as key vault. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- CMK applies automatically to Blob Storage and Azure Files only; Queue and Table storage data is not protected unless you opt those services in when the account is created. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Omit the key version to get automatic updates: Azure Storage then polls the vault or managed HSM once per day and adopts the latest version, so wait 24 hours before disabling the old version. If you specify a version, updating to the new version is your manual job. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Infrastructure encryption is set only at creation time, on the **Encryption** tab of the create-account experience, by picking **Enable infrastructure encryption** = **Enabled**; afterwards the account cannot be switched to it or away from it. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- Only newer account kinds qualify for that setting: general-purpose v2, premium block blob or premium page blob accounts; older account kinds don't support it. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- To confirm the setting, open the storage account and choose **Security + networking** > **Encryption**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- An account can hold up to 10,000 encryption scopes protected by customer-managed keys with automatic key-version updating; past that ceiling, any further CMK-protected scope must be updated manually. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Enabling an encryption scope bills a minimum of 30 days and then prorates hourly; disabling it inside 30 days still charges the full 30 days, so switch off scopes you no longer need. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- A container's default encryption scope must be chosen when the container is created, and you then pick whether blobs in it must use that scope or whether clients may override it with a different scope. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Client-side encryption version 2 uses AES-GCM and is available in the Blob SDKs for .NET 12.13.0+, Java 12.18.0+ and Python 12.13.0+, and the Queue SDKs for .NET 12.11.0+ and Python 12.4+; version 1 uses AES-CBC and is no longer recommended, and Table Storage supports only version 1. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))

## Compare and choose

- Microsoft-managed keys support all storage services, store the key in the Microsoft key store, leave rotation and key control with Microsoft, and scope the key to the account (default), container or blob — the right pick for most workloads. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- Customer-managed keys cover Blob Storage and Azure Files, live in Azure Key Vault or Key Vault Managed HSM, and put rotation and key control in your hands — choose them when you need your own key, your own RBAC on it, or auditable rotation. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- Customer-provided keys are sent per Blob Storage request from a key store you own, giving the finest control over how individual blob data is encrypted and decrypted, but they have no key scope in the storage account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- In all three options the encrypt and decrypt operations themselves are performed by Azure, not by you. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- You can switch a storage account between Microsoft-managed and customer-managed keys at any time, and you can also flip an individual encryption scope between the two key types at any time, even though different scopes in one account may use different key types. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Use encryption scopes when one account must serve several customers or teams and each needs a different key boundary; use plain account-level CMK when a single key for the whole account is acceptable. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Turn on infrastructure encryption only where compliance or assurance demands double encryption — Microsoft states that for most scenarios service-side encryption alone is already sufficient and the extra layer brings little benefit. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- If the account already has infrastructure encryption, every encryption scope created on it inherits it; otherwise you can enable it per scope at scope-creation time, and that per-scope setting is also immutable afterwards. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/infrastructure-encryption-enable))
- Prefer service-side encryption over client-side encryption; client-side encryption is only worth it when you must encrypt inside the client before upload, and Azure Storage recommends the service-side features instead. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
- Azure Policy has built-in definitions that require CMKs for Blob Storage and Azure Files, that require infrastructure encryption, and that require encryption scopes to use customer-managed keys. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))

## Gotchas

- Revoking access to a customer-managed key is done by disabling (or deleting) the key in the key vault; after that, data reads and writes fail with HTTP 403 (Forbidden) for every user — for Blob Storage this covers `List Blobs` with `include=metadata`, `Get Blob`, `Get Blob Properties`, `Get Blob Metadata`, `Set Blob Metadata`, `Snapshot Blob` with `x-ms-meta-name`, `Copy Blob`, `Copy Blob From URL`, `Set Blob Tier`, `Put Block`, `Append Block`, `Put Blob`, `Put Page` and `Incremental Copy Blob`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Azure Files is hit the same way when the key is revoked: `Create Permission`, `Get Permission`, `List Directories and Files`, `Create Directory`, directory and file property/metadata get and set, `Create File`, `Get File`, `Put Range`, `Copy File` and `Rename File` all fail. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- An encryption scope can never be deleted, only disabled; disabling makes later reads and writes on that scope fail with 403 until it is re-enabled, and you should disable a scope before revoking its key in the vault, otherwise you keep paying for it while the data is unreachable. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- If a container's default encryption scope prohibits overrides, uploading a blob with a different scope fails; with overrides permitted, both the default-scope and non-default-scope uploads succeed. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- You cannot set the access tier when uploading a new blob with an encryption scope, and you cannot move an existing encryption-scoped blob to the **archive** tier — although the archive tier itself is still covered by service-side encryption. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Azure Storage never rotates your key for you: create a new key version in the key vault or managed HSM yourself, then update the account. Rotating the key version causes no downtime and no performance hit, but the rotation action is not currently written to the Azure Monitor logs for Azure Storage. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Switching an account from manual to automatic key-version tracking may require explicitly setting the key version to an empty string first. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- CMK for managed disks is a separate mechanism from CMK for Azure Storage resources, so don't assume the storage-account procedure applies to disks. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/customer-managed-keys-overview))
- Encryption scope support can be affected if the account has Data Lake Storage Gen2, NFS 3.0 or SFTP enabled; check feature support in storage accounts before promising per-container or per-blob keys. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/encryption-scope-overview))
- Client-side encryption version 1's CBC implementation has a known vulnerability, so migrate existing data by downloading it, decrypting it, and re-encrypting with version 2; Table Storage has no version 2 path at all. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-service-encryption))
