# Create and configure virtual network peering

## Key concepts

- Virtual network peering links two VNets so they act as one for connectivity; traffic rides Microsoft's private backbone, so no public internet route, gateway or extra encryption is needed for the link ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Two types: **Virtual network peering** (same region) and **Global virtual network peering** (different regions) ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Peering is configured once per side: the first side shows **Initiated**, and the link works only when both sides show **Connected** ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Peerings are not transitive: A↔B plus B↔C gives no A↔C path, so add an explicit A↔C peering or route via an NVA in the hub ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- The two VNets can be in the same or different subscriptions, resource groups and Microsoft Entra tenants, and an ARM VNet can be peered to a classic-deployment VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Peered VNets must have non-overlapping IP address spaces ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Creating a peering causes no downtime for resources in either VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Same-region peering latency equals same-VNet latency; throughput follows the VM size's bandwidth cap with no extra peering limit ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Service chaining works via user-defined routes whose next hop is a VM in a peer VNet or a VPN gateway, but never an ExpressRoute gateway next hop ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Gateway transit lets a spoke use a VPN or ExpressRoute gateway in the peer (hub) VNet; with mixed deployment models the gateway must be in the ARM VNet, and a VNet may hold only one gateway ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- **Subnet peering** is an extra option on top of normal peering that peers only a chosen list of subnets, while normal peering peers the whole address space ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Azure Virtual Network Manager connectivity configurations scale beyond peering: up to 1,000 spokes on one hub, or a mesh of up to 3,000 VNets ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- A nominal charge applies to ingress and egress traffic over the peering; with gateway transit the spoke also pays peering charges for traffic to the peer's gateway ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).

## Settings and limits

- Create path: **Virtual networks** → pick the VNet → **Peerings** under **Settings** → **+ Add** ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Peering link name** (given for both the remote and local views) names the peering from that VNet's side and must be unique in that VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Virtual network deployment model** selects which model the remote VNet was deployed with ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **I know my resource ID** stays unchecked when you have read access to the remote VNet; check it and fill **Resource ID** when you lack read access to that VNet or subscription ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Resource ID** must point to an existing VNet in the same or a supported different region: `/subscriptions/<Id>/resourceGroups/<resource-group-name>/providers/Microsoft.Network/virtualNetworks/<virtual-network-name>` ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Subscription** and **Virtual network** pick the remote VNet; for a different Microsoft Entra tenant, add a guest user from each tenant as administrator in the other ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Allow the peered virtual network to access 'vnet-1'** is on by default; it lets peer VMs reach vnet-1 and extends the **VirtualNetwork** service tag to the peer in network security groups ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Allow 'vnet-1' to access the peered virtual network** is on by default and serves the opposite direction for hub-and-spoke traffic ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Allow the peered virtual network to receive forwarded traffic from 'vnet-1'** (remote view) and **Allow 'vnet-1' to receive forwarded traffic from the peered virtual network** (local view) are off by default; they let traffic forwarded by a third VNet's NVA cross the peering but create no routes or NVAs themselves ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Allow gateway or route server in the peered virtual network to forward traffic to 'vnet-1'** and **Allow gateway or route server in 'vnet-1' to forward traffic to the peered virtual network** are off by default; each needs that side of the pair to actually host a gateway or route server ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Enable the peered virtual network to use 'vnet-1's' remote gateway or route server** is off by default; it needs the local side to have a remote gateway or route server and to allow its gateway forwarding, and only one of the two peerings may use it ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- **Enable 'vnet-1' to use the peered virtual networks' remote gateway or route server** is off by default, needs the same conditions on the peer side, and is unusable if vnet-1 already owns a gateway ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- After **Add**, status shows **Updating** and becomes **Connected** once you press **Refresh** ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Edit path: **Virtual networks** → **Peerings** → pick the peering → change → **Save**. Delete path: select the peering → **Delete** → type **delete** in the box → **Delete** → confirm in **Delete confirmation**; deleting one side also deletes the remote peering ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Required role: **Network Contributor**, or a custom role with `Microsoft.Network/virtualNetworks/virtualNetworkPeerings/write`, `/read` and `/delete`; removing the remote peering needs read and delete on the remote VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Across subscriptions or resource groups, PowerShell and CLI need the full resource URI of the remote VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Global peering can span public, China and Government cloud regions, but never different clouds (for example public cloud with 21Vianet) ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- A VNet cannot be moved to another resource group or subscription while peered: delete the peering, move the VNet, then recreate the peering ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Peerings cannot be created inside a `PUT` virtual network operation ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- A peered VNet's address space can be resized (edit a prefix such as `10.1.0.0/16` to `10.1.0.0/18`, add or delete ranges) with no downtime to the already peered space, for IPv4 and IPv6, cross-tenant; peers must then sync, recommended after every resize ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- `summarizedGatewayPrefixes` on the hub makes VPN and ExpressRoute gateways advertise summarized prefixes instead of hub plus spoke address spaces; it affects only VNets with a gateway subnet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Route table property `disablePeeringRoute` (preview) takes `None` (default, Azure adds system peering routes) or `All` (suppresses IPv4 and IPv6 system peering routes for supported workloads on subnets using that route table) ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- The cap on peerings per VNet is an Azure networking quota listed under the Azure Resource Manager virtual networking limits ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).

## Compare and choose

- Same region vs cross-region: use **Virtual network peering** within a region and **Global virtual network peering** across regions, remembering basic load balancer front-end IPs are unreachable over global peering while standard load balancers work in both ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Normal peering vs **Subnet peering**: normal peering connects whole address spaces; subnet peering limits exposure to named subnets ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Peering vs a VPN or ExpressRoute gateway link: peering is the low-latency backbone path for Azure-to-Azure traffic, and when both exist the traffic uses the peering, not the gateway ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Local gateway vs remote gateway: a local gateway serves the VNet's own on-premises link; gateway transit is for spokes that have no gateway while the hub hosts it ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Peering vs Azure Virtual Network Manager connectivity configurations: peering for a few links; VNM configs for hub-and-spoke up to 1,000 spokes or meshes up to 3,000 VNets ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Per-spoke UDR overrides vs `disablePeeringRoute: All`: suppression replaces one override per spoke with a summarized UDR, because longest-prefix match otherwise picks a more specific system peering route and skips the NVA ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Disable vs delete: for intermittent connectivity, deselect **Allow traffic to remote virtual network** instead of removing the peering ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Default Azure DNS vs **Azure Private DNS** or a custom DNS server: peerings never resolve names across VNets, so cross-VNet resolution needs one of those ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Terraform: use the AzAPI provider for `disablePeeringRoute`; the AzureRM provider does not support it ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Preview limits: the NVA next hop must sit in the same VNet as the workload's NIC, a next hop placed inside a peer VNet is unsupported, and the setting is managed on the route table rather than VNM routing rule collections ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Peering route suppression does not apply to Azure BareMetal Infrastructure workloads in the subnet; they keep normal longest-prefix-match routing while other workloads there use the summarized routes ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).

## Gotchas

- A peering stays **Initiated** until both sides are created; a one-sided peering carries no traffic ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- The forwarded-traffic and gateway-forwarding options only permit traffic to flow; they never create user-defined routes or network virtual appliances, which are configured separately ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- The remote gateway option depends on the other side enabling its gateway-forwarding option, and only one of the two peerings may use a remote gateway ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- A VNet cannot both own a gateway and use a peer's remote gateway, because only one gateway per VNet is allowed ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Point-to-Site VPN clients must be downloaded again after the peering succeeds so they pick up the new routes ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Application Gateways without **Network Isolation** enabled block traffic between peered VNets when **Allow traffic to remote virtual network** is off ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Global peering cannot reach a basic load balancer's front-end IP (internal or public), and services built on basic load balancers fail across global peering ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- Network security groups still apply between peers: full connectivity is the default, and NSG rules in either VNet can block specific access to the other VNet or its subnets ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- After resizing a peered VNet's address space, peers must be synced, and the feature is unsupported when the VNet is peered with a classic VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- `disablePeeringRoute` only suppresses peering routes; it builds no replacement route or inspection path, so the UDRs and a usable next hop must already exist ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)).
- For on-premises transit via VPN gateway, the on-premises device's interesting traffic must list every Azure VNet CIDR (hub, spokes, Point-to-Site pools), and Phase 2 security associations must supply one tunnel per Azure VNet subnet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- When a pair of VNets is joined by both peering and a gateway, the peering always carries the traffic, so remove the peering to force the gateway path ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
- Deleting a peering on one VNet also removes the matching peering on the remote VNet ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering)).
