# Configure Azure DNS

## Key concepts

- DNS turns a service name into an IP address; Azure DNS delivers hosting, resolution, and load balancing for applications on Microsoft's Azure infrastructure. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-overview))
- The Azure DNS portfolio covers five services: **Azure Public DNS** (hosting for internet-facing domains), **Azure Private DNS** (resolution inside virtual networks), **Azure DNS Private Resolver** (query private zones from on-premises and vice versa without VM-based DNS servers), **Azure Traffic Manager** (DNS-based traffic load balancer for public-facing apps across global Azure regions), and **DNS Resolver Policy** (filters and logs DNS queries at the virtual network level, with a Threat Intelligence feed from MSRC to block known malicious domains). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-overview))
- Azure DNS is one of the **Network Foundations** services, alongside **Azure Virtual Networks** and **Azure Private Link**. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-overview))
- DNS is hierarchical: the root domain is `.`, then top-level domains (`com`, `net`, `org`, `uk`, `jp`), then second-level domains (`org.uk`, `co.jp`); a domain name registrar sells names such as `contoso.com` and gives you control of the hierarchy beneath it. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Azure DNS cannot sell domain names: buy through **App Service domains** or a non-Microsoft registrar, then host the zone in Azure DNS for record management. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Create the zone first, then add each record inside it — for example a zone `contoso.com` holding `www.contoso.com` and `mail.contoso.com`. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Records are addressed by relative name plus type: relative `www` in zone `contoso.com` means FQDN `www.contoso.com`; a record at the zone root is the apex (naked) record, written `\@`. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- A record set (resource record set) groups all records in a zone that share a name and type; to serve a second IP for `www`, add the record to the existing record set instead of creating another set. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Supported record types are A, AAAA, CAA, CNAME, MX, NS, PTR, SOA, SRV, and TXT; SPF is represented with TXT, and DS/TLSA become available once the zone is signed with DNSSEC (DNSKEY, RRSIG, NSEC3 are then added automatically). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Hosted zones run on a globally distributed, highly available name server fleet, managed with the same credentials, APIs, tools, and billing as other Azure services. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))

## Settings and limits

- The **Create DNS zone** portal page has a **Basics** tab with **Project details** (**Subscription**, **Resource group** or **Create new**) and **Instance details** (**Name**, **Resource group location**, and the checkbox **This zone is a child of an existing zone already hosted in Azure DNS**). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- The **Resource group location** you pick does not affect where the service runs — the DNS zone service is global and not bound to a location. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- Each new zone is handed four name servers from a shared Azure pool, for example `ns1-37.azure-dns.com`, `ns2-37.azure-dns.net`, `ns3-37.azure-dns.org`, `ns4-37.azure-dns.info`; read them from the zone's **Overview** page and Azure writes the authoritative NS records into the zone for you. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- A zone name must be unique within its resource group and the zone must not already exist, otherwise creation fails; the same name can be reused in another resource group or subscription, but each instance gets different name server addresses and only one set can be configured at the registrar. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Public DNS quotas: 250 public DNS zones per subscription, 10,000 record sets per public zone, 20 records per record set, 400 TXT records per record set, and 50 alias records for a single Azure resource. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- The 250-zone, 10,000-record-set, 20-records-per-set, and 50-alias limits can be raised by contacting Azure Support; the 400 TXT record limit is not marked as adjustable. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- TTL is configured on the record set, not on each record, so all records in the set share it; allowed values run from 1 to 2,147,483,647 seconds (the docs' example uses 3,600 seconds, i.e. 1 hour). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Wildcard record sets work for every record type except NS and SOA: name the set `*`, or use `*` as the left-most label such as `*.foo`; it answers matching queries unless a closer non-wildcard set exists. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- TXT records: each string is at most 255 characters; in the portal, PowerShell, and CLI you supply one string and Azure splits it into 255-character segments, while the REST API requires each string separately, and one TXT record set may hold 4,096 characters in total across all its records. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- A CAA record has three properties: **Flags** (integer 0–255 carrying the critical flag from RFC 6844), **Tag** (`issue` for any certificate, `issuewild` for wildcard certificates only, `iodef` for the CA notification address), and **Value** (the value for the chosen tag). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- A NAPTR record takes **Order** (0–65,535, evaluated ascending), **Preference** (0–65,535, lower preferred among equal Order), **Flags**, **Service** (common values `E2U+sip` and `E2U+mailto`), **Regexp** (POSIX extended regular expression), and **Replacement** (the next FQDN in the chain, used when **Regexp** is empty). ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- An SRV record set name must carry the service and protocol with leading underscores, for example `_sip._tcp.name`; at the zone apex use `_sip._tcp` without `\@`, and **Priority**, **Weight**, **Port**, **Target** are set per record. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- To resolve a private zone from a virtual network you must link that VNet to the zone; linked VNets have full access and can resolve every record published in the private zone. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- **Autoregistration** is turned on for a virtual network link; Azure then registers that VNet's VMs as A records pointing to their private IPs and updates or removes the record whenever a VM is created, changes IP address, or is deleted. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Private zone data is stored as a global resource, so a zone is not dependent on a single VNet or region — the same private zone can be linked to VNets in different regions and stays available if service is interrupted in one VNet. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Azure Resource Manager **Tags** are supported on DNS zone resources but not on record sets; record set **metadata** is the alternative, and unlike tags it cannot filter your Azure bill or be enforced by an ARM policy. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Every DNS resource (zone or record set) carries an Etag that is returned on retrieval; send it back on update and Azure DNS verifies it, so a mismatch signals a concurrent change by someone else. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- REST API Etag headers behave as follows: no header means `PUT` always succeeds; `If-match <etag>` succeeds only if the resource exists and the Etag matches; `If-match *` succeeds only if the resource exists; `If-none-match *` succeeds only if the resource doesn't exist. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Azure DNS PowerShell blocks concurrent changes with Etag checks by default, and the optional `-Overwrite` switch suppresses those checks so concurrent edits are overwritten. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))

## Compare and choose

- Use **Azure Public DNS** when names must resolve for anyone on the internet; use **Azure Private DNS** for names that should resolve only inside virtual networks and connected VNets. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- For split-horizon DNS, create a public and a private zone with the same name so the same query answers differently inside and outside the VNet — the classic pattern for an internal-only version of a service. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Pick private zones over Azure-provided hostnames when you need one name shared by several VNets, which simplifies cross-network and service discovery such as VNet peering; forward resolution between linked VNets works without explicit peering, though you may still peer for traffic reasons. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Cardinality differs: many VNets may link to one private zone, but a VNet can link to only one private zone when autoregistration is enabled. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Reverse lookup in private DNS returns an FQDN made of the host/record name plus the zone name suffix; by default a linked VNet's private IP also returns `internal.cloudapp.net`, and with autoregistration enabled you get both FQDNs. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Conditional forwarding, such as resolving names between Azure and on-premises networks, is done with **Azure DNS Private Resolver** rather than with plain private zones. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Use **Azure Traffic Manager** when you need DNS-based load balancing of public-facing applications across global Azure regions, and use **DNS Resolver Policy** when you need to filter and log DNS queries at the VNet level or block known malicious domains from the Threat Intelligence feed. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-overview))
- For SPF, use a TXT record: RFC 7208 deprecated the SPF record type, and Azure DNS does not support the obsolete type. TXT also carries DKIM and other arbitrary text. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Private DNS supports A, AAAA, CNAME, MX, PTR, SOA, SRV, and TXT, and the feature is available in all Azure regions of the public cloud. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))

## Gotchas

- You can create a zone for a domain you don't own, but Azure's name servers can only become authoritative at the registrar once you own it and can set its NS records. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- A CNAME record set cannot coexist with any other record set of the same name, and you cannot create a CNAME at the apex because the apex already holds the NS and SOA sets; these are DNS standard constraints, not Azure limitations. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- The apex NS record set is created automatically with the zone and deleted automatically with the zone; it cannot be deleted on its own, and the pre-populated Azure name servers inside it cannot be removed or edited — other NS record sets, used to delegate child zones, have no such restriction. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- The apex SOA record set is also created and deleted automatically with the zone and can't be created or deleted separately; all of its properties are editable except the `host` value, which Azure preconfigures to the primary name server name. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- The SOA serial number is not refreshed automatically when you change records in the zone, so update it by editing the SOA record if you need it to change. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Azure DNS rejects a dot before the `\@` in the SOA hostmaster mailbox: both `john.smith@contoso.xyz` (interpreted as `john.smith.contoso.xyz`) and `john\.smith@contoso.xyz` are refused. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- SOA and CNAME record sets can hold only a single record each, because DNS standards forbid multiple records with the same name for those types. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- DNSSEC-managed types (DNSKEY, RRSIG, NSEC3) appear automatically when a zone is signed and cannot be created or modified afterwards; creating DS or TLSA records first requires the zone to be signed with DNSSEC. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-zones-records))
- Avoid `.local` for private DNS zone names, because not all operating systems support that suffix. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- Reverse DNS works only for the private IP space of the linked virtual network. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- During a regional failure, private DNS zones still support CRUD operations through API calls using the SDKs provided with the product. ([Learn](https://learn.microsoft.com/en-us/azure/dns/private-dns-overview))
- When delegating, use all four Azure name servers regardless of your domain name, and don't worry that the name servers' top-level domains differ from your own domain's. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- Copy each name server address with its trailing dot, which marks the end of a fully qualified domain name and is needed for RFC compliance; some registrars append the dot for you, so check with them. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- Vanity name servers — delegating a domain to name servers hosted inside your own zone — are not currently supported in Azure DNS. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- Delegation is not instant: allow at least 10 minutes after updating the registrar, then verify with `nslookup -type=SOA contoso.xyz`. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- A healthy SOA answer shows `responsible mail addr = azuredns-hostmaster.microsoft.com`, `serial = 1`, `refresh = 3600`, `retry = 300`, `expire = 604800`, `default TTL = 300`. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- You don't have to configure the Azure name servers on your own resolver to test delegation — if delegation is correct, normal DNS resolution finds them automatically. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
- Hosting a domain is a four-step flow: create the zone, create records, retrieve the Azure name servers, delegate at the registrar. ([Learn](https://learn.microsoft.com/en-us/azure/dns/dns-delegate-domain-azure-dns))
