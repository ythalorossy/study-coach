# Deploy virtual machines to availability zones and availability sets

## Key concepts
- An **Availability Zone** is a physically separate area inside an Azure region, with independent power, network, and cooling. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))
- A zone contains one or more physically separate datacenters. Zones are normally several kilometers apart and usually within **100 kilometers** of one another. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Placing replicas in different zones lets them survive a zone outage and smaller faults such as a rack or cluster failure. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- **Zone-redundant** resources are replicated or distributed across zones by the service. Microsoft manages request spreading, data replication, and automatic failover. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- **Zonal** resources sit in one zone you select and are isolated from faults elsewhere, but they do not automatically survive their own zone's outage. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- A deployment is **zone-resilient** when it is zone-redundant or when separate instances of a zonal resource occupy at least **2 zones**. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- A **nonzonal** or **regional** deployment has no user-selected zone. Azure may place it in any zone, so a zone outage can interrupt it. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Distinguish the zones offered by a region, the zones a service actually uses, and the instances or replicas deployed; these counts need not match because a service may use only a subset of zones. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- **Physical zones** are the datacenters; each maps to a subscription-specific **logical zone**, and different subscriptions can number the same physical zone differently. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Azure aims to apply service updates one zone at a time per region. Only workloads already spread across several zones benefit from this sequencing. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- An **availability set** is a logical VM grouping that reduces correlated failures. Use at least **2 VMs** to meet the **99.95%** Azure SLA; the set itself has no extra charge. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Azure assigns each availability-set member a **fault domain** and an **update domain**, arranging shared infrastructure to limit simultaneous failures. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- **Virtual Machine Scale Sets** with **flexible orchestration mode** are recommended for high availability with the widest feature range; they centralize management, updates, configuration, and automatic scaling. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Scale-set instances can run across multiple zones, in one zone, or regionally; the available zone-placement choices can differ by orchestration mode. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))

## Settings and limits
- An availability set permits at most **3 fault domains** and **20 update domains**. Both counts are fixed when the set is created. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- A **fault domain** groups VMs that share a power source and network switch. By default, availability-set members are distributed over up to **3 fault domains**. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- An **update domain** groups VMs and hardware that can restart together. Maintenance restarts only one domain at a time, in an order that need not be sequential; that domain has **30 minutes** to recover before another is restarted. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- With **5 update domains**, the sixth VM shares the first VM's domain, the seventh shares the second, and placement continues cyclically. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- A **managed availability set** accepts only VMs with **managed disks**. The managed disks attached to each VM follow that VM's fault-domain placement. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Managed-disk fault-domain capacity is region-dependent: each region offers either **2** or **3**. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Check a region's maximum with ``az vm list-skus --resource-type availabilitySets --query '[?name==`Aligned`].{Location:locationInfo[0].location, MaximumFaultDomainCount:capabilities[0].value}' -o Table``. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- The VM availability guidance describes **3 Availability Zones per supported region**. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))
- The detailed zone table gives **East US 2** four zones and **West US 2** three, so the common pattern has exceptions. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Regions listed with **3 zones** are **Australia East**, **Austria East**, **Belgium Central**, **Brazil South**, **Canada Central**, **Central India**, **Central US**, **Chile Central**, **Denmark East**, **East Asia**, **East US**, **France Central**, **Germany West Central**, **India South Central**, **Indonesia Central**, **Israel Central**, **Italy North**, **Japan East**, **Japan West**, **Korea Central**, **Malaysia West**, **Mexico Central**, **New Zealand North**, **North Central US**, **North Europe**, **Norway East**, **Poland Central**, **Qatar Central**, **South Africa North**, **South Central US**, **Southeast Asia**, **Spain Central**, **Sweden Central**, **Switzerland North**, **Taiwan North**, **UAE North**, **UK South**, **West Europe**, and **West US 3**. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Use `az account list-locations` or `Invoke-AzRestMethod` to read the current subscription's logical-to-physical zone mappings. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- The **List Locations API** returns mappings for one subscription, while the **Check Zone Peers API** compares mappings across multiple subscriptions. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- The **Check Zone Peers API** requires the subscription feature `Microsoft.Resources/AvailabilityZonePeering` to be enabled. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Microsoft's inter-zone network-link target is roughly **2 milliseconds round-trip**. Most multi-zone workloads see no obvious performance penalty, but protocol behavior and hop count change observed latency; test latency-sensitive designs with the real topology. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Moving data among zones inside one Azure region incurs no Azure transfer fee; this applies to traffic over both private and public IP addresses. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- A **Standard**-tier VM includes Azure Load Balancer, while some other tiers do not. The load balancer distributes traffic among VMs. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))
- A scale set has no separate resource charge; you pay for each VM instance created. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))

## Compare and choose
- Availability zones deliver the strongest reliability of the options described. Availability sets provide high availability but less resiliency because some shared infrastructure failures can cross their fault domains. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- In a zone-supported region, spread VMs across multiple availability zones when the priority is protection from an individual datacenter or zone failure. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- In a region without availability zones, use an availability set to obtain fault-domain separation. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Choose an availability set when low VM-to-VM latency outweighs zone isolation; its VMs have closer physical proximity than VMs in separate zones. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- An availability set limits physical-hardware, power, and network faults, but it does not prevent operating-system or application failures. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- For strict latency or performance, deliberately place several VMs in one **zonal** deployment; add resources in other zones and your own failover if you also need zone resilience. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Production workloads should use multiple availability zones when the chosen region supports them. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Mission-critical workloads should consider both multiple zones and multiple regions. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- If data residency or sovereignty limits the design to one region, use multi-zone redundancy plus backup and restore procedures such as **Azure Backup**, and define recovery objectives. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Availability zones do not protect against a full regional outage. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- **Azure Site Recovery** can replicate Azure VMs, on-premises VMs, Azure Stack VMs, and physical servers to a secondary location, then support failover and failback. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))
- Confirm that the service supports zones in the selected region and that its tier or SKU qualifies; some services also require explicit zone configuration. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Azure Storage keeps multiple copies of data. Its redundancy choices trade cost against availability through in-region replication, geographic replication, and secondary-region read access. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))

## Gotchas
- Do not assume that **logical zone 1** means the same physical datacenter across subscriptions; the mapping is assigned to each subscription when it is created. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- When Azure adds a zone to an existing region, current subscriptions keep their mappings and the new zone uses the same logical and physical number there; a subscription created later can map it differently. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- Regional resources might not even have a zone placement, and Azure provides no physical- or logical-zone visibility for them; a zone failure can therefore take down a regional VM. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability))
- Avoid stopping or deallocating the first VM before deploying the second member of an availability set. That sequence can make the second VM's OS disk share the first VM's fault domain; inspect the **Fault Domain** column to check. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Separate fault domains can still lose a datacenter-level network outage, so an availability set does not isolate every shared-infrastructure event. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
- Two or more instances are not enough for zone resilience if they all run in one zone. Spread them over at least **2 zones** or use a zone-redundant service configuration. ([Learn](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview))
- An availability set arranges infrastructure fault and update domains; it does not replace application-level redundancy. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-machines/availability-set-overview))
