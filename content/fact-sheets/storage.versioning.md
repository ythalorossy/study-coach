# Configure blob versioning

## Key concepts
- Blob versioning is an account-level data protection setting that automatically saves a prior copy of a blob every time it is written to or deleted, with no application code required ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- A blob can have one current version (its live state) and any number of previous versions; deleting the current version leaves previous versions in place rather than freeing the storage ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Every version is identified by a version ID whose value is the UTC timestamp when that version was written; the ID is returned in the `x-ms-version-id` response header and is fixed for the lifetime of the version ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Previous versions are immutable, so their content and metadata cannot be modified after creation ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- A blob that existed before versioning was enabled has no version ID; the first write after enabling assigns it a version ID equal to its creation time, and the prior state becomes a previous version ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).

## Settings and limits
- Versioning is switched on per storage account and is offered for the general-purpose v2, premium block blob, and legacy Blob account types; an account with a hierarchical namespace enabled for Data Lake Storage is excluded ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- The feature needs Azure Storage REST API version 2019-10-10 or later and is not available for blobs uploaded through Data Lake Storage APIs ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- In the Azure portal, you turn versioning on under **Data management** > **Data protection** by selecting **Enable versioning for blobs** in the **Tracking** section, where you can choose to keep all versions or delete them after a period ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-enable)).
- Setting the **Delete versions after** portal option automatically adds a rule to the storage account's lifecycle management policy; after that, the **Delete versions after** control disappears from the **Data protection** page until the rule is removed ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-enable)).
- For block blobs, the writes that create a new version are `Put Blob`, `Put Block List`, `Copy Blob`, and `Set Blob Metadata`; the `Put Block` call alone does not create a version because the version is captured on `Put Block List` ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- For page blobs and append blobs, only `Put Blob`, `Put Block List`, `Copy Blob`, and `Set Blob Metadata` create versions; `Put Page` (page blob) and `Append Block` (append blob) do not, so a manual snapshot is needed to capture those states ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Microsoft recommends keeping fewer than 1,000 versions per blob to avoid degrading blob listing latency ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- All versions of one blob must be the same blob type; you cannot overwrite a block blob with a page blob (or any other type) while any previous version exists unless you first delete the blob and every version ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Any version, including the current one, can be moved between hot, cool, cold, and archive tiers by calling `Set Blob Tier` with the version ID ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- A service or user delegation SAS that targets a specific version uses the signed resource value `bv`, and the Delete permission with URI symbol `x` is required to delete a version ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Deleting a previous version requires the Azure RBAC data action `Microsoft.Storage/storageAccounts/blobServices/containers/blobs/deleteBlobVersion/action`, which is included in the built-in **Storage Blob Data Owner** role; **Storage Blob Data Contributor** can delete only the current version ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- To see versions in the portal, open the container, select the blob, choose the **Versions** tab, and toggle **Show deleted versions** to include soft-deleted versions still inside the retention window ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-enable)).

## Compare and choose
- A blob version is system-managed and is created automatically on every write or delete, while a snapshot is application-managed and taken manually; pick versioning for continuous, automatic protection and snapshots for deliberate checkpoints ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Microsoft recommends stopping block blob snapshots after versioning is enabled because versions already capture every update and delete, and additional snapshots only add cost ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Taking a snapshot of a versioned blob creates a new version at the same time as the snapshot and a new current version, so the snapshot and that version hold identical data ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- When both versioning and soft delete are on, overwriting a blob leaves a previous version that is not soft-deleted and must be removed explicitly; no soft-deleted snapshot is produced ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Deleting a blob while both features are on makes the current version a previous version and does not create a soft-deleted entry for the blob; the soft delete retention period does not apply to that deletion ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Deleting a specific previous version under soft delete soft-deletes that version, and it is permanently removed only after the soft delete retention period expires ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- `Undelete Blob` restores every soft-deleted version of a blob in one call and never promotes any version to current; to make an old version current, first undelete and then call `Copy Blob` to copy the chosen version over the current one ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Object replication depends on blob versioning, so all object replication policies on the account must be removed before you can disable versioning ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Versions are billed like snapshots; if no tier is explicitly set, you are billed for unique blocks or pages across all versions, so re-committing a block with the same ID and data still adds a billable block ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Once a tier is explicitly set on a version, you are billed for the full content length of that version and you cannot undo the tier choice, even if you later move the object back to its original tier ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Moving a version to the archive tier bills the full content length of every version and snapshot in the account, not only the one being moved ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- For automatic cleanup, both a lifecycle management policy and an Azure Storage Actions task can delete previous versions; lifecycle management uses the day-based `daysAfterCreationGreaterThan` property, while Storage Actions can key on when a version became noncurrent for finer control ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).

## Gotchas
- Enabling versioning changes the meaning of delete: deleting a blob no longer frees space, because the data persists as a previous version and continues to be billed ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Disabling versioning does not delete existing versions, snapshots, or blobs; afterward you can still read, list, and delete existing versions, but new writes to a blob produce a non-versioned blob that overwrites the current state on future updates ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Versioning does not protect against deletion of a storage account or a container; use an Azure Resource Manager lock for the account and container soft delete for containers ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- An Immutability (WORM) policy on a container or the account can prevent versioning from being disabled ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- The `Put Blob` operation replaces the entire content of a blob and therefore tends to create the most new unique blocks and the highest version-related charges; use `Put Block` and then `Put Block List` to update only the changed blocks ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Lifecycle management version-age rules count from the version's original creation time, not from when it became a previous version, so a long-lived blob that is finally overwritten can be deleted almost immediately by a small `daysAfterCreationGreaterThan` value ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Enabling versioning on an account with frequently overwritten data, or one that is backed up from a cool or cold tier, can substantially raise storage capacity charges and may trigger data retrieval charges for the stored versions ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- Storing frequently overwritten data in a separate account with versioning disabled is the recommended way to control costs when only some workloads need version history ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview)).
- After you choose **Delete versions after** in the portal, that control disappears from the **Data protection** page and only returns if you delete the corresponding lifecycle management rule (and any other rules that delete versions) from the policy ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-enable)).
