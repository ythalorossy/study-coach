# Configure scaling for an App Service plan

## Key concepts

- App Service scaling has two directions: **scale up** (bigger capacity per instance — more CPU, memory, disk) and **scale out** (more VM instances running the same app). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Scale up is done by changing the **pricing tier** of the App Service plan that hosts the app; it is also what unlocks capabilities such as dedicated VMs, custom domains and certificates, staging slots and autoscaling. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Scale out adds instances, and the ceiling depends on tier: 3 instances on Basic, 10 on Standard, 30 on Premium, and 100 in App Service Environments on the Isolated tier. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- A scale change applies within seconds, affects **all apps in that App Service plan**, and requires no code change and no redeploy. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Back-end dependencies such as Azure SQL Database or Storage are scaled separately and are not managed by the App Service plan. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- App Service also offers **automatic scaling**, a scale-out option driven by incoming HTTP traffic that is configured **per app**, and it is a different feature from Azure Monitor **autoscale** (metric and schedule rules). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Automatic scaling is available for all app types — Windows and Linux, deployed as code or as containers — but it is **not supported for deployment slot traffic**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Only **one** scaling method should be active for an App Service plan at a time (manual, autoscale or automatic scaling). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Azure Monitor autoscale applies its metric and schedule rules to the **entire App Service plan**, so every app in the plan scales together; automatic scaling instead lets apps inside one plan scale independently of each other. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Use automatic scaling when you want App Service to react to HTTP traffic without writing rules or schedules; use autoscale when you need CPU-, memory-, queue-length-, custom-metric- or time-based rules and schedules. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Automatic scaling fits apps whose back end (for example a database) cannot scale as fast, because you can cap how far the plan scales out. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))

## Settings and limits

- Scale-up path in the portal: app page → left pane → **App Service plan** → **Scale up** → choose a pricing tier → **Select**; a green success check mark confirms completion. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- To move a plan off the Free tier you must first remove the spending limit on the subscription in **Cost Management + Billing**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Automatic-scaling path in the portal: web app left menu → **Settings** → **Scale-out (App Service plan)** → select **Automatic**, set **Maximum burst**, select **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **Maximum burst** is the highest instance count the plan may reach from incoming HTTP requests; on Premium v2, v3 and v4 you can specify up to **30**, and the value must be equal to or greater than the plan's worker/instance count. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **Always ready instances** is a per-app setting that fixes the minimum instance count; extra instances are added above it only up to the plan's **Maximum burst**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **Maximum scale limit** caps how far a single web app scales out; turn it on with the **Enforce scale-out limit** option and give it a value between 1 and the plan's maximum burst. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **Prewarmed instances** provide a warm buffer during HTTP scale and activation events, keep buffering until the app's maximum scale-out limit is reached (nothing is prewarmed beyond that limit); the default is **1** and it should normally stay at 1. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- The prewarmed instance count **cannot be changed in the portal** — you must change it with the Azure CLI. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Turn automatic scaling off from **Scale-out (App Service plan)** by selecting **Manual** and choosing **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Automatic scaling covers **App Service web apps only**; for Azure Functions the recommendation is the Azure Functions Premium plan, and automatic scaling is disabled whenever a plan mixes web apps and Functions apps. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **ARR affinity** (Application Request Routing cookies) pins requests to specific instances and therefore restricts scaling; when you enable **Automatic Scaling** on a plan, ARR affinity is automatically disabled for all pre-existing apps in that plan. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- To disable ARR affinity yourself: app → **Settings** → **Configuration** → **General settings** tab → **Session affinity** → **Off** → **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- **Health Check** can be enabled alongside automatic scaling — you do not have to disable it. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- The `AutomaticScalingInstanceCount` metric reports the VMs an app runs on (including the prewarmed instance if deployed) and exists only for apps with **Automatic Scaling** enabled. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Autoscale prerequisites: an App Service plan on **Standard tier or higher** with at least one app, plus the **Owner** or **Contributor** role, or a custom role with `Microsoft.Insights/autoscaleSettings/*` permissions, on the plan. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Autoscale discovery path: **Monitor** → **Settings** → **Autoscale**, where filters by subscription, resource group or resource type show each resource's instance count and a status of **Not configured**, **Enabled** or **Disabled**; from a plan you can also use **Settings** → **Scale out (App Service plan)**. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- The first rule generated by **Custom autoscale** → **Scale based on a metric** → **Add a rule** defaults to adding one instance when the **CPU Percentage** metric stays above **70 percent** over **10 minutes**. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Best practice is to add a scale-in rule too: Operator **Less than**, metric threshold **20**, Operation **Decrease count by**. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Under **Instance limits** you set **Maximum** (the default instance count/minimum is 1); without raising the maximum the plan stays at a single instance no matter what the rules say. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Scale conditions: **Add a scale condition** → **Scale to a specific instance count** with **Repeat specific days** plus a **Start time** and **End time**; outside that window the default scale condition applies. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- For unusual dates use **Specify start/end dates**; that condition can carry its own metric rules, its own maximum (for example 10) and its own default instance count (for example 3). ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- The **Run history** tab lists past scale events (the activity log records every scaling event) and the **JSON** tab exposes the autoscale setting as an ARM resource you can edit directly and save. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Each rule has its own cool-down period (default **5 minutes**); after a scale action a rule cannot trigger again until its cool-down elapses, while a rule with a shorter cool-down may become eligible sooner. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- To stop autoscale, choose **Manual scale**, set the instance count and save — manual scale removes the autoscale rules and pins the resource to a fixed instance count. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- **Configure notifications** sends email or webhook alerts when a scale event occurs; predictive autoscale and the scale-in policy choices **Default**, **NewestVM**, **OldestVM** are Virtual Machine Scale Set capabilities rather than App Service plan capabilities. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))

## Compare and choose

- Manual scaling: Basic tier and up; no rules or schedules, no always-ready or prewarmed instances, no per-app maximum; ARR affinity on by default. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Autoscale: Standard tier and up; rule-based and schedule-based scaling, no always-ready or prewarmed instances, no per-app maximum; ARR affinity on unless disabled; rules apply plan-wide. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Automatic scaling: Premium v2 to v4 only; traffic-based, no schedules, always-ready instances (minimum 1), prewarmed instances (default 1), per-app maximum via **Maximum scale limit**; ARR affinity should be disabled manually. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Decision shortcut: automatic scaling when the trigger is HTTP traffic and you want per-app independence; autoscale when the trigger is a metric or a clock and you want uniform plan-wide behaviour. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Scale up versus scale out: scale up a stateful app (ARR affinity friendly) or one that needs dedicated resources, custom domains and certificates, staging slots or autoscale support; scale out a stateless app to gain throughput and elasticity. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Instance ceilings by tier: Basic **3**, Standard **10**, Premium **30**, App Service Environment (Isolated) **100**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- Tier-by-tier feature and quota comparisons live in the App Service limits table; VM sizes per tier are on the Windows pricing page. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- With automatic scaling you are billed **per second for every instance, including prewarmed instances**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))

## Gotchas

- Because only one scaling method should be active per plan, enabling automatic scaling or autoscale while another method is still configured leads to conflicting behaviour — remove or disable the other method first. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Premium v4 has separate configuration guidance, so check the Premium V4 article before switching a plan into that tier. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- A plan cannot leave the Free tier while a spending limit is still active on the subscription. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-scale-up))
- A plan that hosts both App Service web apps and Azure Functions apps cannot use automatic scaling — it is disabled there. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- ARR affinity cookies are on by default and block scale-out, so leave them off when using automatic scaling; stateful apps still need their session state designed for multiple instances. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Scale-in is deliberately slow: the platform typically starts reviewing for scale-in about **5–10 minutes** after load stops rising and then removes at most one instance every few seconds to a minute, while scale-out speed depends on the app's startup time. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Prewarmed-instance billing: while idle only the always-ready instances run and no prewarmed instance is allocated, so nothing extra is billed; when traffic arrives and those instances activate, a prewarmed instance is allocated and billed, and a replacement is provisioned once the prewarmed one is used. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- A plan's **assigned instances** are the minimum it must run and are what you are billed for, so they can exceed your apps' always-ready values. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- To recalculate assigned instances you must actually **change** an app's always-ready value — re-saving the same value does nothing — and the portal does not apply the recalculation correctly, so use the CLI or the ARM API. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Worked example: a plan shows 7 assigned instances while its apps have always-ready values of 2, 3 and 5, so you pay for 7; changing one app from 3 to 4 recalculates the plan down to 5 (the highest always-ready value). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- `AppServiceHTTPLogs` may show 404 entries for `/admin/host/ping`; these are harmless and do not affect availability or scaling, but a 5xx response on that endpoint can cause intermittent restarts, and the ping endpoint cannot be customized. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling))
- Flapping is a loop of opposing scale events — scaling in raises CPU on the remaining instances and triggers a scale-out that drops it again — so pair scale-out rules with scale-in rules and cool-down periods. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Autoscale rules act on the whole plan, so one busy app drags every app in the plan up and down; if apps in the same plan need different behaviour, automatic scaling is the per-app option. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
- Moving an autoscale setting to another region requires the REST API, and diagnostic settings created with the autoscale setting are not copied — recreate them in the destination region. ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-get-started))
