# Configure an internal or public load balancer

## Key concepts

- Azure Load Balancer is a managed cloud service that spreads inbound **Layer 4** TCP and UDP flows across backend virtual machines (VMs) or virtual machine scale set (VMSS) instances, using load-balancing rules and health probes to decide where each flow lands. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- The address you give the **frontend IP configuration** decides the type of load balancer: a **public IP address** creates a public load balancer, a **private IP address** creates an internal (private) load balancer. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Core components are **frontend IP configuration**, **backend pool**, **health probes**, **load balancer rules**, **high availability (HA) ports**, **inbound NAT rules** and **outbound rules**; you create them through Azure, Azure CLI, Azure PowerShell or ARM templates. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- A public load balancer handles internet-facing traffic and can also provide **outbound** connectivity by translating backend private IPs to public IPs; an internal load balancer only balances traffic inside the virtual network and can never accept traffic directly from the internet. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- One load balancer can expose several frontend IPs and hold several backend pools; separate load-balancing rules then send different frontend ports and protocols to different groups of instances. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Traffic is distributed as pass-through, giving ultralow latency and scaling to millions of TCP/UDP flows; load balancing and port forwarding are limited to TCP and UDP. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- Two SKUs are current: **Standard** and **Gateway**; **Basic** was retired on **September 30, 2025**, so new deployments use Standard (Gateway is for network virtual appliances). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Azure Load Balancer is one of the Load Balancing and Content Delivery services, alongside Azure Front Door and Azure Application Gateway, each with its own use case. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))

## Settings and limits

- **Backend pool**: instances sit in a single virtual network; VMs need no public IP to join a public load balancer's pool, stopped VMs can be added, and adding or removing instances reconfigures the balancer automatically. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Backend pool membership is by network interface or IP address, and a **Private Endpoint** can never be a backend pool member. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- **Health probe** protocol choices on Standard are **TCP**, **HTTP** and **HTTPS**; you also set the **unhealthy threshold** that decides when an instance is pulled out of rotation. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Probe-failure behaviour on Standard: established TCP connections to an unhealthy instance stay alive (they end only when the application closes the flow, an idle timeout fires, or the VM shuts down); a single unhealthy instance moves existing UDP flows to a healthy one; if every instance is unhealthy, all existing UDP flows terminate. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- A **load balancing rule** maps a frontend IP configuration and frontend port to a backend port and spreads traffic across **all** instances in the target pool; rules apply to **inbound traffic only**. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- An **HA ports** rule is a load-balancing rule with `protocol` set to `All` and `port` set to `0`; it balances all TCP and UDP flows on every port of an **internal Standard** load balancer, also carries ICMP, and makes its per-flow decision on the 5-tuple (source IP, source port, destination IP, destination port, protocol). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- An **inbound NAT rule** forwards a frontend IP and port to one **specific** VM or scale set instance rather than the whole pool, using the same hash-based distribution as load balancing. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- An **outbound rule** applies outbound network address translation (NAT) to every instance the backend pool identifies, letting backends reach the internet or other endpoints. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Standard supports both **IP based** and **NIC based** backend types; Basic was NIC based only and its pool endpoints had to be VMs in a single availability set or a VMSS. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- A public Standard load balancer requires a **Standard** public IP; Basic public IPs are not supported on a Standard load balancer (and Standard public IPs were not supported on Basic). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Availability zones: Standard frontend IP configurations can be **zone-redundant** or **zonal** for inbound and outbound traffic; Basic offered no availability zone support. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- The Standard SLA is **99.99%**; Basic had no SLA and was offered at no charge. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Management operations on Standard typically complete in **under 30 seconds**, versus **60-90+ seconds** typical for Basic. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Standard-only extras: **TCP Reset on Idle** on any rule, **declarative outbound rules**, **Azure Monitor** multidimensional metrics and diagnostics, and multiple frontends for both inbound and outbound (Basic allowed inbound frontends only). ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Standard platform integrations: Global VNet Peering for Standard internal load balancers, NAT Gateway for both Standard internal and public, Private Link for Standard internal, and the **Global** tier for cross-region load balancing on public Standard load balancers. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- **HA ports** are unsupported on public load balancers and on retired Basic, and they are not intended for typical web or application workloads that need port-specific rules; they target appliances such as firewalls, VPNs or SD-WAN devices. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Hard limits: load-balancing rules and inbound NAT rules support only TCP/UDP (no ICMP, except internal Standard with HA ports enabled); a rule cannot span two virtual networks; IP fragmentation of UDP/TCP packets is not supported; and outbound flow from a backend VM to an internal load balancer frontend fails. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Quota constraint: only **one public (NIC based)** and **one internal (NIC based)** load balancer per availability set, and this restriction does not apply to IP-based load balancers. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Move limits: resource-group move within the same subscription is supported for Standard load balancers and Standard public IPs, but **subscription move** is not supported; a standalone VM, availability set or VMSS can reference one SKU only, never both. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Security by default: Standard load balancers and public IPs are **closed to inbound connections** unless an **NSG** explicitly permits the traffic, and traffic is blocked if no NSG exists on the subnet or NIC; internal VNet traffic to an internal load balancer remains allowed. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))

## Compare and choose

- Public vs internal: choose **public** for internet-facing inbound traffic and for outbound SNAT from the backends; choose **internal** for private line-of-business traffic inside the VNet or from on-premises over hybrid connectivity; only Standard supports both types. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Load balancing rule vs inbound NAT rule: a rule spreads traffic across the whole pool, while an inbound NAT rule pins one frontend port to one named instance — the choice for single-instance SSH/RDP-style access. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Regular rules vs HA ports: use per-port rules for web and application ports; use HA ports (`protocol` = `All`, `port` = `0`) when every TCP/UDP port of an internal Standard load balancer must be balanced for NVA high availability. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Standard vs Gateway SKU: Standard is the general-purpose L4 service; **Gateway Load Balancer** targets third-party network virtual appliances and can be chained with a Standard load balancer. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Probe protocol choice: **TCP** is the simple connectivity check, **HTTP** and **HTTPS** validate an application path; the retired Basic SKU never supported HTTPS probes. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- Monitoring on Standard: multidimensional **Azure Monitor** metrics, prebuilt **Insights for Azure Load Balancer** dashboards, standard **diagnostics**, **health event logs** and load balancer **health status**; retired Basic supported no diagnostics. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))

## Gotchas

- Do not plan new Basic deployments: **Basic Load Balancer was retired on September 30, 2025**, so upgrade to Standard as soon as possible. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- Basic was open to the internet by default while Standard is closed by default, so a Standard public load balancer without an explicit NSG allow rule silently drops inbound traffic. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- A failing health probe does not sever existing TCP sessions on Standard; they survive until the application ends the flow, an idle timeout occurs, or the VM shuts down. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- If all backend instances are unhealthy, all existing UDP flows terminate; on the retired Basic SKU all TCP connections ended when all probes were down. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Outbound rules did not exist on Basic, and outbound flow from a backend VM to an **internal** load balancer frontend fails, which breaks apps that call back through the internal frontend. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Mismatching the public IP SKU to the load balancer SKU is invalid: a Basic public IP cannot attach to a Standard load balancer, and a Standard public IP cannot attach to Basic. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/skus))
- All frontends and their backend instances of one load balancer must live in the same virtual network; a load-balancing rule can never span two VNets. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- HA ports on a **public** load balancer are not supported, and HA ports is not a substitute for port-specific rules on ordinary web workloads. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/components))
- Azure Load Balancer stores no customer data and processes all traffic in real time, so use Azure Monitor, diagnostics and health event logs for evidence instead of expecting stored logs. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
- The **Admin State** setting lets you override health probe behaviour during maintenance for individual backend instances. ([Learn](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-overview))
