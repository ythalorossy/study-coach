# Evaluate effective security rules in NSGs

## Key concepts

- An Azure network security group (NSG) filters traffic to and from resources in a virtual network; its rules allow or deny inbound and outbound traffic, and each rule states source, destination, port and protocol. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- An NSG attaches at two levels: to a **subnet** and/or to a **network interface** (NIC). One NSG can serve many subnets and NICs, while each subnet and each NIC holds zero or one NSG. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- **Effective security rules** are the merged view of every rule that applies to a NIC: the rules of the NSG on the NIC plus the rules of the NSG on the subnet holding that NIC. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Inbound evaluation order is subnet NSG first, then NIC NSG; the same order applies to intra-subnet traffic. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- Outbound evaluation order is reversed: NIC NSG first, then subnet NSG, again including intra-subnet traffic. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- Inbound rules combine as AND: the port must be allowed by the subnet NSG *and* by the NIC NSG, so an allow in only one of them never reaches the VM. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Outbound rules combine as OR for denial: a deny in either NSG stops the flow, and the other NSG is then never evaluated. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- Built-in defaults set the baseline: the default **DenyAllInbound** rule (shown as **DenyAllInBound** in rule output) blocks all inbound traffic unless a custom rule explicitly allows it, and the default **AllowInternetOutbound** rule permits outbound traffic unless a custom rule denies it. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- Default rules also admit inbound traffic originating inside the virtual network, and VMs in one subnet can normally talk to each other. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Service tags such as **Internet**, **VirtualNetwork** and **AzureLoadBalancer** are named bundles of IP prefixes that simplify rule authoring. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Rules match by priority, where a lower number wins, so a custom rule must outrank the default deny to take effect. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))

## Settings and limits

- Portal path: open the VM, expand **Networking**, choose **Network settings**, select the NIC, expand **Help**, then pick **Effective security rules**; only the first 50 rules are listed, and **Download** exports the full set as a .csv. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- The same view opens from the standalone **Network interface** resource or from the **NSG** resource. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- PowerShell: `Get-AzEffectiveNetworkSecurityGroup -NetworkInterfaceName vm-nic -ResourceGroupName test-rg` returns the rules as JSON. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Azure CLI: `az network nic list-effective-nsg --name vm-nic --resource-group test-rg` returns the same JSON. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Prerequisites: Azure PowerShell module 1.0.0 or later (check `Get-Module -ListAvailable Az`, sign in with `Connect-AzAccount`) and Azure CLI 2.0.32 or later (check `az --version`, sign in with `az login`). ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- To find NIC IDs when only the VM name is known: `Get-AzVM -Name vm-1 -ResourceGroupName test-rg` then read `.NetworkProfile`, or `az vm show --name vm-1 --resource-group test-rg` then read `networkProfile.networkInterfaces[].id`. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Output fields: **NetworkSecurityGroup** holds the NSG ID, **Association** states whether the link is a **NetworkInterface** or a **Subnet**, and **EffectiveSecurityRules** lists the merged rules. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Names prefixed `defaultSecurityRules/` are the built-in defaults present in every NSG; names prefixed `securityRules/` are user-created rules. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Rules that use a service tag also expose `expandedDestinationAddressPrefix` (and the source equivalent), listing every address prefix the tag represents. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- When the same NSG is linked to both the NIC and the subnet, the output repeats entries for default rules and for shared custom rules. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- If an association changes right before you run the command, wait a few seconds so the output reflects the new state. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Effective rules appear only when an NSG is attached to the NIC, the subnet, or both, and only while the VM is in the running state. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- A VM can have several NICs, and each NIC has its own effective rule set; a subnet NSG applies to every NIC in that subnet, while NIC-level NSGs differ per interface. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Fixing blocked inbound port 80: source **Any**, source port **Any**, destination the VM IP, IP range or all subnet addresses, destination port **80**, protocol **TCP**, action **Allow**, priority **100**, name **Allow-HTTP-All**; create it in both NSGs when both are attached. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Windows WMI/DCOM management needs two inbound allows: TCP **135** for the RPC endpoint mapper plus the dynamic RPC range, which is `49152-65535` by default on current Windows but must be verified on the target host. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Give those two rules distinct unused priorities between **100** and **4096**, and add them to every NSG attached to the VM's subnet or NICs. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Create them with `az network nsg rule create --resource-group <resource-group> --nsg-name <nsg-name> --name Allow-RpcEndpointMapper --priority <priority-rpc-endpoint-mapper> --source-address-prefixes <management-source-prefix> --source-port-ranges '*' --destination-address-prefixes <target-vm-nic-or-subnet-prefix> --destination-port-ranges 135 --access Allow --protocol Tcp --direction Inbound`, plus a matching rule for `49152-65535`. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- The PowerShell equivalent is `Add-AzNetworkSecurityRuleConfig` for each rule, then `Set-AzNetworkSecurityGroup` to write the NSG back. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))

## Compare and choose

- Use the portal's **Effective security rules** pane for a fast visual check of a single NIC; use `Get-AzEffectiveNetworkSecurityGroup` or `az network nic list-effective-nsg` when you need full JSON for scripting and automation. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Effective rules show what is configured and applied; use **IP flow verify** in Azure Network Watcher for a yes/no verdict on a specific flow plus the rule responsible for allowing or denying it. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Reach the Azure Virtual Network Manager **network verifier** when you need insight into reachability between virtual machines, the internet, or other Azure resources, including NSG rules and other policies in play. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- Prefer attaching the NSG to the **subnet** over individual NICs, and use **application security groups** (ASGs) when selected NICs in that subnet need different rule sets. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- As a best practice, avoid attaching NSGs at both the subnet and NIC level for the same workload, because overlapping rules conflict and cause filtering problems that are hard to troubleshoot. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- If no NSG rule explains the failure, look outside the NSG: guest OS firewall software, routes for virtual appliances, or forced tunneling redirecting internet traffic on-premises. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- To filter traffic between VMs in one subnet, write the rule in the subnet NSG, since it reaches every interface in that subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))

## Gotchas

- Inbound is the stricter direction: one allow is not enough, while for outbound a single deny in either NSG stops the flow. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- The blocking default rule **DenyAllInBound** has source `0.0.0.0/0`, which includes the internet, and in the sample no higher-priority (lower-numbered) rule allowed port 80 inbound. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- The portal shows only the first 50 rules, so export the .csv with **Download** before concluding a rule is missing. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Duplicated rows do not mean a rule was applied twice; they come from an NSG attached to both the NIC and the subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Empty output means either no NSG is attached at any level or the VM is not running; check both before assuming the configuration is correct. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- When both levels carry an NSG, the fix must be applied twice, since the sample resolution requires creating the allow rule in the subnet NSG and the NIC NSG. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- The **VirtualNetwork** service tag expands to include peered virtual network prefixes automatically; inspect the expanded prefix list when peering causes surprises. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- A TCP 135-only test can succeed while the follow-on dynamic RPC connection is blocked, so verify the endpoint mapper and the dynamic range separately. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Treat `49152-65535` as the Windows default, not a guarantee; confirm the real range on the target host and put that value in the rule. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Intra-subnet traffic is filtered too: a rule denying all inbound and outbound traffic in a subnet NSG stops the VMs of that subnet from reaching each other. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- A subnet NSG rule changes the effective rules of every NIC in that subnet, so it can alter an unrelated VM that merely shares the subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- With no NSG at either level, one page describes traffic to the VM as unfiltered and blocked by default, noting a VM with a standard public IP address is secure by default until an NSG is attached. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-group-how-it-works))
- The other page frames the same gap as exposure: a VM with a public IP address and no NSG on the NIC or subnet leaves all ports open for inbound and outbound, so attach an NSG to the subnet hosting the NIC. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
- Rule names use `defaultSecurityRules/` and `securityRules/` prefixes, and the default inbound deny appears with an uppercase **B** in **DenyAllInBound**, which differs from the prose spelling **DenyAllInbound**. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/diagnose-network-traffic-filter-problem))
