# Configure resource locks

## Key concepts

- Management locks are an Azure Resource Manager feature that guard a subscription, resource group, or resource against accidental deletion or modification, and a lock wins over any permission a user or role already has ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- There are exactly two lock levels: **CanNotDelete** (authorized users can read and modify but not delete) and **ReadOnly** (authorized users can only read — nothing can be deleted or updated), which is roughly the **Reader** role's permission set applied to everyone ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- The same two levels have different display names in the portal: **Delete** and **Read-only** in the portal versus **CanNotDelete** and **ReadOnly** in command-line and template code ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Unlike Azure RBAC, which grants permissions to specific users, principals, or roles, a lock applies one restriction across all users and roles at the scope where it sits ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Lock scope options are a subscription, a resource group, or an individual resource — Azure provides four management scopes (management groups, subscriptions, resource groups, resources), and locks cannot be added to a management group ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview)).
- Locks are inherited: a lock at a parent scope applies to every resource inside it, including resources created afterwards, and when several locks stack along the chain the most restrictive one takes precedence ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Locks cover only control plane operations sent to `https://management.azure.com`; data plane calls that go straight to a service endpoint, such as `https://myaccount.blob.core.windows.net/`, are not restricted ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).

## Settings and limits

- Creating or removing a lock requires the `Microsoft.Authorization/*` or `Microsoft.Authorization/locks/*` actions, which the built-in **Owner** and **User Access Administrator** roles hold; you can also grant them through another specialized built-in role or a custom role ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Locks block POST requests to Azure Resource Manager, so operations that merely look like reads can fail — for example, a ReadOnly lock stops a user listing **storage account** keys, assigning Azure RBAC roles scoped to that storage account or to a data container, or creating a **blob container** through the control plane ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Neither CanNotDelete nor ReadOnly on a **storage account** protects the blob, queue, table, or file data itself; control plane deletes such as File Shares - Delete are blocked, while the data plane Delete Share succeeds ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A CanNotDelete lock on a resource or resource group also prevents Azure RBAC assignments from being deleted there, and on a resource group it blocks Resource Manager from auto-deleting deployment history entries, which matters at the 800-deployment ceiling ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A CanNotDelete lock on the resource group created by **Azure Backup Service** makes backups fail, because the service cannot clean up restore points; it supports at most 18 restore points ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Resource groups hold up to 800 instances of a given resource type (some types are exempt), and deleting a resource group deletes everything inside it ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview)).
- In the portal the subscription-level lock blade is labeled **Resource locks** while the resource-group-level one is labeled **Locks**; you open **Locks** in the resource's Settings blade, choose **Add**, then supply a lock name, lock level, and optional notes, and **Delete** removes it ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- In an ARM template or Bicep file the lock is a `Microsoft.Authorization/locks` resource at apiVersion `2016-09-01` with `properties.level` and an optional `properties.notes`; omit the `scope` property when locking at the deployment scope (resource group or subscription) and set `scope` when locking a single resource inside it ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- The REST call is `PUT https://management.azure.com/{scope}/providers/Microsoft.Authorization/locks/{lock-name}?api-version=2016-09-01`, where scope is a subscription, resource group, or resource and the lock name is free-form ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- PowerShell uses `New-AzResourceLock` with `-LockName` and `-LockLevel` plus `-ResourceGroupName`, or `-ResourceName` and `-ResourceType` for a single resource; inspect locks with `Get-AzResourceLock` and delete with `Remove-AzResourceLock -LockId` after reading `.LockId` from `Get-AzResourceLock` ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Azure CLI uses `az lock create --name --lock-type CanNotDelete --resource-group <rg>` plus `--resource-name` and `--resource-type` for a single resource, `az lock list` to view, and `az lock delete --ids $lockid` where the ID comes from `az lock show ... --query id --output tsv` ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Python uses `ManagementLockClient.management_locks` with `create_or_update_at_resource_level` or `create_or_update_at_resource_group_level`, plus `list_at_subscription_level`, `get_at_resource_level`, `delete_at_resource_level` and `delete_at_resource_group_level` ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).

## Compare and choose

- Choose **CanNotDelete** when authorized users must keep changing a resource but nobody should remove it; choose **ReadOnly** when the resource must stay frozen for everyone regardless of role ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Choose locks over RBAC when you need a blanket restriction for every user and role; choose RBAC when you need per-principal, per-scope permissions ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Choose a higher scope (subscription or resource group) when you want one restriction applied broadly; choose a resource-level lock when only that single resource must be protected ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview)).
- For an **NSG**, a ReadOnly lock prevents creation of the matching NSG flow log, whereas a CanNotDelete lock does not prevent that flow log from being created or modified — so pick CanNotDelete if flow logs must keep working ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- For a **SQL Database logical server**, either lock level stops deletion or modification of the server while still allowing data create/update/delete, because data transactions are data plane calls ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Use Azure Policy, not locks, when you need declarative restrictions or conventions enforced across a subscription; a resource group can be the scope for policies, roles, and locks alike ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).

## Gotchas

- A Delete lock on one resource blocks deletion of its entire resource group; there is no partial deletion, even if the group and the other resources are unlocked ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Locks do not stop subscription cancellation — Azure deactivates the resources first and deletes them permanently only after a waiting period ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Extension resources inherit the lock of the resource they extend, so locking a storage account also blocks deleting a **Microsoft.Insights/diagnosticSettings** entry pointing at its blob service ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A ReadOnly lock on a resource group blocks moving resources in or out of it, yet a resource carrying a ReadOnly lock can still be moved to a different resource group ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A ReadOnly lock on a resource group containing a **virtual machine** blocks starting or restarting it, blocks **automation account** runbook starts, and blocks scaling an **App Service plan** up or out, because those actions need POST requests ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A ReadOnly lock on a **Log Analytics workspace** blocks enabling User and Entity Behavior Analytics (UEBA), while a CanNotDelete lock still allows data purge — remove the **Data Purger** role instead of relying on the lock ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A ReadOnly lock on a **subscription** stops **Azure Advisor** from storing its query results; on an **Application Gateway** it blocks reading backend health; on an **AKS** cluster it blocks using the Kubernetes resources section in the portal; on **App Service** it blocks Server Explorer file listings ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- For **PostgreSQL**, clear any Delete or ReadOnly locks from the virtual network and all subnets before creating the server in that VNet, then reapply the locks afterwards ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A CanNotDelete lock on a **VM** protected by **Site Recovery** blocks removing some Site Recovery resource links when you disable replication; remove the lock first if you plan to protect the VM again ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- Managed application services such as **Azure Databricks** create a locked infrastructure resource group whose lock the system owns; deleting the lock or that group fails, so delete the parent service to remove both ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
- A CanNotDelete lock on a resource group containing an **Azure Machine Learning** workspace breaks cluster autoscaling, because unused nodes can no longer be removed ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources)).
