# Set up alert rules, action groups, and alert processing rules in Azure Monitor

## Key concepts

- An **alert rule** watches resources, takes a signal from them, and evaluates conditions; when the conditions are met it fires an **alert**, runs the attached action groups, and updates alert state ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- If one rule covers several resources, each resource is evaluated separately and its own alert fires ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- An **action group** is a reusable bundle of who gets notified and what runs automatically; each action has a **Type**, a **Name**, and type-specific **Details** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- **Alert processing rules** (formerly action rules) modify alerts as they fire instead of creating new ones; the ARM resource type is still `Microsoft.AlertsManagement/actionRules` ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Processing rules can add action groups, suppress (remove) action groups, apply filters, and follow a schedule, over a scope from one resource up to a whole subscription in the same subscription ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Alerts are **stateful** (fire once, stay `fired` until resolved, then a resolved notification is sent) or **stateless** (fire every time the condition is met); all activity log alerts are stateless ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- A metric alert resolves after three consecutive checks without the condition being met; a log search alert resolves when the condition isn't met for a span tied to its frequency (1 minute → 10 minutes; 5–15 minutes → 3 periods; 15 minutes–11 hours → 2 periods; 11–12 hours → 1 period) ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- Alert instances are deleted after 30 days, but a stateful alert's condition is kept until it resolves so the rule can't re-fire; **User response** stays **New**, **Acknowledged**, or **Closed** until you change it, and fired instances are read-only so edits only affect future alerts ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- Alert types include metric, log search, simple log search, activity log, smart detection, and Prometheus; recommended out-of-the-box rules cover virtual machines, AKS resources, and Log Analytics workspaces ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))

## Settings and limits

- Up to five action groups can be attached to one alert rule; they execute concurrently in no defined order, and one action group can be reused by many rules ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- An action group lives in a region chosen at creation: **Global** (persisted in at least two regions, processed anywhere, required for Service Health alerts) or **Regional** (zone-redundant, processed inside your chosen geography) ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Regional processing is offered in East US, West US, East US2, West US2, South Central US, North Central US, Sweden Central, Germany West Central, India Central, and India South ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Notification types are **Email**, **Email Azure Resource Manager role**, **SMS**, **Azure app push notifications**, and **Voice**; action types are **Automation Runbook**, **Event hubs**, **Functions**, **ITSM**, **Logic apps**, **Secure webhook**, and **Webhook** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- The **Email Azure Resource Manager role** notification mails role members and supports only Owner, Contributor, Reader, Monitoring Contributor, and Monitoring Reader; new recipients must confirm their address with a code within 30 minutes of saving the group, while ARM-role emails need no confirmation ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- SMS replies work: `DISABLE <Action Group Short name>`, `ENABLE <Action Group Short name>`, `STOP`, `START`, `HELP` ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Rate limiting suspends SMS, voice, push, and email per phone number, address, or device across all subscriptions; other action types aren't rate limited ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A webhook is retried up to 5 times after a failed first call with delays of 5, 20, 5, 40, and 5 seconds; after that the endpoint is left alone for 15 minutes, and only status codes 408, 429, 503, 504 or `HttpRequestException`/`WebException`/`TaskCancellationException` are retried ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- **Event hubs** is the only action type supporting Azure Private Link and network security perimeter, with cross-tenant support from API version `2023-09-01-preview` ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Managed identity for action groups (preview) works for Automation Runbook (Automation Contributor), Azure Function, Event Hub (Azure Event Hubs Data Sender), and Logic App (Logic App Contributor), but not for ITSM, Secure webhook, or Webhook ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- In an ARM template an action group is a `Microsoft.Insights/actionGroups` resource whose `groupShortName` is at most 12 characters ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A metric rule supports up to five conditions; each sets **Threshold** (static or dynamic), **Operator**, **Aggregation type** (Sum, Count, Average, Min, Max), **Threshold value**, **Unit**, and for dynamic thresholds **Threshold sensitivity** of **High**, **Medium** (default), or **Low** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- The dynamic threshold operator default is "greater than the upper threshold or lower than the lower threshold", and dynamic rules can also set **Number of violations**, **Evaluation period**, and **Ignore data before** in **Advanced options** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- Evaluation uses **Check every** plus **Lookback period**, for example checking every 1 minute while looking back 5 minutes ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- With multiple conditions you may pick only one value per dimension, can't use the "all current and future values" asterisk, and can't use dynamic thresholds; dimensions shared by two conditions must carry the same value in both ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- Metric rule names can't be changed after creation, must be unique per resource group, can't contain `* # & + : < > ? @ % { } \ /`, can't end in a space or period, and resource group plus rule name is capped at 252 characters ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- **Enable upon creation** starts the rule right away and **Automatically resolve alerts** makes it stateful; without that box the rule is stateless ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- **Custom properties** are key/value pairs of static text or `${<path to schema field>}` values; they reach webhook, Logic Apps, Azure Functions, and Automation runbook payloads but not email, SMS, or push, and don't show on the alert details page ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- A custom-metric rule can be pinned to North Europe, West Europe, Sweden Central, or Germany West Central ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- Processing rule filters include alert context, alert rule ID, alert rule name, description, monitor condition, monitor service, resource, resource group, resource type, and severity; filters combine with AND, each filter holds up to five values combined with OR, and the matched string must have no spaces ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- A processing rule runs all the time by default, or you can set a one-time window or a recurring schedule ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Creating an alert rule needs read on the target resource, write on the resource group holding the rule, and read on any linked action group; **Monitoring contributor** creates alerts and **Monitoring reader** views them ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))

## Compare and choose

- **Alert rules** generate new alerts; **alert processing rules** alter fired alerts, so use the latter for post-firing routing or suppression ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Suppressing via a processing rule strips action groups from fired alerts, while disabling alert rules stops alerts firing at all; disabling is impractical when a rule covers resources not under maintenance, when many rules cover the resource, or when alerts don't come from a rule (such as Azure Backup) ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Choose **Global** processing for Service Health alerts and geographic independence, **Regional** processing when zone redundancy or a data-residency boundary matters ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- **Webhook** fits a public endpoint needing basic auth in the URI, **Secure webhook** fits a protected API authenticated by a Microsoft Entra ID service principal and doesn't do basic auth, and **Event hubs** is the pick for private targets because it alone supports Private Link and network security perimeter ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Use **Logic apps** when the endpoint expects a particular schema (for example Microsoft Teams) and the payload must be reshaped first ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A **static threshold** uses your configured value; a **dynamic threshold** learns the metric's behavior pattern, and sensitivity controls required deviation — High triggers on the smallest deviation, Medium is the default balance, Low only on large deviations ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- Turn on **Automatically resolve alerts** for a stateful rule that fires once and later reports resolution; leave it off for a stateless rule that keeps notifying while the condition holds ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- If one fired alert matches both a **Suppress notifications** rule and an **Apply action group** rule, suppression wins on priority ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- For alert sources that can't pick their own action groups (Azure Backup, VM Insights guest health, Azure Stack Edge, Azure Stack Hub), attach action groups with a processing rule; processing rules don't affect Azure Service Health alerts ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- At scale: one metric rule can cover same-type resources in one region with a notification each, log search rules can cover everything reaching a workspace with **Split by dimensions** giving one alert per resource, Azure policies can create rules en masse, and simple log search alerts evaluate every row for near-real-time alerting ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))

## Gotchas

- Older tooling still calls processing rules action rules, so `Microsoft.AlertsManagement/actionRules` remains the resource type to use ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- A new or updated processing rule can take up to 30 minutes to take effect, and alerts fired during that window may escape it ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- A processing rule can't cover a resource belonging to a different subscription ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Suppressed alerts remain visible in the portal, Azure Resource Graph, the API, and PowerShell, and because every action group is removed they also skip the end-of-maintenance resolved notification ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- The **Alert rule ID** filter needs the full resource ID, such as `/subscriptions/SUB1/resourceGroups/RG1/providers/microsoft.insights/metricalerts/MY-API-LATENCY` ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules))
- Service Health alerts exist only in the public cloud and need the action group's region set to **Global** to respond properly ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A Functions action embeds the function's HTTP trigger endpoint and access key, so rotating the key means deleting and re-creating that action; the endpoint needs HTTP POST and the function needs storage account access ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A webhook endpoint must be publicly reachable, can't receive security certificates, and must tolerate the different JSON payloads that alert sources emit ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- After a new Azure Resource Manager role is added to a subscription it can take up to 24 hours for members to start getting notifications, and each member needs a primary email in their Microsoft Entra profile ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- Save the action group before using **Test**; closing the test window stops the run and yields no results, and a finished test shows **Success** or **Failed** with **Error details** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups))
- A metric can need 10 to 15 minutes to become available after the resource is created, so a rule made right away may have no data yet ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- There is no deduplication: two rules with the same conditions both fire, and each metric rule is billed per monitored time series ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
- In a multi-condition rule, filtering one condition on a dimension (for example `ApiName` = `GetBlob`) forces the same dimension value on the other conditions that share it ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule))
- Stateless metric notification cadence follows the rule's frequency: under 5 minutes a notice goes out between 1 and 6 minutes; 5 minutes or more, between the frequency and twice it (15 to 30 minutes for a 15-minute frequency) ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-overview))
