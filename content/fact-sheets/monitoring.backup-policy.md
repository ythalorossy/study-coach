# Create and configure a backup policy

## Key concepts

- A backup policy lives inside a Recovery Services vault and has two parts: a **Schedule** (when the backup runs) and a **Retention** (how long each recovery point is kept). ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- One policy can protect many Azure VMs; policies can also be authored for SQL Server databases hosted in Azure VMs, for SAP HANA databases running in Azure VMs, and for Azure file shares, while MARS file/folder settings live in the MARS console. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- A vault holds recovery points and policies, can hold up to 500 Recovery Services vaults per Azure subscription, and its access is managed with Azure RBAC. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Recovery Services vaults replicate with **GRS** by default; the options are **LRS** (three copies in a single datacenter, 11 nines durability), **GRS** (paired secondary region) and **ZRS** (availability zones, residency in the same region). ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Azure VM backup relies on an extension installed by the Azure VM agent: **VMSnapshot** on Windows and **VMSnapshotLinux** on Linux; the **MARS agent** covers files/folders and on-premises Windows servers. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Azure Backup reads each disk's blocks and sends only the delta since the previous run, with the disks handled in parallel, so every backup after the first one is incremental. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- The **Enhanced** policy type adds zone-redundant Instant Restore snapshots, several backups per day (as often as every 4 hours), support for Trusted Launch VMs, Premium SSD v2, Ultra Disks and multidisk crash-consistent snapshots, plus snapshot-tier retention of up to 30 days. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Creating a vault automatically produces system-managed default policies such as **DefaultPolicy**, **HourlyBackup** and **Enhanced**; they can be deleted but are recreated automatically and act as fallbacks. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))

## Settings and limits

- Portal path to create one: open the Recovery Services vault → **Backup** → **Backup policies** → **+ Add** → on **Select policy type** pick **Azure Virtual Machine** → on **Create policy** set **Policy subtype**. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- The **Policy subtype** choices are **Standard** and **Enhanced**. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- **Backup schedule** frequency can be **Hourly**, **Daily** or **Weekly**. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Hourly schedule defaults: start time **8 AM**, repeat every **4 hours**, duration **24 hours**; intervals of 4, 6, 8, 12 or 24 hours can be chosen. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- With an hourly schedule the recovery point objective ranges from a 4-hour floor to a 24-hour ceiling; choosing the lower 12-hour RPO lets snapshot retention rise to 30 days. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- **Instant Restore** snapshot retention ranges from 1 to 30 days and defaults to 7 days, and it can never exceed the vault retention duration. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- The maximum Instant Restore retention shrinks as daily snapshot count grows - for example every 4 hours over 24 hours means six scheduled snapshots and fewer allowed retention days. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- **Retention range** choices are preselected from the chosen frequency, with defaults of 180 days for daily points, 12 weeks for weekly points, 60 months for monthly points and 10 years for yearly points; all are editable. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Monthly and yearly backup points fall under Long Term Retention (LTR); weekly retention means a run on a chosen weekday, monthly on a chosen day of the month, yearly on a chosen day of the year. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Under **Backup Now**, the **Retain Backup Till** field sets that on-demand backup's retention; an on-demand job duplicates the entire VM when the very first backup has not completed, and otherwise transmits only what changed since the last snapshot. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- A sensible pattern is roughly four backups per day for a VM - one from the policy schedule plus three triggered by hand - although on-demand backups stop at nine attempts so failed runs can be retried. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- To edit an existing policy: vault dashboard → **Manage** → **Backup policies** → select the **Azure Virtual Machine** policy → **Modify**; to move a VM to another policy, pick the policy on the vault item dashboard and select **Save**, which applies immediately. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- Retention edits reach back: the duration you set is imposed on recovery points already stored, so shortening it prunes them and lengthening it keeps older ones longer. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Moving the schedule from daily to weekly clears existing daily recovery points; moving from weekly to daily keeps weekly ones only for the days remaining under current retention. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Premium-storage VMs need free space for a temporary staging location named **AzureBackup-** sized like the recovery point snapshot; it is removed when the job ends and billed at premium page blob rates. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Vaulted data sits in a Microsoft-managed subscription and tenant, is encrypted at rest with Microsoft-managed keys by default, travels over HTTPS with TLS 1.2+, and **Multi-User Authorization** adds an Azure Resource Guard layer for critical operations. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))

## Compare and choose

- Pick **Enhanced** when you need zone-resilient Instant Restore storage, more than one backup per day (minimum 4-hour interval), Trusted Launch VMs, Premium SSD v2, Ultra Disks or multidisk crash-consistent snapshots. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Pick **Standard** for the cheaper, established behaviour; it cannot protect Ultra Disk or Premium SSD v2, and Trusted Launch VM backup with Standard needs Azure CLI 2.73.0+, PowerShell Az 14.0.0+ or REST API 2025-01-01+. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Use **selective disk backup** to exclude noncritical or shared disks and cut snapshot cost; a subset of disks can then be restored from a recovery point in both Instant Restore and the vault tier. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- **Stop protection and retain backup data** halts future jobs but keeps recovery points (you still pay), restores remain possible and **Resume backup** stays available. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- **Stop protection and delete backup data** halts jobs and wipes recovery points, so no restore is possible and **Resume backup** is not offered; the data is kept for 14 days in a soft-delete state you can still recover from. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- **Delete backup data** on the vault item dashboard is only enabled if you previously stopped protection while retaining data, and it removes all recovery points together - individual points cannot be selected. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- **Full** = entire data source, used for the first backup; **Incremental** = only blocks changed since the previous backup, used for all backups to Azure; **Differential** = blocks changed since the last full and is not used by Azure Backup. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- **LRS** protects against rack or drive failure, **GRS** against region-wide outages, **ZRS** against zone failures while keeping data in the same region. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Backups can move from the **Archive** tier to **Vault-Standard** for restores or management work; Vault-Standard restores faster but costs more to store. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Consistency choices: VSS-based app-consistent snapshots on running Windows VMs (full VSS backup by default, file-consistent fallback), file-consistent on Linux unless you add pre/post scripts, and agentless crash-consistent backups when application consistency is unnecessary. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))

## Gotchas

- Once a VM backup is enabled with the **Enhanced** policy you cannot switch that VM back to **Standard**; migration from Standard to Enhanced exists in preview. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Enabling Enhanced adds snapshot cost, so weigh it against the resilience and frequency gains. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Backup jobs fail for disks that have data access authentication turned on. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- With hourly schedules the last backup of the day is what is transferred to the vault; if that fails, the first backup of the next day is transferred instead. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Enhanced policy is offered in all Azure public and US Government regions, and VMs whose disks have public network access disabled can be backed up. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-vms-enhanced-policy))
- Deleting a VM without stopping protection makes on-demand backups fail with **UserErrorVmNotFoundV2**; the critical pre-check appears only for failed on-demand jobs, not for failed scheduled ones. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- Backup items whose source VM is gone stay active and billable: expired points are cleaned per policy, but up to two of the newest points (a vaulted restore point plus the most recent one) can outlive policy expiry, so delete those items to stop charges. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- Removing recovery points that spent less than 180 days in the **Archive** tier triggers an early deletion charge. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- Changing only the schedule days while retention stays the same stops new points for the removed days, and because backups are incremental the storage reduction is gradual. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Snapshot data is not always copied to the vault immediately - at peak times this can take hours, and a VM's total backup time stays under 24 hours for daily policies. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- On Windows the snapshot extension coordinates with VSS: **Microsoft Visual C++ 2015 Redistributable (x64) version 14.40.33810.0** is installed, VSS startup is set to automatic and the **IaaSVmProvider** service is added. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- To rebuild the Windows extension: run `Remove-AzVMExtension -ResourceGroupName "<rg>" -VMName "<vm>" -Name "VMSnapshot"`, stop the **Windows Azure Guest Agent** service, rename `C:\Packages\Plugins\Microsoft.Azure.RecoveryServices.VMSnapshot` to `..._old`, delete `HKEY_LOCAL_MACHINE\Software\Microsoft\WindowsAzure\HandlerState\Microsoft.Azure.RecoveryServices.VMSnapshot_1.X.XX.X`, run `REG ADD "HKLM\SOFTWARE\Microsoft\BcdrAgent" /v IsProviderInstalled /t REG_SZ /d False /f` and the matching `BcdrAgentPersistentKeys` command, restart the agent and the VM, then run an on-demand backup. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- On Linux, delete the `Microsoft.Azure.RecoveryServices.VMSnapshotLinux-1.0.XXXX.X` folder under `/var/lib/waagent` and trigger a VM backup so the extension is reinstalled. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-manage-vms))
- On-premises Linux machines cannot be backed up directly with the MARS agent; use DPM or MABS instead. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
- Before restoring an encrypted managed-disk VM, make sure its keys and secrets already exist in the key vault. ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-architecture))
