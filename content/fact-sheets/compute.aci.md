# Provision a container by using Azure Container Instances

## Key concepts

- Azure Container Instances (ACI) is a serverless service for running Linux or Windows containers in Azure with no virtual machines to provision or manage and no cluster orchestrator to adopt; it comes in regular, confidential and Spot variants. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Startup is quick because nothing has to be provisioned first; popular base OS images are cached in the service to shorten custom image deployments, and **standby pools** make starts even faster. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Images may come from Docker Hub, from your own Azure Container Registry (ACR), or from another cloud-hosted Docker registry. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- The unit you deploy is a container group: one group can carry several containers that live on the same container host and share the group's network, storage and lifecycle, which is how you add sidecars such as a log shipper next to your app container. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Public access works through an assigned IP plus a domain name; you choose the label portion, so the app answers at `<customlabel>.<azureregion>.azurecontainer.io`. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- A managed identity lets the group sign in to any Microsoft Entra-supported service without credentials embedded in the code, and the same identity can authenticate the ACR pull so no user name or password is kept in the group definition. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Confidential containers execute inside a trusted execution environment (TEE) that delivers hardware-level confidentiality and integrity guarantees and encrypts data while it sits in memory; you opt in by choosing that SKU at deployment. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Spot containers are interruptible workloads scheduled onto spare Azure capacity, priced up to 70% below regular-priority containers and charged per second of memory and core usage, with preemption possible whenever Azure runs short on room. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Persisting output means mounting Azure Files shares (backed by Azure Storage) into the group, and debugging is helped by exec-style shell access into a live container, reached over HTTPS with TLS. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- **NGroups** gives fleet control over several linked groups (target count, rolling upgrades, multi-zone placement, load-balancer ingress, confidential containers), while **virtual nodes on ACI** let AKS pods execute as ACI groups so you keep Kubernetes constructs without the cluster autoscaler provisioning VM nodes. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Isolation is hypervisor level: code inside a container on ACI is separated from other tenants about as strongly as it would be inside a virtual machine. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))

## Settings and limits

- Portal route: **Create a resource** > **Containers** > **Container Instances**. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- On **Basics** you fill in **Resource group**, **Container name**, **Image source** and **Container image**; the quickstart uses `myresourcegroup`, `mycontainer`, **Quickstart images** and `mcr.microsoft.com/azuredocs/aci-helloworld:latest` (Linux), a Node.js program that serves a static HTML page. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- For **Availability zones**, choose the logical zone the group should land in; leaving **None** (the default) skips pinning, and zonal placement is offered only in regions that have availability zones. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- On **Networking**, the **DNS name label** you type has to be unique inside that Azure region; the resulting address pattern is `<dns-name-label>.<region>.azurecontainer.io`, and a "DNS name label not available" message means the label is taken, so pick another. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- **DNS name label scope reuse** offers **Tenant**, **Subscription**, **Resource Group**, **No reuse** and **Any reuse**; **Any reuse** is flagged as the weakest option, and the quickstart picks **Tenant**. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- Restart policy is set per container group with three values: **Always** (applied automatically if you specify nothing), **Never**, and **OnFailure**. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- In the CLI the policy is passed as `az container create --restart-policy <Always|Never|OnFailure>`; the locally installed CLI must be version 2.0.21 or newer, or run it from Azure Cloud Shell. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- Once the service halts a container set to **Never** or **OnFailure**, that container's state reads **Terminated**; read it with `az container show --resource-group myResourceGroup --name mycontainer --query containers[0].instanceView.currentState.state`. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- Log access: portal path **Settings** > **Containers** > **Logs**; CLI path `az container logs --resource-group myResourceGroup --name mycontainer`, which prints the STDOUT stream (the `mcr.microsoft.com/azuredocs/aci-wordcount:latest` image runs a Python script over Shakespeare's Hamlet and prints its ten most frequent words before exiting). ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal), [Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- Deployment flow: **Review + create**, then **Create**; two notifications follow (request in progress, then group deployed), and you reach the group through **Resource Groups** > `myresourcegroup` > `mycontainer` and browse to its FQDN once **Status** shows **Running**. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- Removal: from the group's **Overview** choose **Delete**, then answer **Yes** in the confirmation dialog. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- Sizing is declared precisely per group — you state CPU cores and memory — and charging is per second, so a short-lived job stops costing the moment it finishes. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- GPU: for heavy compute jobs such as machine learning, Linux containers can be placed on NVIDIA Tesla GPU resources, currently in preview. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Image ceiling: 15 GB; larger images can behave unpredictably. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Architecture ceiling: x64 (AMD64) images are the only kind that run here; arm64 images cannot. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Every secure connection to ACI has to negotiate TLS 1.2; the 1.0 and 1.1 versions have been withdrawn. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Windows and Linux containers are scheduled through one API; you state your preferred OS type when creating the container group. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Some features exist only for Linux containers: several containers in one group, volume mounting (Azure Files, `emptyDir`, GitRepo, secret), Azure Monitor resource-usage metrics, and GPU resources (marked retired). ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Virtual network placement: a group living in a VNet subnet needs a NAT gateway for its outbound traffic, and that is the only outbound arrangement the service supports; once there it can reach other VNet resources and on-premises systems over VPN gateway or ExpressRoute. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Availability zones: a group can be pinned to a zone you choose yourself, and the zone is decided one group at a time. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))

## Compare and choose

- Restart policy choice: **Always** suits an always-on service and is the fallback when you choose nothing; **Never** suits a job that should end after it succeeds; **OnFailure** suits a job you want retried after an error, and the container is always run at least once. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- **Never** versus **OnFailure**: **Never** promises no restart only after a clean exit (code 0), whereas **OnFailure** restarts the container after a nonzero exit code — pick **OnFailure** when you want recovery from crashes but no endless loop after success. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- Regular versus Spot: standard priority when uptime matters; Spot when eviction is acceptable, taking a discount of up to 70% in exchange for being cut off during capacity shortages. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Regular versus Confidential: choose Confidential when data in use must stay protected by hardware isolation and memory encryption, since it is picked as a deployment SKU; NGroups can also roll out confidential groups. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- ACI versus AKS: use a plain ACI group for one isolated container or a one-shot task; use AKS pods on virtual nodes when you need Kubernetes APIs, cluster scheduling and orchestration while the actual compute stays serverless. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- One group versus NGroups: a single container group covers one workload; NGroups is the option when you need a maintained number of groups, coordinated rolling upgrades, spread across zones, or load-balanced ingress for a set of related groups. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))

## Gotchas

- An error exit (nonzero code) can make the platform restart the container no matter which policy you picked, even **Never**; to guarantee single execution, absorb errors inside the app and exit 0, or inspect the exit code with `az container show` and react to it yourself. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-restart-policy))
- Restarting a group can change its IP address, so never bake an IP into your configuration; when you need a fixed public address, put Application Gateway in front of the group. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Platform maintenance can bounce your groups without anyone asking, and a number of Windows Server base images have dropped support — start from one of the common Windows base images that still work. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Certain port numbers are reserved for the service's own use and binding them causes strange behaviour; the service also blocks privileged container operations, so a design that depends on the root directory is unsupported. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Secrets you type on a CLI command line are kept in clear text in the backend; put them in CLI environment variables so they are encrypted or transformed when stored. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Skipping the NAT gateway in a virtual network removes the group's outbound path, so it is a requirement rather than an option for VNet deployments. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Labels are claimed per region, and a generated hash is woven into the FQDN to stop malicious subdomain takeover; broad reuse choices such as **Any reuse** weaken that protection, so a narrower scope such as **Tenant** is preferable. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-quickstart-portal))
- Escalation order: restart the container, then re-check your own application code and local network setup, then use the troubleshooting guide, and only then contact support. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
- Customer data is not retained by the service, though the subscription IDs behind created resources are kept because groups depend on them to keep running. ([Learn](https://learn.microsoft.com/en-us/azure/container-instances/container-instances-overview))
