# Configure storage tiers

## Key concepts

- Access tiers are a block blob feature only: tiering applies to block blobs and is not supported for append blobs or page blobs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- **Hot** tier is the online tier for data that is read or written often; it has the highest per-GB storage cost but the lowest access and transaction cost, with millisecond time-to-first-byte. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- **Cool** tier is online and meant for infrequently touched data that must still be readable and writable instantly; storage is cheaper than hot, access and transaction costs are higher, and blobs should be kept at least **30 days**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- **Cold** tier is also online with millisecond retrieval, cheaper storage and higher access cost than cool, and blobs should be kept at least **90 days**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- **Archive** is the offline tier with the lowest storage cost and the highest retrieval cost; an archived blob cannot be read or modified until it is rehydrated, and retrieval latency is measured in hours with a **180-day** minimum retention. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- **Smart** tier automatically moves data between hot, cool and cold based on usage patterns instead of relying on tier changes you trigger. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Availability: hot is **99.9%** (**99.99%** for RA-GRS reads); cool, cold and archive are **99%** (**99.9%** for RA-GRS reads). ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Hot, cool and cold support all redundancy configurations; archive works only with **LRS**, **GRS** and **RA-GRS**, so ZRS, GZRS and RA-GZRS accounts cannot hold archived blobs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Storage capacity limits are applied at the storage account level rather than per access tier, so capacity can be concentrated in one tier or spread across several. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))

## Settings and limits

- Default account tier in the portal: **Settings** > **Configuration** > **Blob access tier (default)**, with values Hot, Cool or Cold; it defaults to Hot. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Default account tier at creation time: on the **Advanced** tab, under **Blob storage**, set **Access tier** to Hot, Cool or Cold. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- The default applies only to blobs without an explicit tier; the portal labels those blobs **Hot (inferred)**, **Cool (inferred)** or **Cold (inferred)**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Per-blob override on upload: **Upload** > expand **Advanced** > **Access tier** = Hot or Cool; this wins over the account default. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Change an existing blob's tier in the portal: select the blob, choose **Change tier**, pick the target tier, then **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Outside the portal, move tiers with the **Set Blob Tier** operation or the `azcopy set-properties` command, using PowerShell, Azure CLI, AzCopy v10 or a Storage client library. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Minimum tool versions for the cold tier: REST API **2021-12-02**; .NET and Python both need **12.15.0**; Java needs **12.21.0**; JavaScript needs **12.13.0**; the PowerShell Az.Storage module needs **5.8.0**; the Azure CLI needs **2.50.0**; AzCopy needs **10.18.1**; and Azure Storage Explorer needs **1.29.0**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Rehydration priority comes from the optional `x-ms-rehydrate-priority` header on Set Blob Tier or Copy Blob: **Standard** is the default and can take up to **15 hours** for blobs under 10 GB, while **High** can complete in under an hour for the same size but costs more. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Call Get Blob Properties to read `x-ms-rehydrate-priority` on an in-flight restore; it returns **Standard** or **High**, and a pending request can be raised to High but never lowered back to Standard. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Rehydration throughput is capped at **10 GiB per storage account per hour** with priority retrieval, and that cap is account-wide rather than per blob, so bulk restores do not scale linearly and can be throttled. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Minimum retention: general-purpose v2 accounts bill **30 days** for cool and **90 days** for cold if you delete or move early, while legacy Blob Storage accounts have no minimum retention for cool or cold; archive is 180 days everywhere. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- The archive tier cannot be chosen as an account's default access tier, and a legacy Blob Storage account must be created with hot or cool selected. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- For many blobs, enumerate them and call Set Blob Tier on each, or bundle calls into a single **Blob Batch** request (which supports Set Blob Tier and Delete Blob) for better performance. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))

## Compare and choose

- Warmer to cooler (hot to cool, hot to cold, hot to archive, cool to cold, cool to archive, cold to archive) is billed as a write operation to the destination tier; cooler to warmer moves are billed as a read plus data retrieval from the source tier. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Use **Set Blob Tier** for warmer to cooler moves: it moves the blob and its data in place and is instant between online tiers. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Use **Copy Blob** for cooler to warmer moves and for archive rehydration: the source blob stays in its original tier, a new blob is created in the target, and no early deletion penalty is charged, but you pay capacity for two blobs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Lifecycle management policies are the rule-based way to move data to cooler tiers (and expire it) inside a single account; they cannot rehydrate an archived blob back to an online tier. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- For tier moves at scale across multiple accounts, use a **storage task** in Azure Storage Actions rather than per-account lifecycle rules. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Changing the account default tier is chargeable in general-purpose v2 accounts: switching cooler bills write operations per 10,000 for every blob whose tier is inferred, and switching warmer bills reads per 10,000 plus data retrieval per GB; legacy Blob Storage accounts are only charged when going warmer. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Rehydrate with **Copy Blob** when the archived source must stay archived, when the data sits in an RA-GRS secondary region, or when you need the copy in another account in the same region (service version 2021-02-12 or later); use **Set Blob Tier** when you want to change the tier of the existing blob and can accept the retrieval cost and the 180-day rule. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Workload fit: hot for actively used data or data staged for later cool migration; cool or cold for short-term backup and disaster recovery, aging datasets that still need instant access, and large low-touch data sets; archive for long-term or secondary backups, raw data that must be preserved, and compliance data that is hardly ever read. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Premium block blob storage cannot be tiered to hot, cool, cold or archive by Set Blob Tier or lifecycle management; data must be copied out with the **Put Block From URL** API or a compatible AzCopy version into the hot tier of another account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))

## Gotchas

- Early deletion penalties are prorated: deleting a cool blob after 21 days bills 9 more cool days (30 minus 21), and deleting an archived blob at 120 days bills the full 180 days; rewriting a blob with Put Blob, Put Block List or Copy Blob inside the window counts as deletion. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- With soft delete enabled, a blob only counts as deleted once its retention period expires, so no early deletion fee applies while it is merely soft-deleted. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- While a blob is being rehydrated it keeps being billed as archive data until the tier actually flips to hot, cool or cold. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- A Set Blob Tier rehydration request cannot be cancelled after it is submitted, and the blob's access tier still reports archive for the whole operation. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Set Blob Tier does not update the last modified time, so a `tierToArchive` lifecycle action without a `daysAfterLastTierChangeGreaterThan` condition can re-archive a blob you just rehydrated; add that condition or rehydrate by copying instead. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- A rehydrating Copy Blob must target a different blob name or container, never the source itself, and the destination cannot be the archive tier; the new blob can appear in the container listing while still reporting archive, so don't delete the source until you see the `Microsoft.Storage.BlobTierChanged` Event Grid event instead of polling Get Blob Properties. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
- Snapshots aren't supported for archived blobs, and archived snapshots or previous versions can't be rehydrated in place — copy them to an online tier; archived metadata stays readable but read-only while index tags remain writable, and metadata is billed at cool-tier rates. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Changing an account's redundancy while archived blobs exist requires rehydrating every one of them to hot, cool or cold first; the LRS to GRS move is only supported if nothing was archived while the account was LRS. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Explicitly moving a blob that is in cool or cold to archive triggers the early deletion charge for the tier it left. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Set Blob Tier only moves between online tiers: a blob using an encryption scope can't be archived that way, and a new blob with an encryption scope can't have its access tier changed on upload. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-online-manage))
- Enabling Data Lake Storage Gen2, NFS 3.0 or SFTP on an account can reduce feature support for tiering, so check the feature support matrix for your account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Cost runs in opposite directions: per-GB capacity price falls as the tier gets cooler while read access and per-transaction prices rise, and tier changes on versioned or snapshot blobs can add charges. ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview))
- Rehydration billing: Set Blob Tier is charged for read transactions plus data retrieved, while Copy Blob adds destination write transactions and carries no early deletion fee; a high-priority request on a blob under 10 GB that takes more than five hours is not billed at the high-priority retrieval rate (standard rates still apply). ([Learn](https://learn.microsoft.com/en-us/azure/storage/blobs/archive-rehydrate-overview))
