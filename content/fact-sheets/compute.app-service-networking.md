# Configure networking settings for an App Service

## Key concepts

- App Service splits networking into inbound (requests to your app) and outbound (calls from your app); a feature built for one direction never solves the other direction's problem. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Multitenant plans use the Free, Shared, Basic, Standard, Premium, PremiumV2, PremiumV3, and PremiumV4 SKUs; an App Service Environment (ASE) is single-tenant, runs inside your virtual network, and uses Isolated SKUs. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Inbound options are app-assigned address, access restrictions, service endpoints, and private endpoints; outbound options are virtual network integration, gateway-required virtual network integration, and Hybrid Connections. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Virtual network integration is outbound-only: it reaches resources in and through a virtual network, but it never grants inbound private access to your app, which requires a private endpoint. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Access restrictions behave like a firewall: allow and deny rules are evaluated on the App Service front ends, which sit upstream of the workers running your code. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- A private endpoint gives your app a private IP from your virtual network over Azure Private Link, and only the app bound to that private endpoint is reachable across it. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Hybrid Connections tunnels outbound TCP to one host and port per connection, commonly to on-premises targets, doesn't depend on an Azure virtual network, and suits apps that open few connections. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Out of the box an app accepts internet traffic and reaches only internet-hosted endpoints, and networking features aren't available for apps deployed through Azure Arc. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))

## Settings and limits

- Regional virtual network integration requires Basic, Standard, Premium, Premium v2, Premium v3, or Premium v4, supports TCP and UDP, and works for Web Apps, Function Apps, and Logic Apps. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- The integration needs a dedicated, unused IPv4 subnet of `/28` or larger, and the virtual network must sit in the same region as the app. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- An App Service plan supports at most two virtual network integrations; apps in the plan can share one integration, but each app has only one active integration at a time. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Subnet capacity: five IPs are consumed at creation, one per plan instance, and scaling temporarily doubles usage; a `/26` covers one multitenant plan's maximum scale, and the portal requires `/27` for new subnets but accepts `/28`. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Multi plan subnet join (MPSJ) lets several plans share one subnet and needs `/26` or larger; the plans must sit in one subscription, while the subnet may be in another. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Windows Containers consume one extra subnet IP per app per plan instance, so four apps on ten instances need 50 IPs; each core provides three networking units, one for the worker and one per connection. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- `WEBSITE_VNET_ROUTE_ALL` routes all outbound traffic through the integration; when it's off, only RFC1918 private traffic and service-endpoint traffic enters the virtual network, while internet traffic leaves directly from the app. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Site properties override app settings and can be audited with Azure Policy, so Microsoft recommends them; other routing app settings are `WEBSITE_CONTENTOVERVNET` and `WEBSITE_PULL_IMAGE_OVER_VNET`. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Configuration traffic (content share, container image pull, backup/restore, managed identity tokens, Key Vault references) follows the public route by default, so each option must be switched to use the integration. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- The instance's integration-subnet IP appears as `WEBSITE_PRIVATE_IP`; its value can change, so allow the whole subnet range. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Configuring the integration needs `Microsoft.Network/virtualNetworks/read`, `Microsoft.Network/virtualNetworks/subnets/read`, `Microsoft.Network/virtualNetworks/subnets/write`, and `Microsoft.Network/virtualNetworks/subnets/join/action` on the subnet or above; write access is needed only when the subnet isn't yet delegated. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- An app can hold up to 512 access restriction rules. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- The unmatched rule always sits last: with no rules at all, unmatched traffic is allowed, but once one rule exists the default flips to deny, and you can explicitly choose allow or deny. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- Rules are evaluated in priority order; rules sharing a priority are evaluated in the order the Azure Resource Manager API returns them and the portal lists them before sorting. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- **App access** is `Disabled` or `Enabled`; when unset (`null`) access is enabled unless a private endpoint exists, which flips the default to disabled. The ARM property is `publicNetworkAccess`, and changing it restarts Linux sites. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- The main site and the advanced tools site (scm/kudu) each keep their own rule collection and unmatched rule, and a setting lets the advanced tools site reuse the main site's rules. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- Multi-source rules combine up to eight IP ranges or eight service tags; any rule can filter HTTP headers with up to eight values each, using `X-Forwarded-For`, `X-Forwarded-Host`, `X-Azure-FDID`, or `X-FD-HealthProbe`. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- `AnyVnets` can replace the IP range in an existing rule to allow any service-endpoint-enabled subnet, but the portal can't create such a rule directly. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- Inbound App Service addresses are covered by the `AppService` service tag and management addresses by `AppServiceManagement`; no tag covers outbound addresses, and PremiumV4 apps don't expose outbound IPs. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Inbound ports in the multitenant service can't be blocked: 80 and 443 for HTTP/HTTPS, 454 and 455 for management, 21, 990, and 10001-10300 for FTP/FTPS, 4020, 4022, and 4024 for remote debugging, 8172 for Web Deploy, and 7654 and 1221 for infrastructure; port 445 (SMB) is blocked by default. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))

## Compare and choose

- To restrict inbound traffic to known IP addresses, address ranges, or service tags, choose access restrictions, which filter traffic before it reaches the worker. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- To restrict inbound traffic to chosen virtual network subnets in the multitenant service, choose service endpoints with access restriction rules, because IP-based rules only handle VNet ranges inside an ASE. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- To expose an app on a private IP in your virtual network, choose a private endpoint; an ILB ASE provides single-tenant private hosting for many apps. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- For outbound calls to virtual network resources in the app's region, choose regional virtual network integration; for other regions, peer the integrated network. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- For outbound calls to on-premises or disconnected private networks, choose Hybrid Connections, which opens just one host and port per connection. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- To reach service-endpoint-secured or private-endpoint-enabled services, integrate the app, enable the service endpoint on the destination for the integration subnet, and ensure DNS resolves the private endpoint's IP. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- To secure or steer outbound traffic, pair virtual network integration with NSGs to block traffic, route tables (UDRs) to send it via firewalls, and a NAT gateway for a dedicated outbound IP and SNAT relief. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- To hide an API tier behind a front-end app, service endpoints are simpler but protect only the API, whereas private endpoints add a subnet and top-level resource yet prevent data exfiltration from the front end. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- For WAF protection or load balancing, pair Application Gateway with service endpoints or private endpoints; use Azure Front Door with access restrictions for multi-region load balancing. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- For an app-specific inbound address or IP-based SSL, choose an app-assigned address, whose traffic still travels through the scale unit's shared front ends. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Prefer regional virtual network integration over gateway-required integration, which is Windows-only, uses a point-to-site VPN, can't use ExpressRoute-connected virtual networks, and mainly helps with another region or a classic virtual network. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- Choose an ASE for single-tenant hosting, much larger scale, private CA client certificates, or forced TLS 1.2 across all apps; its subnet rules hit every app, and it carries higher cost, slower scaling, and external dependencies. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/networking-features))
- To block all public traffic, set **App access** to `Disabled`; to deploy through a private endpoint, keep public app access enabled and set the advanced tools site's unmatched rule to deny. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- To allow only one Azure Front Door instance, combine the `AzureFrontDoor.Backend` service tag with an `X-Azure-FDID` header filter holding that instance's GUID. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))

## Gotchas

- Access restrictions never filter traffic arriving over a private endpoint; control that path with NSGs on the private endpoint instead. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- Service-endpoint-based rules aren't supported on apps with a private endpoint or IP-based SSL (app-assigned address), and service endpoints also break remote debugging from those subnets. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- In an ILB ASE the default entry point is internal to the virtual network; enabling `publicNetworkAccess` only opens that internal address, while disabling it leaves private endpoints as the only access. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- Rules that block public access can also block log streaming, so allow the App Service IP addresses in the restriction list if you rely on that feature. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-access-restrictions))
- An NSG on the integration subnet filters outbound traffic only, its inbound rules don't apply, and it remains effective even when a route table is attached to the same subnet; route tables and NSGs affect only traffic actually routed through the integration and never replies to inbound requests. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Windows apps fail to connect when the destination IP matches an App Service worker infrastructure range, because Windows treats it as local; avoid overlapping destination subnets and remember the app can move workers during scaling or maintenance. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- The integration subnet can't have service endpoint policies enabled; disconnect the integration before deleting the virtual network, and you can't change an app's or plan's subscription while integration is active. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- A global Azure Storage account can fail for VNet-integrated apps when all-traffic routing is on and no service endpoints, private endpoints, or UDRs exist; fix it with a service endpoint, a private endpoint, or an account in the same region. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Outbound SMTP on port 25 works only when routed through the integration, and virtual networks or subnets created before 1 August 2022 need a temporary configuration change to sync the subscription setting. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Unsupported through virtual network integration: drive mounting, Windows Server Active Directory domain join, NetBIOS, Docker Compose, database backup, and App Service Logs to a private storage account (use Diagnostics Logging with Trusted Services instead). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- With all-traffic routing on, the source address stays one of the app's listed outbound addresses unless traffic passes through a firewall or NAT gateway, which then supplies the source IP. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- Disconnecting from a virtual network restarts the app but leaves the subnet intact, and can leave an orphaned Service Association Link that blocks subnet updates or deletion until it's purged. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
- A virtual network kept in another subscription needs that subscription registered for the `Microsoft.Web` resource provider. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration))
