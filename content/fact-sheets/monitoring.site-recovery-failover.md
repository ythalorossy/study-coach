# Perform a failover to a secondary region by using Site Recovery

## Key concepts

- **Azure Site Recovery** gives Azure VMs disaster recovery: source VMs replicate continuously to a secondary region, and on an outage you fail over to that secondary region and run the workload there. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- A failover creates the VM in the target resource group, target VNet, target subnet and target availability set, and you may use any recovery point during the failover. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- After failing over, you **Re-Protect** the VM in the secondary region so it replicates back to the primary, and then fail back once the primary is healthy. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Enabling replication auto-installs the **Site Recovery Mobility service extension** on the VM; the extension registers the VM with the service and continuous replication starts. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Disk writes go immediately to the **cache storage account** in the source region; Site Recovery processes that cached data and sends it to the target storage account or the replica managed disks. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Crash-consistent recovery points are generated every five minutes by default and that interval can't be modified; app-consistent recovery points follow the frequency set in the replication policy. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- A crash-consistent snapshot captures only what was on disk at that instant, with nothing from memory, so it doesn't guarantee consistency for the OS or for applications. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- An app-consistent snapshot adds in-memory data and in-flight transactions and uses VSS with the copy-only (`VSS_BT_COPY`) method, which doesn't change SQL Server transaction log backup time or sequence number. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Recovery points are built from those snapshots and are kept for the period defined by recovery point retention in the replication policy. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Source VMs must use managed disks, and a cache storage account must sit in the source network; replication needs outbound connectivity only and never inbound access to the VM. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- A **replication group** bundles VMs so they fail over to shared crash-consistent and app-consistent recovery points, at the cost of workload performance. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Site Recovery can create the target resources for you when you enable replication, or you can create and customize them yourself. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))

## Settings and limits

- The default **recovery point retention** in a new replication policy is one day (24 hours); keeping recovery points longer can raise storage cost. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- The default **app-consistent snapshot frequency** is zero hours, meaning app-consistent snapshots are disabled. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Set the app-consistent snapshot frequency below the retention window; with the default 24-hour retention, use a frequency under 24 hours. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Default **target subscription** is the source subscription; Site Recovery creates the target resource group in the target region with an `asr` suffix, and it can be in any region except the source. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- The target VNet and subnet are created with an `asr` suffix, and a network mapping is made between source and target VNets in both directions. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Replica managed disks are copies of the source disks with the `-ASRReplica` suffix; their **Disk state** should be `ActiveSAS`, and they automatically carry a tag with the `ASR-ReplicaDisk` prefix. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- For a source VM in an availability set, an existing target availability set is reused; otherwise Site Recovery creates one with the `asr` suffix. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- The target VM **SKU** defaults to the source SKU or the next best available one, and the dropdown only shows SKUs of the same family (Gen 1 or Gen 2). ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Target settings such as resource group, target name and SKU can be edited after replication is running, but the availability type (single instance, set or zone) cannot be changed without disabling replication, editing, and re-enabling. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Virtual machines with Premium SSD v2 disks require **High Churn** and a Premium Storage Account for the cache. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Commercial-cloud URL allow-list: `*.blob.core.windows.net` (storage), `login.microsoftonline.com` (Microsoft Entra ID), `*.hypervrecoverymanager.windowsazure.com` (replication), `*.servicebus.windows.net` (monitoring and diagnostics), `*.vault.azure.net` (Key Vault), `*.automation.ext.azure.com` (Azure Automation). ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Government-cloud equivalents: `*.blob.core.usgovcloudapi.net`, `login.microsoftonline.us`, `*.hypervrecoverymanager.windowsazure.us`, `*.servicebus.usgovcloudapi.net`, `*.vault.usgovcloudapi.net` and `*.azure-automation.us`. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Network Security Group rules must allow outbound HTTPS on port 443 in both source and target regions, using service tags `Storage.<region-name>`, `AzureActiveDirectory`, `EventHub.<region-name>`, `AzureSiteRecovery`, `AzureKeyVault` and `GuestAndHybridManagement`. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Members of a replication group communicate with each other over port 20004, so no firewall appliance may block it; on Linux you open that outbound port manually. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- The **Failover** pane offers four recovery point choices: **Latest processed**, **Latest**, **Latest app-consistent** and **Custom**. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Custom** is available only when you fail over a single VM and are not using a recovery plan. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Shut down machine before beginning failover** asks Site Recovery to try shutting the source VMs down first to reduce data loss, and the failover continues even if that shutdown attempt fails. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Commit** completes the failover: it deletes all available recovery points for that VM in Site Recovery and the recovery point can no longer be changed. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- To use a different recovery point after failover, choose **Change recovery point** on the VM **Essentials** page. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Re-Protect** on the VM **Overview** page starts reverse replication (secondary to primary); it sends the initial data and then deltas, and resources marked as new are created by Site Recovery. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Re-Protect requires the VM status to be **Failover committed**, the primary region to be available, and permissions to create VMs in that primary region. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))

## Compare and choose

- **Latest processed** restores from the newest recovery point Site Recovery has already processed, spends no time processing, and therefore gives the lowest RTO; its time stamp is shown. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Latest** processes all data already sent to Site Recovery and creates a recovery point for each VM before failing over, giving the lowest RPO because all replicated data is included. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Latest app-consistent** fails over to the newest app-consistent recovery point and shows its time stamp; choose it when application-level consistency outweighs speed. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- **Custom** fails over to a recovery point you pick, and is available only when you fail over a single VM without a recovery plan. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Crash-consistent points are enough for OS replication and for servers such as DHCP and print servers, and most apps recover well from them; app-consistent points are slower and heavier on app performance, so reserve them for workloads that need them. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Run a disaster recovery drill (test failover) before a real failover to prove the setup works without touching production; for the real outage use **Failover**, then **Commit** only once the failed-over VM satisfies you. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Fail over to get running in the secondary region, re-protect to replicate back to the primary, and fail back to return the workload to the primary location. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Group VMs that must stay consistent into a replication group instead of failing them over individually, accepting the added performance impact. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- For zone-to-zone recovery, pick a logical target zone that maps to a different physical zone, because equal logical zone numbers don't mean equal physical zones across subscriptions or regions. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))

## Gotchas

- Don't select **Commit** until the failed-over VM is confirmed running and correctly sized, because commit deletes the recovery points permanently. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- A disk added after replication was enabled isn't covered by earlier recovery points, so the replication point displays something like "1 of 2 disks". ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Placement settings depend on target availability: verify that any capacity reservation supports the target VM size and zone, and check proximity placement group assignments, which may need manual reassociation after failover or reprotection. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- An alternative VM SKU recommendation can be offered when the original SKU isn't available in the target region, including during a test failover. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- Before failing over, confirm the VM is protected and healthy, runs a supported Windows or Linux OS, and meets the compute, storage and networking requirements. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-tutorial-failover-failback))
- The availability type can't be changed while replication is running; the only route is disable replication, modify the setting, then re-enable it. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- With the default app-consistent snapshot frequency of zero hours there are no app-consistent recovery points to pick, and any frequency you do set must stay under the retention period. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Source-region Network Security Group rules must permit outbound replication traffic; build them in a test environment before production, and prefer service tags over individual IP addresses because Microsoft updates service tags over time. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- Key Vault outbound access is needed only to enable replication for ADE-enabled VMs via the portal, and Azure Automation outbound access only for portal-driven auto-upgrade of the mobility agent. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- The cache storage account lives in the source network and buffers changes, which keeps the impact on production applications running on the VM minimal. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
- In the target region, make sure you can create VMs and that the subscription has enough resources for the VM sizes required after failover. ([Learn](https://learn.microsoft.com/en-us/azure/site-recovery/azure-to-azure-architecture))
