# Configure service endpoints for Azure platform as a service (PaaS)

## Key concepts

- Service endpoints give a virtual network a direct, optimized path to supported Azure PaaS services over the Microsoft Azure backbone, so the vnet's private address space identifies the traffic and no reserved public IPs are needed. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Endpoints are switched on per service and per subnet (not per vnet or per VM); one subnet can carry several service endpoints at the same time, and every compute instance in that subnet uses them. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-restrict-network-access-to-resources))
- The service you pick in the subnet's **Services** list is identified by its Microsoft provider tag, for example **Microsoft.Storage**, **Microsoft.Sql**, **Microsoft.KeyVault**, **Microsoft.AzureCosmosDB**. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- After an endpoint is enabled, traffic to that service leaves the VM with its private IPv4 address instead of its public IPv4; open TCP sessions to the service are closed during the switch. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Azure adds a more specific default route per service address prefix with next hop type `VirtualNetworkServiceEndpoint`; that route wins over any user-defined route or BGP route matching the same prefix. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- DNS is untouched: service hostnames still resolve to the service's public IP addresses; only the path and the source address of the traffic change. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Because vnet private ranges can overlap, the endpoint is what lets the service recognize your vnet uniquely, so a virtual network rule can lock the PaaS resource to that vnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Service endpoint policies are the companion feature: they filter vnet egress over an endpoint and, for Azure Storage, permit only named storage accounts. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))

## Settings and limits

- Generally available service tags (each in the regions where its service is available): **Microsoft.Storage**, **Microsoft.Storage.Global**, **Microsoft.Sql**, **Microsoft.AzureCosmosDB**, **Microsoft.KeyVault**, **Microsoft.ServiceBus**, **Microsoft.EventHub**, **Microsoft.Web**, **Microsoft.CognitiveServices**, **Microsoft.ContainerRegistry**; **Microsoft.Sql** also serves Synapse Analytics dedicated SQL pools and Azure Database for MariaDB. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Permissions: write access on the virtual network lets you turn endpoints on; securing a service resource to the vnet additionally needs `Microsoft.Network/virtualNetworks/subnets/joinViaServiceEndpoint/action` on the subnets being added — built-in service administrator roles include it and custom roles can add it. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Scope: the vnet and the PaaS resource may be in the same or different subscriptions, and some services (Azure Storage, Azure Key Vault) also work across different Microsoft Entra ID tenants. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Region rule: Azure SQL endpoints apply only to traffic inside the vnet's region, so the vnet must sit in the same region as the SQL resource; every other supported service can be secured from a vnet in any region. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Limits: one vnet can be associated with up to 500 different subscriptions and regions per supported service that has active virtual network rules, while the total number of service endpoints in a vnet is unlimited. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Pricing: no extra charge for endpoints or endpoint policies; the normal Azure service price list applies. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Endpoint policies are generally available for Azure Storage in all global regions and may only be deployed on ARM-deployed virtual networks that are in the same region and subscription as the policy. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Endpoint policy limits: `ServiceEndpointPoliciesPerSubscription` 500, `ServiceEndpointPoliciesPerSubnet` 100, `ServiceEndpointPoliciesPerVirtualNetwork` 100, `ServiceResourcesPerServiceEndpointPolicyDefinition` 200. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Policy definition shape: `name`, `description`, `service` (**Microsoft.Storage**), `resourceGroup`, a `serviceResources` array of resource IDs, type `Microsoft.Network/serviceEndpointPolicies/serviceEndpointPolicyDefinitions`; allow-list granularity is a whole subscription `/subscriptions/subscriptionId`, a resource group `/subscriptions/subscriptionId/resourceGroups/resourceGroupName`, or one account `/subscriptions/subscriptionId/resourceGroups/resourceGroupName/providers/Microsoft.Storage/storageAccounts/storageAccountName`. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- On the storage account set **Public network access** to **Enabled from selected virtual networks and IP addresses**, then in **Virtual networks** choose **+ Add existing virtual network** and pick the subscription, vnet and subnet, and save. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-restrict-network-access-to-resources))
- NSG pattern for a storage-only subnet: outbound rule **allow-storage-all** (source service tag **VirtualNetwork**, destination service tag **Storage**, port **445**, protocol **Any**, action **Allow**, priority **100**) plus **deny-internet-all** (destination service tag **Internet**, port **\***, action **Deny**, priority **110**) that overrides the built-in allow-all outbound rule; then associate the NSG to the subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-restrict-network-access-to-resources))

## Compare and choose

- Service endpoint vs private endpoint: a service endpoint keeps the service's public IP and routes vnet traffic privately over the backbone; a private endpoint (Azure Private Link) places a network interface and a dedicated private IP for the service in your vnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Microsoft recommends Azure Private Link and private endpoints for secure, private access to PaaS; classic service endpoints remain the simpler, lower-management option, and standard service endpoints (public preview for Storage, Key Vault, SQL preview, Cosmos DB preview) extend them with network identifiers and network security perimeter integration for large-scale centralized control across many vnets. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Service tags in NSGs vs endpoint policies: NSG service tags limit egress to a service region but still allow any account inside it; policies name exact accounts and deny everything else, giving finer data-exfiltration control. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- No policy vs policy: with no policy attached, a subnet that has the Storage endpoint can reach every storage account; once a policy is attached, only the resources it lists are reachable from compute in that subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Several policies on one subnet are unioned — resources named in any one of them are allowed, all others denied — and because policies are allow-lists, every dependency of your app must be listed explicitly. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Applying a Storage endpoint policy upgrades the Storage service endpoint scope from regional to global, so all Storage traffic from that subnet is secured over the endpoint and the policies themselves apply globally. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- To inspect Azure service traffic, deploy a network virtual appliance, enable the endpoint on the appliance's subnet and secure the PaaS resource to that subnet only, because endpoint routes bypass forced tunneling. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))

## Gotchas

- Plan the cutover: source addresses flip from public to private IPv4, so service firewall rules built on your vnet's public IPs stop working, and there can be a temporary interruption to service traffic while an endpoint is added or removed. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Endpoint policies deny anything not on the allow-list, including classic storage accounts, which can never be listed — avoid policies for traffic that must reach classic accounts. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Managed storage accounts are not supported by endpoint policies and are denied by default when a policy sits on the subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Managed Azure services other than Azure SQL Managed Instance are unsupported by endpoint policies; that covers shared-subnet ones such as Azure Batch, Application Gateway, VPN Gateway, Azure Firewall and Microsoft Entra Domain Services, plus dedicated-subnet ones such as App Service Environment, Redis Cache and API Management. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Policies only filter traffic originating in the subnets they are attached to; on-premises traffic needs appliances or firewalls, and on-premises access to a vnet-secured resource requires adding your NAT or ExpressRoute public IPs to that resource's IP firewall. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- A policy only takes effect on a subnet where the matching service endpoint (for example **Microsoft.Storage**) is already enabled, and enabling an endpoint on an existing populated subnet can disrupt the workloads in it. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-restrict-network-access-to-resources))
- In peered or connected vnets, enable the endpoint on every subnet individually and attach policies to each vnet separately — there is no inheritance across the peering. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoint-policies-overview))
- Storage endpoint routing changes do not affect VM disk traffic for managed or unmanaged disks (disk I/O, mount and unmount); Storage network rules can still restrict REST access to page blobs. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-service-endpoints-overview))
- Verification is manual: there is no centralized logging for endpoint policies, so check service diagnostics (source IP should be the vnet private IP), effective routes, NSG flow logs and storage logs; a VM in a subnet without the endpoint fails with `mount error(13): Permission denied`. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/tutorial-restrict-network-access-to-resources))
