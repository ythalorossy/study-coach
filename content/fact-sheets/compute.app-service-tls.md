# Configure certificates and Transport Layer Security (TLS) for an App Service

## Key concepts

- TLS certificates (formerly called SSL certificates) protect incoming traffic in App Service: they encrypt data in transit, authenticate the app through trusted certificates, and stop tampering during transmission. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- Two separate steps are needed to serve HTTPS on a custom domain: the certificate must exist on the app, and a binding must attach that certificate to the domain — adding a certificate alone never secures the domain. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- A domain with a binding shows state **Secured** on the **Custom domains** page, but App Service never checks whether that certificate is self-signed or expired, so browsers can still show errors. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- TLS is terminated at the App Service network load balancers, so HTTPS requests arrive at your worker as unencrypted HTTP; read `X-Forwarded-Proto` in code, and the `x-appservice-proto` header (value `http` or `https`) for the original protocol. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- Private certificates are stored in a deployment unit (internally a *webspace*) keyed to the plan's resource group, region and OS, and are shared with other apps in that same combination; limits are 1,000 private certificates per webspace and 1,000 public certificates per App Service plan. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- The free App Service managed certificate is issued by DigiCert, renews automatically, and updates all of its bindings with the new certificate as long as your prerequisites stay the same; issuance and renewal changed in some scenarios on July 28, 2025, so check the ASMC blog post. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- For some domains you must create a DNS Certification Authority Authorization record with the value `0 issue digicert.com` to let DigiCert issue or renew the managed certificate. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Mutual TLS (mTLS) is supported on both Linux and Windows App Service plans: clients present certificates validated against a trusted CA chain you configure, and client certificate details are exposed to code through request headers. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- End-to-end (E2E) TLS encryption also encrypts front-end-to-worker traffic inside Azure, not just client-to-front-end traffic; it is offered on Premium plans (recommended for new deployments) and legacy Standard plans. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))

## Settings and limits

- Supported inbound TLS versions are **TLS 1.3** (fully supported), **TLS 1.2** (the default minimum for new web apps and their SCM endpoints) and the legacy **TLS 1.1** / **TLS 1.0**, which are no longer considered secure. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- Set the floor with **Minimum Inbound TLS Version** in the portal, Azure CLI or an ARM template; to force TLS 1.3 set it to **TLS 1.3**, whose cipher suites are fixed at `TLS_AES_256_GCM_SHA384` and `TLS_AES_128_GCM_SHA256`. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- **Minimum TLS Cipher Suite** is supported on Basic SKU or higher on multitenant App Service; the list and its priority order are fixed — you can't add or reorder suites, and choosing one blocks every less-secure suite rather than only the selected ones. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- In an App Service Environment, the `FrontEndSSLCipherSuiteOrder` cluster setting controls cipher order; it must still include both TLS 1.3 suites, and you must restart the front end after changing it. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- Tier requirements differ by task: private certificates need an **App Service plan** on Basic, Standard, Premium or Isolated, while creating a TLS binding for a custom domain needs Basic, Standard or Premium. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- **SNI SSL** lets you add many bindings and many TLS/SSL certificates on one shared IP for different domains; all modern browsers (Edge, Chrome, Firefox, Opera) support Server Name Indication. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- **IP based SSL** allows only one binding and one certificate, on a dedicated public IP that App Service creates for you, and it is supported only on the Standard tier or higher. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- After an IP-based SSL binding, repoint the domain's A record to the new dedicated IP shown on the **Custom domains** page, and point any `*.azurewebsites.net` CNAME at `sni.<app-name>.azurewebsites.net` instead of the plain host name. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- Free managed certificate limits: no wildcard certificates, not exportable, no private DNS support, not supported in App Service Environment, and unusable as a client certificate by thumbprint (that capability is planned for deprecation and removal). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Free managed certificate limits, continued: only alphanumeric characters, dashes (-) and periods (.) are allowed, custom domains can be up to 64 characters, an A record must point to the app's IP, and root domains integrated with Azure Traffic Manager are excluded. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Only one managed certificate can be created per supported custom domain; for a root domain such as contoso.com the app must have no **IP restrictions** configured and must be reachable from the internet, because issuance and renewal depend on it. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Uploaded or imported private certificates must be a password-protected PFX containing the full chain (intermediates plus root), carry an extended key usage for server authentication (OID `1.3.6.1.5.5.7.3.1`), and be signed by a trusted CA to be usable in a TLS binding. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- To import from Key Vault, give the App Service resource provider `Microsoft.Web` read access by assigning the **Key Vault Certificate User** role to service principal app ID `abfa0a7c-a6b6-4736-8310-5855508787cd` (Azure Cloud) or `6a02c803-dafd-4136-b4c3-5a6f318b4714` (Government), for example with `az role assignment create --role "Key Vault Certificate User" --assignee "abfa0a7c-a6b6-4736-8310-5855508787cd" --scope "/subscriptions/<subscription-id>/resourcegroups/<resource-group-name>/providers/Microsoft.KeyVault/vaults/<key-vault-name>"`. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- App Service force-redirects HTTP to HTTPS by default; the redirect and the minimum TLS version are changed in the app's general settings, and the built-in Azure Policy definition "App Service apps should use the latest TLS version" audits the minimum TLS version of your apps. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- Binding workflow in the portal: **Custom domains** > **...** next to the domain > **Add binding**, then pick an existing **Certificate** or a **Source** (**Create App Service Managed Certificate**, **Import App Service Certificate**, **Upload certificate (.pfx)**, **Import from Key Vault**), choose **TLS/SSL type**, run **Validate**, then **Add**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))

## Compare and choose

- Free App Service managed certificate: zero cost and fully managed with automatic renewal, but it cannot be exported, cannot be a wildcard and is unusable outside App Service — the default pick for a simple custom domain. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- App Service certificate (ASC): paid, issued by GoDaddy, kept in your key vault, exportable and usable outside App Service — choose it when you need wildcard domains or portability. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- Bring your own certificate (BYOC): upload your own PFX under **Bring your own certificates (.pfx)** with a **Certificate password** and **Certificate friendly name** — pick it when you already own the certificate or need your own CA. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Import from Key Vault: keeps the PKCS12 certificate in your vault as the source of truth and lets App Service sync the renewed version automatically within 24 hours and update the binding — best when your certificates already live in Key Vault. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Public certificate (`.cer`): never used to secure custom domains; upload it via **Public key certificates (.cer)** when your code must present a public certificate to reach a remote resource. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- SNI SSL versus IP based SSL: use SNI SSL for multitenant apps and many domains sharing one IP; use IP based SSL only when a client needs a dedicated public IP, and remember it costs you Standard tier or higher. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- Manage cipher preferences in exactly one place: if your App Service Environment already uses `FrontEndSSLCipherSuiteOrder`, don't also enable **Minimum TLS Cipher Suite** on the app, because conflicting configurations can result. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))
- Azure-managed domains such as `*.azurewebsites.net` are already secured with default certificates, so no certificate or binding work is needed for them; only custom DNS names require binding. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/overview-tls))

## Gotchas

- Renew a certificate without downtime: upload the new certificate, bind it to the domain **without deleting** the old binding (use **Update binding** from the **...** menu on the **Custom domains** page), then delete the old certificate. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- Deleting a binding can change your app's inbound IP address even when the binding was IP based, which is exactly the risk when renewing a certificate already used in an IP-based SSL binding. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Certificate validation errors in browsers usually mean a self-signed certificate or a PFX exported without the intermediate certificates — merge the chain into `mergedcertificate.crt` before exporting. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-bindings))
- The root issuer, public key and private key of a managed certificate can change at any time outside your control, so never pin or hard-depend on it; use another certificate method if you need pinning. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- OpenSSL v3 changed the default PFX cipher from 3DES to AES256, which App Service doesn't accept; export with `openssl pkcs12 -export -out myserver.pfx -inkey <private-key-file> -in <merged-certificate-file> -keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg SHA1` (OpenSSL v1 defaults work as-is). ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- A private CA certificate can't be used for inbound TLS in multitenant App Service — that requires App Service Environment v3; the same applies to loading a CA into the platform trusted root store. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Outbound calls with a private CA client certificate are supported for Windows container apps in multitenant App Service, and for both code-based and container-based apps in App Service Environment v3. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- Never delete the Key Vault permissions granted to App Service, or the app stops syncing with the latest vault certificate version; if the vault firewall blocks public access, enable **Allow trusted Microsoft services to bypass this firewall**. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
- In ARM templates and Bicep you normally assign **Key Vault Certificate User** with the service principal *object* ID of the enterprise application; the application (client) ID works with tooling such as the Azure CLI role assignment command. ([Learn](https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate))
