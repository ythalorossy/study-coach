# Create a Recovery Services vault

## Key concepts

- A Recovery Services vault is an Azure storage and management entity that keeps recovery points over time along with the backup policies for protected VMs; you use it for on-demand backups, for restores, and for creating backup policies ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- One vault can hold backup data for Linux or Windows IaaS VMs, SQL Server in Azure VMs, System Center DPM, the Windows Server and Azure Backup Server agents, and other hybrid assets, and it gives one central portal for Azure Backup and Azure Site Recovery jobs, alerts, metrics, health, and reports ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Vaults use the Azure Resource Manager model, support Azure RBAC for fine-grained control of backup and restore access, and come with three Azure Backup built-in roles for managing recovery points ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- With soft delete, a backup that is removed — deliberately or by accident — remains recoverable for 14 extra days at no charge, so the backup item can be brought back without losing data; Enhanced soft delete lets you choose the retention period and keeps soft delete permanently on, so it cannot be turned off by a malicious actor ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Cross Region Restore (CRR) is switched on at vault level and restores replicated data in the Azure paired secondary region whenever you choose, for audit, compliance, or a regional outage, without waiting for Azure to declare a disaster ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Cross-tenant restore (preview) maps a source vault to a target vault so data can be restored into a different tenant, which helps recovery from tenant lockout or ransomware attacks ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Backup data is kept in a Microsoft-managed Azure subscription and tenant, so guests and external users have no direct access to the storage or its contents, protecting existing backups even if the production environment is compromised ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Azure Backup automatically provisions and manages the vault's storage, so you do not create or specify a storage account for backup data; immutable vaults additionally stop recovery points being deleted before their backup-policy expiry, and immutability can be made irreversible against ransomware ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Azure Advisor gives hourly recommendations for VMs that have no backup, lets you snooze recommendations, and can enable backup inline by naming the vault plus the backup policy that defines schedule and retention; its advice is grouped under High Availability, Security, Performance, and Cost ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))

## Settings and limits

- Portal creation runs **Resiliency** > **Vault** > **+ Vault**, then **Recovery Services vault** > **Continue**, and **Review + create** > **Create** finishes it; watch the **Notifications** area and **Refresh** the list if the new vault doesn't appear ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- **Subscription** selects the target subscription, with several choices shown only when the account is linked to more than one; **Resource group** accepts **Use existing** or **Create new** with a name ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- The **Vault name** must be unique within the Azure subscription, be 2 to 50 characters long, start with a letter, and contain only letters, numbers, and hyphens ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- The **Region** must match the region of the data source the vault protects; for data sources in several regions, create one vault per region and create the vault in the first location before any other ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- **Storage replication type** in **Backup Configuration** offers **Geo-redundant**, **Locally-redundant**, or **Zone-redundant**, followed by **Save**; the default is **Geo-redundant** storage (GRS) ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- The **Cross Region Restore** toggle in **Backup Configuration** enables restore to the paired region and works only with the **Geo-redundant** (GRS) replication type ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- CRR supports VMs created through Azure Resource Manager, including encrypted VMs, and SQL Server or SAP HANA databases hosted on Azure VMs, restoring the VM, the disk, the database, or the database files; VMs from the classic deployment model are not supported ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- For vaults that have no private endpoint (preview), the Recovery Services agent is also covered, as are machines running on Ultra Disks; CRR adds extra charges, and backup items may need up to 48 hours before they can be used in the secondary region after it is switched on ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- CRR recovery point objective limits: in the worst case the secondary region trails the primary by 36 hours; the Standard policy holds the primary region RPO to 24 hours or less and secondary-region replication to 12 hours or less; the Enhanced policy improves the best achievable case while the worst case stays at 36 hours, and permissions are required to use CRR ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- **Cross Subscription Restore** is enabled in **Properties** with **Enable Cross Subscription Restore** > **Update**, restoring into a different subscription in the same tenant as the source; it currently applies to Azure VMs, to the SAP ASE and SAP HANA workloads hosted in Azure VMs, to SQL Server running in Azure VMs, and to Azure Files ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Encryption uses platform-managed keys by default with no action needed, and it applies to every workload backed up to the vault; customer-managed keys use RSA keys from an Azure Key Vault, where an AES 256-based DEK protects the data and the vault must be granted access to the key ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- To configure customer-managed keys: enable the vault's managed identity, assign permissions so the vault can reach the key in Azure Key Vault, enable soft delete and purge protection in that Key Vault, then assign the encryption key to the vault; afterwards you may disable the key or revoke access whenever needed ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- **Soft delete** is **Enabled** by default on newly created vaults, and both storage replication and security defaults should be reviewed before backups are configured; the vault's storage replication choice does not apply to Azure file share snapshot backup, because those snapshots stay in the file share's own storage account ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))

## Compare and choose

- Choose **Geo-redundant** (GRS) when Azure is the primary backup storage endpoint; it is the default and keeps a replicated copy in a paired region ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Choose **Locally-redundant** (LRS) when Azure is not the primary backup storage endpoint, to reduce storage costs while accepting lower regional durability ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Choose **Zone-redundant** (ZRS) when you need data availability without downtime in a region and guaranteed data residency ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Use CRR on a GRS vault for an on-demand secondary-region restore during drills, audit, compliance, or disaster response, instead of waiting for a Microsoft-declared disaster as GRS alone would require ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Keep platform-managed keys for zero-setup encryption; use customer-managed keys when you need control over the keys and the ability to revoke access, accepting that this must be set before protecting items and cannot be undone ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Use soft delete for the built-in 14 extra days of protection against accidental or malicious deletion; add Enhanced soft delete when you need a customized retention period and always-on protection that cannot be switched off ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-azure-recovery-services-vault-overview))
- Moving GRS to LRS while preserving data means stopping protection with retained data, keeping the existing recovery points in the GRS vault at ongoing cost, restoring only unexpired points from it, and creating an initial replica in the LRS vault; discarding the old data instead means deleting current protection and backup data from the GRS vault and reconfiguring backups in a new LRS vault ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- For an Azure VM on the preserve-data path, move the VM to another resource group so it counts as a different VM, and remember that a VM can be added to only one vault at a time ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))

## Gotchas

- Set the storage replication type before you configure any backup; afterwards the portal no longer offers the modify choice, and the documented workarounds are needed to change it ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Once protection starts for the first time, CRR cannot be reverted to GRS or LRS, so settle the replication model before protecting any item ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- Customer-managed key encryption cannot be enabled after items are protected and cannot be reversed once enabled, and the vault key can still be disabled or its access revoked later ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- A vault's region must match its data source, so plan one vault per region and create the first vault in the first location before creating another ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- If **Cross Region Restore** settings do not appear on **Backup Configuration** even with access to restricted paired regions, re-register the provider by opening the subscription's **Resource provider** pane and selecting `Microsoft.RecoveryServices` > **Re-register** ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
- The destructive GRS to LRS route needs soft delete turned off first and wipes the protected server's backup data and backup items for good, with no undo; any Azure file share, SQL Server instance, or SAP HANA server must be unregistered from **Backup Infrastructure** before it is backed up in the new vault ([Learn](https://learn.microsoft.com/en-us/azure/backup/backup-create-recovery-services-vault))
