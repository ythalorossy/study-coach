# Configure identity-based access for Azure Files

## Key concepts

- Identity-based authentication over SMB authorizes users with a directory identity instead of a storage account key and adds no extra service charge; it supports Windows, Linux and macOS clients, but NFS shares can't use it. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Three identity sources exist: **On-premises Active Directory Domain Services (AD DS)**, **Microsoft Entra Domain Services**, and **Microsoft Entra Kerberos**; only one can be configured per storage account, and it governs every file share in that account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Flow: the identity source validates the caller and returns a Kerberos ticket, the client attaches it to the request, and Azure Files authorizes from the ticket alone — it never receives the user's credentials. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Whichever source you pick, Kerberos must be enabled under **Authentication methods** in the storage account's SMB security settings. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Two gates must both be passed to reach data: a share-level Azure RBAC role and a Windows ACL at file or directory level; networking and DNS are configured separately. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- With AD DS or Entra Kerberos, only hybrid identities present both on-premises and in Microsoft Entra ID can be authorized, because share permissions target the Entra object while ACLs are enforced in AD — sync with Microsoft Entra Connect Sync or Cloud Sync. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Keyless SMB for applications and Azure compute should use a managed identity, a separate mechanism that can coexist with the three user identity sources. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- You can migrate an account to a different identity source later, but the switch briefly breaks identity-based access to all shares; the documented order meanwhile is share-level permissions, file/directory permissions, networking and DNS, then mounting. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))

## Settings and limits

- Recommended enablement uses the **AzFilesHybrid** module, which needs .NET Framework 4.7.2 or later, the latest `Az` and `Az.Storage` 8.1.0+ modules, and the Active Directory PowerShell module. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- `Join-AzStorageAccount` performs the equivalent of an offline domain join; `-SamAccountName` must be 20 characters or fewer (15 or fewer with NETBIOS restrictions) and is given without the trailing `$`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- `-DomainAccountType` takes **ComputerAccount** (default) or **ServiceLogonAccount**, and the object is created in the domain root unless `-OrganizationalUnitDistinguishedName` is supplied. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Least-privilege Azure permissions for the join: **Reader** on the resource group and **Contributor** on the storage account; an **Owner** or **Contributor** at subscription scope already qualifies. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Manually, create the AD password with `New-AzStorageAccountKey -KeyName kerb1` and read it with `Get-AzStorageAccountKey -ListKerbKey`; that key is for setup only and can't drive control- or data-plane calls. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Set the SPN `cifs/<StorageAccountName>.file.core.windows.net` with `Setspn -S`; for a user account also set a matching UPN with `Set-ADUser -UserPrincipalName cifs/<StorageAccountName>.file.core.windows.net@<UPN-suffix>`, then set the password to the `kerb1` value with `Set-ADAccountPassword`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Enable the feature with `Set-AzStorageAccount -EnableActiveDirectoryDomainServicesForFile $true` plus `-ActiveDirectoryDomainName`, `-ActiveDirectoryNetBiosDomainName`, `-ActiveDirectoryForestName`, `-ActiveDirectoryDomainGuid`, `-ActiveDirectoryDomainSid`, `-ActiveDirectoryAzureStorageSid`, `-ActiveDirectorySamAccountName` (no `$`) and `-ActiveDirectoryAccountType` (`Computer` or `User`). ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- AES-256 Kerberos is recommended and requires the AD object to be a computer account (default) or service logon account plus write access to `msDS-SupportedEncryptionTypes`; set it with `Set-ADComputer`/`Set-ADUser -KerberosEncryptionType "AES256"`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- AzFilesHybrid supports AES-256 only (service logon accounts from v0.2.5), pre-0.2.2 setups defaulted to RC4 and should be upgraded immediately — afterwards run `klist purge` and remount; a July 2026 Windows Server Update also flips the AD DS default from RC4 to AES-256, so staying on RC4 risks mount errors. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Computer account passwords rotate from the client machine (every 30 days by default) and never expire in AD, while service logon account passwords expire per domain policy — refresh before the maximum password age either way. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Verify with `$storageAccount.AzureFilesIdentityBasedAuth.DirectoryServiceOptions` and `.ActiveDirectoryProperties`; the AD identity representing the storage account never needs syncing to Microsoft Entra ID. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Disable it via **Data storage** > **Classic file shares** > **Identity-based access** > **Active Directory Domain Services (AD DS)** > **Configure** > the **Disable Active Directory for this storage account** checkbox > **Save**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- A default share-level permission is set on the storage account so it applies to every share inside it, and it starts as **None**, denying all file and directory access; enable it under **Step 2: Set share-level permissions** with **Enable permissions for all authenticated users and groups**, then choose a role. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- Share-level permission changes normally take effect within 30 minutes but can take longer, so wait for propagation before testing access. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))

## Compare and choose

- Pick AD DS when an existing on-premises domain is in place and clients can reach its domain controllers; pick Entra Domain Services for a managed domain in Azure; pick Entra Kerberos for cloud-first or mixed environments, Entra-joined clients, FSLogix profiles or macOS clients without domain-controller connectivity. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Entra Kerberos removes the domain-controller connectivity requirement, but Linux user authentication isn't supported with it, and hybrid identities still need traditional AD DS synced to Microsoft Entra ID, Entra-joined or hybrid joined clients, and an MFA exclusion for the storage account application. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Entra Domain Services creates the storage account identity automatically during enablement, lets all Microsoft Entra ID users (cloud-only or hybrid) authenticate, and manages sync from Microsoft Entra ID for you; non-Azure clients can't join the managed domain but can connect with explicit credentials if they reach its domain controllers. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview))
- Assigning share-level permissions to specific cloud-only identities works only with Entra Kerberos and only in public regions — elsewhere use a default share-level permission; for hybrid identities assign against the Entra-synced UPN such as `user1@contoso.com`, not the on-premises one. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- Use a default share-level permission when AD DS can't sync to Microsoft Entra ID, when the synced tenant differs from the share's tenant (multitenant), or when ACLs should do the enforcing; it's also the only route for computer accounts, sMSAs and gMSAs, which have no Entra identity for RBAC, and for unsynced users who belong to a synced AD DS group, because Azure Files reads group SIDs straight from the Kerberos ticket. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- With both a default permission and a specific assignment, the identity gets the higher one — a user with **Storage File Data SMB Share Reader** still gets **Storage File Data SMB Share Elevated Contributor** if that's the default. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- Role meanings: **Storage File Data SMB Share Reader** ≈ a read share ACL; **Storage File Data SMB Share Elevated Contributor** ≈ a change share ACL (adds modify-ACLs); **Storage File Data SMB Share Contributor** gives read/write/delete without changing ACLs; **Storage File Data Privileged Contributor** and **Privileged Reader** do the same but override existing ACLs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- ACL tooling depends on identity type: File Explorer, `icacls`, the portal and the `RestSetAcls` module all work for hybrid identities under Entra Kerberos, but only File Explorer and `icacls` work for AD DS and Entra Domain Services, and only the portal and `RestSetAcls` work for cloud-only identities. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- RBAC and NTFS permissions intersect rather than add: the most restrictive wins either way — RBAC Contributor plus NTFS Read yields read only, RBAC Reader plus NTFS Modify still yields read only, and NTFS None with any RBAC role means access denied. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- For ACL work prefer the Windows permission model: assign **Storage File Data SMB Admin**, mount with `net use Z: \\<StorageAccountName>.file.core.windows.net\<FileShareName>` (not PowerShell, or the share won't show in File Explorer or `cmd.exe`), and use `takeown` when an existing ACL blocks you; the role carries the `readFileBackupSemantics/action`, `writeFileBackupSemantics/action` and `takeOwnership/action` data actions, while a storage account key mount is the less secure fallback. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- Full Control ACL plus **Storage File Data SMB Share Elevated Contributor** (or an equivalent custom role) also lets you edit ACLs without the admin role or a key. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))

## Gotchas

- With a `User` account type, a mismatched UPN breaks Kerberos with error 1396 **The target account name is incorrect** and `KRB_AP_ERR_MODIFIED`; the UPN must match the SPN, especially after AES-256, and `Join-AzStorageAccount` sets it automatically so manual setups miss it. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Never sync users whose UPN contains `/`, spaces or other unsupported characters — that causes Microsoft Entra Connect errors; fix the UPN to something like `user@domain.com` or exclude the user with filtering rules. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- The AD PowerShell cmdlets require PowerShell 5.1 with administrator privileges; PowerShell 7.x and Azure Cloud Shell don't work, and `Debug-AzStorageAccountAuth` (AzFilesHybrid v0.1.2+) covers AD DS and Entra Kerberos but not Entra Domain Services. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Disabling AD DS leaves the computer or service logon account in AD as an orphan; deleting it isn't automatic. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable))
- Don't use `*` wildcards in custom role definitions — a wildcarded data action grants every current and future data action to everyone assigned the role, so list actions explicitly. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- `Move-OnPremSharePermissionsToAzureFileShare` converts only the root directory into RBAC assignments and grants the role equivalent to the root ACL, so users who are read-only at the root but writable below need manual RBAC fixes. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions))
- File Explorer and `icacls` fail for cloud-only identities — use the portal or `RestSetAcls`, for example `Add-AzFileAce ... -AccessRights Read,Synchronize -InheritanceFlags ObjectInherit,ContainerInherit`; neither is suitable when the client isn't domain joined or you run multiple AD forests, where `icacls <drive>: /grant <user-upn>:(f)` is the fallback. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- Portal ACL edits: **Deny** beats **Allow**, neither set means inherited, and changed inheritable permissions reach only future children — run `Restore-AzFileAclInheritance -Recursive` for existing items. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- ACLs on identities that aren't synced to Microsoft Entra ID aren't enforced under Entra Kerberos because the ticket lacks them, whereas AD DS does enforce them since its SIDs are in the ticket. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- Well-known principals differ in Azure Files: `BUILTIN\Administrators` is empty and nobody can be added, `BUILTIN\Users` matches `NT AUTHORITY\Authenticated Users`, and `NT AUTHORITY\SYSTEM` plus `CREATOR OWNER` entries still appear on the root. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
- **Storage File Data SMB Admin** isn't equivalent to a storage account key: a key mount gives immediate full access to everything, while the role only adds the `takeown` privilege and existing ACLs still govern normal file access. ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-configure-file-level-permissions))
