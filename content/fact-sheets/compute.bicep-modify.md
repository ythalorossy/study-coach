# Modify an existing Bicep file

## Key concepts

- Bicep is declarative, so the order of statements in the file does not change how a deployment is processed. When you revise an existing file you can add a `param`, `var`, `output`, `resource` or `module` in any position, even after the blocks that reference it. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- The top-level elements of a Bicep file are `metadata`, `targetScope`, `param`, `var`, `type`, `func`, `resource`, `module` and `output`, plus `#` directives and `@` decorators. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `targetScope` decides where the whole file deploys. If it is omitted the default is `resourceGroup`, so a resource-group-level file needs no scope declaration; the other accepted values are `subscription`, `managementGroup` and `tenant`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- Azure Resource Manager resolves parameter values before any deployment operation starts, and every parameter must declare exactly one data type such as `string`, `int`, `bool`, `object` or `array`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- A parameter may carry a default value, used whenever no value is supplied at deployment time. Defaults can be expressions (for example `resourceGroup().location`) or be built from another parameter, but never from a `var`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- A `var` stores a computed or repeated expression once and is reused by reference; variables can also take decorators such as `@description` and `@export`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- A resource declaration needs a symbolic name, a fully qualified type with an API version and a body of type-specific properties, for example `resource stg 'Microsoft.Storage/storageAccounts@2025-06-01' = { ... }`. The symbolic name is how the rest of the file reads values back from that resource. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- A child resource can either be nested inside the parent resource body or declared separately and tied to the parent with the `parent` property; the separate form needs the whole type path, for example `Microsoft.Storage/storageAccounts/fileServices/shares@2025-06-01`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- A module is another `.bicep` file (or an ARM JSON template) that the current file deploys. Modules are compiled into one ARM template that uses nested deployments, and the module's own `outputs` are read back through the module's symbolic name. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- `output` returns values from a deployment, for example `output storageEndpoint object = stg.properties.primaryEndpoints`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `type` declares a user-defined data type, including a union of literal values such as `'Standard_LRS' | 'Standard_GRS'`, and that type can then be used as the type of a `param`; `func` declares your own function, and Bicep's built-in functions are available without any import. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `for` creates many copies of a resource, module, variable, property or output from an array, an object or an integer range such as `range(0, storageCount)`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `if` marks a resource or module as conditional; the expression is evaluated during deployment and decides whether the item is created. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- Directives start with `#` and control diagnostics: `#disable-next-line` (next line only), `#disable-diagnostics` (whole file or until re-enabled) and `#restore-diagnostics`. At least one identifier must follow the directive, and identifiers such as `BCP138` or `no-unused-params` are case sensitive. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- Comments use `//` for a single line and `/* ... */` for a block of lines. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))

## Settings and limits

- A Bicep file can contain a maximum of **256** parameters. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- Parameter names must be valid Bicep identifiers: letters, digits and underscores only, with no periods or other special characters. ARM template JSON does allow periods, and the decompiler rewrites such names with underscores (for example `Security.Authentication.AAD.Tenant` becomes `Security_Authentication_AAD_Tenant`). ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- Within one scope a parameter may not share its name with a variable, a resource, an output or another parameter. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@allowed([ ... ])` lists the accepted values in an array and the deployment fails during validation if a different value is passed; it is allowed only on `param` statements. For an array-typed parameter the supplied value may be any subset of the listed values. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@minLength` and `@maxLength` constrain strings by character count and arrays by item count; `@minValue` and `@maxValue` constrain integers. All four limits are inclusive, and you can set either one or both of a pair. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@secure()` is valid only on `string` and `object` parameters, matching the ARM `secureString` and `secureObject` types; the value is then kept out of deployment history, the portal and command-line output. Numbers or arrays must be wrapped in a secure object or serialized as a secure string to be passed securely. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@description('...')` text becomes the tip shown for that parameter during a portal deployment and may use Markdown; `@metadata({ ... })` carries arbitrary custom properties such as `source` or `contact` and may also include a `description` property. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- Decorators sit in the `sys` namespace, so if your file already contains an item called `description` you must qualify the decorator as `@sys.description(...)`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@batchSize(int)` makes loop instances deploy one after another; without it resources and modules deploy in parallel, and the decorator is only valid on a `resource` or `module` that uses a `for` expression. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `@retryOn` accepts error-code strings plus an optional retry count of at most **10**, using exponential back-off. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- The module `name` property is optional: omit it and a GUID becomes the nested deployment name. A module symbolic name may contain a-z, A-Z, 0-9 and `_` but cannot start with a digit, and a module may not reuse the name of a parameter, variable or resource. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Without a `scope` property a module deploys at the parent's target scope. To change it, set `scope` to a scope object — the symbolic name of a resource group, subscription or management group, declared or marked `existing` — or to a result of the `resourceGroup()`, `subscription()`, `managementGroup()` or `tenant()` function; an arbitrary string is invalid. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Module paths come in three forms: public registry `br/public:<file-path>:<tag>` (equivalently `br:mcr.microsoft.com/bicep/<file-path>:<tag>`), private registry `br:<registry-name>.azurecr.io/<file-path>:<tag>`, and template spec `ts:<sub-id>/<rg-name>/<template-spec-name>:<version>`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Starting with **Bicep CLI v0.43.1** custom domains are rejected when referencing or restoring modules from Azure Container Registry, raising diagnostic **BCP446**. Only `*.azurecr.io`, `*.azurecr.cn`, `*.azurecr.us`, `mcr.microsoft.com`, `mcr.azure.cn` and `ghcr.io` pass the built-in hostname allowlist. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Version gates to remember: `@secure()` on module outputs requires Bicep 0.35.1 or later, and a user-assigned managed identity on a module requires 0.36.1 or later, though back-end services do not yet support that identity. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Template specs and registry modules are only usable by principals that hold the matching permissions, so sharing a module means also sharing access to its registry or template spec. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))

## Compare and choose

- `param` versus `var`: use a parameter for input that changes per deployment and can be supplied at deploy time; use a variable for values computed inside the file. Remember that a parameter default can never point at a variable. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- `@allowed` versus union type syntax: `@allowed` pins one `param` to a fixed value list, while a union such as `'A' | 'B'` can be used in a `type`, a `param` and an `output`, so choose the union when the same restriction must also apply to outputs or to properties of a user-defined type. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `@description` versus `@metadata`: `@description` is the human-facing help text surfaced in the Azure portal, `@metadata` is for machine-readable custom properties that are not worth putting in a description. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- Parameters versus outputs: parameters push values into a deployment, outputs push values back out of it; a module's values reach the parent file through its `outputs` property, for example `stgModule.outputs.storageEndpoint`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Module versus repeated inline resource block: a module encapsulates and reuses complex deployment logic across files, whereas inline resources suit small one-off definitions; a module is the only way to reuse code, and it is compiled into nested deployments. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Module registry versus template spec: only Bicep can deploy from the module registry and only from inside another Bicep file, while template specs can be deployed from the API, Azure CLI, Azure PowerShell and the Azure portal and can use `UiFormDefinition` for the portal experience. Bicep modules can also pull in extra artifacts with the `loadTextContent` and `loadFileAsBase64` functions, which template specs cannot package. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- Nested child resource versus top-level child with `parent`: nesting keeps the hierarchy visible in one block, while the top-level form is the right choice when the child must be referenced on its own or created in a loop. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- `targetScope` versus module `scope`: `targetScope` sets the default for the entire file, and a `scope` on a single module overrides it, which is how a subscription-scoped file deploys a module into a resource group. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- `if` versus `for`: `if` decides whether one instance is deployed, `for` produces many instances from a collection, and the two can be combined in one declaration such as `[for i in range(0, storageCount): if (i % 2 == 0) { ... }]`. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- Local path versus registry path: a local module path is relative to the current file and must use the forward slash `/`; the Windows backslash `\` is not supported, although paths may contain spaces. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))

## Gotchas

- Spaces and tabs carry no meaning in a Bicep file, but line breaks do. A reformat that moves `if (...)` or the opening brace onto the next line of a resource declaration will not compile. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- The `reference()` function and the `list*` functions read a resource's runtime state and therefore cannot appear in the parameters section, because parameters are resolved before deployment begins. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- The Bicep language has no `apiProfile` concept, so you cannot map one profile to a set of API versions per resource type. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- User-defined functions (`func`) are not generally available yet; only an experimental feature exists today. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- Some Bicep features require a matching change to the intermediate ARM template language, so in environments such as Azure Stack a feature can arrive later than it does in global Azure. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
- The `name` you give a module is the label of the nested deployment inside the compiled ARM template, so renaming it changes how that nested deployment appears in the deployment history. Deploying two modules with the same static name to the same scope at the same time can make one deployment report the wrong output: use a unique name such as `'${deployment().name}-storageDeploy'`, or drop `name` so a GUID is generated. The `no-module-name` linter rule flags modules that still set an explicit name. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- A module that comes from a registry must be restored first: `bicep restore` copies it into the local cache, and the Visual Studio Code extension triggers this automatically, but IntelliSense may not work until the restore finishes. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- When you rewrite a registry module reference from a custom domain to a native `.azurecr.io` hostname, clear the local module cache and run `bicep restore` again so the corrected path is picked up. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/modules))
- If a key in `@metadata()` collides with a dedicated decorator such as `@description`, the decorator always wins and the metadata copy is redundant. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/parameters))
- Use `#disable-*` directives sparingly and only after reviewing the diagnostic; identifiers are case sensitive and a directive without any identifier is an error. ([Learn](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/file))
