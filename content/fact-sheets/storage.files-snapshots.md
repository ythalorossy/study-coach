# Configure snapshots and soft delete for Azure Files

## Key concepts

- A share snapshot freezes a file share as it exists at a given moment and the copy is immutable: the snapshot is taken at the **file share** level while recovery is done per individual **file**, so one file can be brought back without restoring the whole share ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Typical uses: recovering from application bugs or corrupted writes (take a snapshot before deploying new app code), recovering a file that was accidentally renamed or overwritten, and periodic backup/audit points ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Apart from a **DateTime** value stamped onto the share URI, a snapshot looks exactly like its base share — for example `https://storagesample.file.core.windows.net/myshare?sharesnapshot=2024-12-09T17:44:51.0000000Z` ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Once created a snapshot can be read, copied or deleted, but never modified; existing snapshots are never overwritten by a new one, so you must delete an old snapshot explicitly to free space ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshots inherit the redundancy of the base share: in a geo-redundant storage account the snapshot is also stored redundantly in the paired region ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Files' system properties and the file share metadata are carried into the snapshot with the same values unless you supply separate metadata at snapshot creation time ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Soft delete is the recovery mechanism for a **deleted file share**: the share is kept in a soft-deleted state for the configured retention window, and undeleting brings back the share with all of its contents, including its snapshots, in the state they had before deletion ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Soft delete for file shares is configured once at the **storage account** level, so one setting governs every file share in that account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Neither feature is a substitute for governance controls: snapshots only protect files, and soft delete only protects file shares, so preventing deletion of the storage account itself needs an Azure Resource Manager lock on the account and/or resource group ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).

## Settings and limits

- Maximum 200 share snapshots per file share; after you hit 200 you must delete older snapshots before new ones can be created ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshots can be retained for up to 10 years; there is no limit on how many simultaneous calls to create snapshots can run ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshots are incremental: only the data that changed since your most recent snapshot is stored and billed; any write to a file or property, or any metadata update, counts as changed content ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Deleting a snapshot removes only the data unique to that snapshot; every active snapshot still contains everything needed to browse and restore that point in time, so you only really need to keep the newest one for a full restore ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshot data does not count toward the maximum file share size, and there is no total cap on how much space snapshots can use, though normal storage account limits still apply ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshots live until you delete them or until the base file share is deleted; deleting a file share automatically removes its snapshots, so you cannot keep them after the share is gone ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- To delete a snapshot in the portal you must first remove any locks: open the storage account, go to **Settings** > **Locks** and delete the listed locks ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- In the portal you create and manage snapshots from the file share's **Snapshots** tab (storage account > **Data storage** > **Classic file shares** > file share > **Snapshots** > **+ Add snapshot**), restore a file with right-click > **Restore** > **Overwrite original file**, and you can attach an optional comment when taking a snapshot ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Soft delete retention defaults to 7 days and can be any value from 1 to 365 days; the clock starts at the moment the share is deleted and you can change the retention period at any time ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Shares deleted before a retention change expire based on the retention period that was configured at the time they were deleted ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- New storage accounts have soft delete enabled by default, and you can enable or disable it for new or existing accounts; disabling it does not remove the ability to undelete shares that were already deleted while it was on ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- To enable soft delete in the portal: storage account > **Data storage** > **Classic file shares** > **Soft delete** > **Enabled** for **Soft delete for all file shares** > set **File share retention period in days** with the slider (1-365) > **Save**; to recover a share, go to **File shares**, turn on **Show deleted shares**, select the share and choose **undelete** — the status column changes from **Deleted** to **Active** ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Soft-deleted provisioned file shares keep consuming their provisioned quota in the storage account's total quota calculation until the share's soft-delete expiry, when it is fully deleted ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Soft delete billing follows the share's billing model — **Provisioned v2**, **Provisioned v1** or **Pay-as-you-go** soft delete are charged differently ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- SMB shares: snapshots are created and listed with the portal, Azure PowerShell (for example `New-AzRmStorageShare`) or Azure CLI (for example `az storage share snapshot`), and you can browse or mount a specific version; a full share restore is possible over SMB, NFS, the REST API, the portal, client libraries or PowerShell/CLI ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- SMB on Windows: mount the share, open **Properties** on the item or its parent folder and use the **Previous versions** tab, where **Open** browses the snapshot and **Restore** copies the entire directory recursively back to the original location ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- SMB on Linux: mount a specific snapshot by passing `snapshot=@GMT-2023.01.05-00.08.20` (a GMT timestamp in **@GMT-year.month.day-hour.minutes.seconds** format) to `mount -t cifs` with a `credentials=` file; this needs Linux kernel 4.19 or later ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- NFS: mount the share, then list recovery points in the hidden `/media/nfs/.snapshots` directory, `cd` into the snapshot's directory and copy the files out with `cp -r . ../../restore`; allow at least 30 seconds after creating a snapshot before the `.snapshots` directory appears ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- NFS shares created with the Microsoft.FileShares resource provider expose the endpoint in the portal **JSON view** as **hostName** (format `fs-xxxxxxxxxxxxxxxxx.xx.file.storage.azure.net`), or read it with `Get-AzFileShare` / `az fileshare show`, then mount `<hostName>:/<hostNamePrefix>/<fileShareName>`; metadata of an existing snapshot on these shares can be updated from **Operations** > **Snapshots** > **Properties** ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- NFS limitations: Azure Backup does not support NFS file shares, NFS snapshots are available in all Azure public cloud regions, and only the file management APIs (`AzRmStorageShare`) work for NFS snapshots — the file data plane APIs (`AzStorageShare`) are not supported ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).

## Compare and choose

- Need a previously deleted **file share** back? Choose **soft delete** — it retains the whole share, its files and its snapshots, and undelete returns everything to its pre-deletion state ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Need a previously deleted **file** (or an earlier version of a file) back while the share still exists? Choose **share snapshots**, or Azure file share backup — soft delete cannot help because it only works at the share level ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Need protection against the **storage account** being deleted or modified? Choose an Azure Resource Manager lock on the account and/or resource group, since neither snapshots nor soft delete cover account-level deletion ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Need a scheduled, policy-driven backup with retention management? Choose **Azure file share backup**, which automates snapshotting and is supported for **SMB file shares only** ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- On **NFS** shares, snapshots are the only in-service option because Azure Backup does not support NFS ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Restoring by copying a file out of a snapshot overwrites the base share's version of that file but leaves the snapshot intact, and the restored content counts as changed content in later snapshots ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Copying a snapshot file to a different destination under a different name produces an ordinary writable file, not a snapshot, and your base share stays untouched ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Overwriting a destination file does not harm snapshots already taken of that destination file ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- A snapshot is never "promoted" to replace the base share: a whole-share restore is done file by file, and you cannot copy an entire snapshot to another storage account in one operation — use `AzCopy` or another copy mechanism per file ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Snapshot coverage differs by resource provider: share snapshots work for classic shares created with the Microsoft.Storage provider (SMB and NFS) and for shares created with the Microsoft.FileShares provider, while soft delete applies only to the classic Microsoft.Storage shares ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).

## Gotchas

- Snapshots are file-level protection only — they never stop a user or process from deleting the file share or the whole storage account ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Deleting the file share silently takes its snapshots with it, so there is no way to keep snapshots after share deletion ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- You cannot bypass soft delete to purge a share early: to permanently delete a soft-deleted share before expiry you must undelete it, disable soft delete, delete it again, and then remember to re-enable soft delete so other shares stay protected ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Turning soft delete off does not immediately destroy already soft-deleted shares — those can still be undeleted ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- Changing the retention period does not retroactively re-date existing soft-deleted shares; they expire per the retention in force when they were deleted ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-prevent-file-share-deletion)).
- For NFS shares, mount the share *before* taking snapshots — if you snapshot a new NFS share before its first mount, listing snapshots returns an empty list; delete those early snapshots and recreate them after mounting ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Using the wrong API family breaks NFS snapshot operations: `AzRmStorageShare` (file management) works, `AzStorageShare` (file data plane) does not ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- When copying with `robocopy` from an elevated command prompt, mapped drives may be invisible and a drive letter can fail — reference a UNC path that points at the snapshot view, not the live share, or you will copy the share's current state instead of the point-in-time data ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- In the Windows **Previous versions** tab you won't see an entry for a file that never changed after the snapshot was taken — that matches how a Windows file server behaves ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Storage account locks block snapshot deletion, so clear **Settings** > **Locks** first or the delete operation fails ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Because snapshots are incremental, high-churn periods leave large unique blocks; delete the snapshots from those periods to control cost, and plan snapshot frequency and retention carefully to avoid unnecessary charges ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
- Prefer automated snapshotting over manual steps — the REST API, client SDKs, Azure file share backup or scripting are more reliable for data recovery than ad hoc portal clicks ([Learn](https://learn.microsoft.com/en-us/azure/storage/files/storage-snapshots-files)).
