# Configure Azure Storage firewalls and virtual networks

## Key concepts

- Azure Storage firewall rules decide which networks may reach a storage account's public endpoint. Out of the box a storage account accepts connections from any network; the moment you add network rules, only explicitly listed sources are allowed and every other request is rejected. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- There are four kinds of configuration you can combine on one account: virtual network rules, IP network rules, resource instance rules, and exceptions for trusted Azure services. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Network rules are network filtering, not authentication. A client that comes from an allowed source still has to satisfy the account's own authorization requirements (Microsoft Entra ID role assignments, shared keys, or a SAS token). ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Virtual network rules allow traffic from named subnets of Azure Virtual Networks. The virtual network may live in any subscription, in any Microsoft Entra tenant, and in any Azure region. A storage account supports up to 400 virtual network rules. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Every subnet that you add as a rule must also have a storage service endpoint enabled on the subnet itself; the endpoint is what gives the direct, secure route to the storage account. The portal creates the endpoint for you as you pick the subnet, while PowerShell and Azure CLI require you to create it separately. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- There are two endpoint types: `Microsoft.Storage`, which reaches storage accounts only in the same region as the virtual network, and `Microsoft.Storage.Global`, which reaches accounts in any region. A subnet can carry only one of them, so you must delete the existing endpoint before adding the other. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- IP network rules allow a public IP address range, and are the tool for clients that are not in a virtual network, such as on-premises machines. Up to 400 IP network rules are supported per storage account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- For on-premises connectivity over Azure ExpressRoute you must allow the NAT IP addresses used for Microsoft peering in the resource IP firewall list; the service provider or the customer supplies those addresses. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Resource instance rules cover Azure resources that cannot be isolated by a subnet or an IP range. Such a resource must live in the same Microsoft Entra tenant as the storage account, though it can be in any subscription of that tenant, and the role assignments on the resource instance decide which operations it can run against the storage data. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- A network security exception is the escape hatch for Azure services that run outside your network boundary and cannot be expressed as a virtual network or IP rule, for example a service that only needs to read resource log files or metrics tables. These services authenticate strongly before they connect. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- A private endpoint is a network interface in your virtual network that gives each storage service its own IP address from the virtual network's range, and traffic travels over the Microsoft backbone instead of the public internet. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Creating a private link does **not** close the public endpoint by itself; the firewall is what denies or controls public traffic, and that is a separate configuration step you must do yourself. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))

## Settings and limits

- Portal navigation for all of this: open the storage account, and under **Security + networking** choose **Networking**, then under **Resource settings: Virtual networks, IP addresses, and exceptions** choose **View**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-virtual-networks))
- The **Manage** button sets the account-wide default: **Enable** + **Enabled from all networks** for open access, **Enable** + **Enabled from selected networks** for network rules, **Disable** for no public traffic at all, or **Secured by perimeter** to use a network security perimeter. Press **Save** to apply. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-set-default-access))
- Adding a rule: **Add existing virtual network**, pick from the **Virtual networks** and **Subnets** lists, then **Add**; or **Add new virtual network** and supply the details to create one and select **Create**. Then **Save**. To delete a rule, open the ellipsis (**...**) on the virtual network or subnet and choose **Remove**. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-virtual-networks))
- Permissions needed to add a virtual network rule: the **Storage Account Contributor** built-in role, or a custom role carrying the `Microsoft.Network/virtualNetworks/subnets/joinViaServiceEndpoint/action` operation on the subnets being added. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-virtual-networks))
- Numeric limits: maximum 400 virtual network rules and maximum 400 IP network rules per storage account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Timing behaviour: after you save settings that allow access, the firewall rules that block access stay in force for up to one more minute. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-set-default-access))
- Subnets are denied by default: a request from a subnet that has no rule fails with HTTP 403 until the subnet is added to a virtual network rule. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Private endpoints require a general-purpose v2 account (Standard or Premium); general-purpose v1 accounts cannot use them, and you need one private endpoint per storage service. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Target sub-resources and their private DNS zones: blob = `privatelink.blob.core.windows.net`, Data Lake Storage = `privatelink.dfs.core.windows.net`, file = `privatelink.file.core.windows.net`, queue = `privatelink.queue.core.windows.net`, table = `privatelink.table.core.windows.net`, static website = `privatelink.web.core.windows.net`. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Creating a private endpoint sends a consent request to the storage account owner; if the requester already owns the account the request is approved automatically, and owners handle pending requests on the **Private endpoints** tab. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))

## Compare and choose

- **Enabled from all networks** is the permissive default that lets any client reach the account; **Enabled from selected networks** is the mode that actually enforces your virtual network, IP and resource instance rules; **Disable** cuts public traffic completely and leaves private endpoints as the only route; **Secured by perimeter** hands control to a network security perimeter. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-set-default-access))
- Choose **IP network rules** for traffic from outside Azure (office networks, on-premises, scanners) and **virtual network rules plus a service endpoint** for traffic from Azure subnets, which keeps the source address private and avoids hairpinning through public IPs. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Choose a **resource instance rule** when the source is an Azure resource that no subnet or IP range can isolate, and a **trusted service exception** when the caller is an Azure platform service such as a diagnostics or logging service that reads logs or metrics. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- `Microsoft.Storage` reaches storage accounts in the same region as the subnet, and `Microsoft.Storage.Global` reaches accounts in any region. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- For disaster recovery, build virtual networks in the paired region ahead of time, enable the storage service endpoint there and add network rules for those subnets; the same rule also grants access to the RA-GRS replica. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Same-tenant subnets are configured in the portal; a subnet in a **different Microsoft Entra tenant** must be added with PowerShell, Azure CLI or the REST API, because the portal never lists cross-tenant subnets. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-virtual-networks))
- If the goal is private-only connectivity for a virtual network, use a **private endpoint** plus **Disable** of public network access. You do **not** need a virtual network rule for a subnet that has a private endpoint, because the firewall governs the public endpoint only, and Private Link grants access through its own consent flow. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Private endpoints and service endpoints can coexist: a subnet can reach one account through its private endpoint and other accounts through service endpoints, and private endpoints work with every protocol the account supports, including REST and SMB. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- For geo-redundant accounts, add private endpoints to the secondary instance too if you want fast reads of the replica; a secondary private endpoint is **not** required for failover, because the existing endpoint reconnects to the new primary automatically. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Data Lake Storage and Blob are paired choices: create a private endpoint for the `dfs` sub-resource **and** one for `blob`. Blob-only fails operations such as Manage ACL, Create Directory or Delete Directory, while dfs-only leaves redirects to the Blob endpoint unresolved. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))

## Gotchas

- Once a subnet has a service endpoint, its traffic reaches storage with a **private source IP**, so any IP network rule that relied on that subnet's public address silently stops mattering. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- A SAS token with an IP allow-list does not widen access: it only narrows the token holder's access inside what the network rules already permit. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Deleting a subnet that is referenced by a network rule also removes it from the account's rules, and a new subnet created with the same name inherits nothing — it must be authorized explicitly again. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-virtual-networks))
- Because service endpoints deliver regional connectivity, a paired-region virtual network rule matters: without it, a failover can leave the account unreachable even though the rules look correct today. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
- Traffic from a virtual network that owns a private endpoint is always permitted, even when public network access is set to **Disabled** on the account. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Keep using the ordinary connection string from inside the virtual network; DNS does the routing. Do **not** connect by using the `privatelink` subdomain URL yourself. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Outside the virtual network the account name resolves through a CNAME chain to the public endpoint and its public IP; inside, it resolves to the private endpoint address, which is how the same connection string works in both places. With your own DNS server you must delegate the `privatelink` subdomain to the virtual network's private DNS zone or add the A records yourself. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- When copying blobs between accounts, the client needs network access to **both** the source and the destination, so privatising only one side breaks the copy. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Account-to-account copy through private endpoints only works with clients that call the Azure REST API, for example AzCopy or Azure CLI; NFS-based copying is not supported, and endpoints aimed at the `dfs` sub-resource alone do not work for copying. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- A DNS side effect catches people out: if account A2 has a blob private endpoint in some network, clients in a network that already has a blob private endpoint to account A1 must also reach A2 through a private endpoint, while A2 accounts with no blob private endpoints remain reachable directly. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-private-endpoints))
- Restricting settings do not lift instantly: after saving an allow change, deny rules can persist for up to a minute, so test failures during that window are expected. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-set-default-access))
- Review the documented restrictions before rolling firewall settings out broadly, since IP range, subnet and account-type limitations can block an otherwise valid design. ([Learn](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security))
