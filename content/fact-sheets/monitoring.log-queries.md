# Query and analyze logs in Azure Monitor

## Key concepts

- Azure Monitor Logs is built on Azure Data Explorer and speaks the same **Kusto Query Language (KQL)**, so KQL skills and reference material carry over between the two products ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- **Log Analytics** is the main Azure portal tool for writing, running and testing log queries; you normally validate a query there first, then copy it to its final destination ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- The same query can be reused as the basis of **log search alert rules** (run automatically at intervals, results inspected to decide whether to fire an alert), **workbooks**, **Azure dashboards**, **Azure Logic Apps** workflows, PowerShell runbooks through `Invoke-AzOperationalInsightsQuery`, and the Log Analytics query API used by any REST client ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- Idiomatic query client libraries are published for .NET, Go, Java, JavaScript and Python so log data can be pulled from a workspace programmatically ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- Azure Monitor Logs offers two authoring experiences: **KQL mode** for hand-written advanced queries, and **Simple mode**, a point-and-select UI where you choose a table and add filters ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- The **Observability Agent** lets you explore log data in natural language instead of writing KQL; it runs the KQL on your behalf and surfaces the insights ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Log data is organised into tables made of columns, and every table and column is listed in the schema (**Tables**) pane of Log Analytics; the demo environment supplies sample tables such as **AppRequests** with columns like **Name**, **Url**, **DurationMs**, **ResultCode** and **ClientCity** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- A query starts with either a table name or the `search` command; the pipe character `|` separates commands so the output of one becomes the input of the next, and you can add any number of piped elements ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- KQL as used by Azure Monitor is case sensitive: keywords are usually lowercase, and table and column names must match the case shown in the schema pane ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Azure Monitor deliberately omits parts of standard KQL: the **alias statement** and **query parameters** statements; the functions `cluster()`, `cursor_after()`, `cursor_before_or_at()`, `cursor_current()`/`current_cursor()`, `database()`, `current_principal()`, `extent_id()` and `extent_tags()`; the cross-cluster join operator; and the Python and `sql_request` plug-ins ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- Azure Monitor adds three operators that exist only there: `workspace()` for querying across Log Analytics workspaces, `app()` for classic Application Insights applications, and `resource()` for correlating data between resources ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- Querying a workspace requires `Microsoft.OperationalInsights/workspaces/query/*/read` permission, as provided by the **Log Analytics Reader** built-in role ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- The Log Analytics **demo environment** includes sample data supporting the tutorial queries and requires no Azure subscription ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Run a query with the **Run** button or by pressing `Shift+Enter` with the cursor anywhere in the query text; IntelliSense completes table names in scope and KQL commands ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))

## Settings and limits

- The **Time range** picker next to **Run** defaults to **Last 24 hours** and applies to all queries; **Last hour**, **Last 12 hours** and **Last 7 days** are among the built-in choices ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- If you write a time range into the query, the picker automatically switches to **Set in query** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- In-query time filters use relative expressions such as `ago(30m)`, `ago(1h)`, `ago(7d)` and `ago(10s)` (minutes, hours, days, seconds), and are best placed immediately after the table name ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Displayed rows are capped by the **Show** limit / portal result limit for Azure Monitor Logs; a query with no limit such as `sort` can return far more records than the portal can display, and the extra work also slows the query ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- The row limit is set by the `take` operator in KQL mode and by the **Show** option in Simple mode ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Because of the **Show** limit, the record count in the results pane may not shrink after you narrow the time range ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Scope depends on where you open **Logs**: from the Azure Monitor menu of a subscription it targets the whole **Log Analytics workspace**, while from a resource's menu it narrows to that resource's records only; the current scope is shown by the ellipsis of the current query ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- The **Tables** pane groups tables by **Solution** by default and lets you regroup or filter them; hovering a table and choosing **Run** previews its records from the last 24 hours, and the **Useful links** entry opens the table reference for its columns ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- In Simple mode you add filters with the **Add** filters icon to the right of the **Show** limit; the default filter operator is **Select from list**, which offers values taken from the records in your current results ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Filters configured from the results column headers are Excel-like, apply to the displayed records, and are wiped whenever you rerun the query ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Log query API endpoints for Log Analytics and Application Insights require TLS 1.2 or higher for querying log data and events, as of July 1, 2025 ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
- A workspace you cannot read produces a **No access** error; an administrator must grant the **Log Analytics Reader** role or equivalent read permissions ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))

## Compare and choose

- `take` vs `sort` vs `top`: `take` returns an arbitrary, unordered sample of up to N rows, `sort` orders rows but does not limit how many are returned, and `top` sorts on the server and returns only the top N — use `top 10 by TimeGenerated` when you want the newest records efficiently ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- `sort by TimeGenerated desc` and `sort by TimeGenerated` return identical results because descending is the default for `sort` and `top`; add `asc` for ascending order ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- `project` keeps only the columns you list and can rename or compute them (for example `EventDetails=Activity`, `EventCode=substring(Activity, 0, 4)`), whereas `extend` retains every original column and adds the computed one, which appears only when you expand a record ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Combine conditions with `and`/`or` in a single `where` (for example `where Level == 8 and EventID == 4672`) or chain several `where` operators one after another; `!=` and `<>` are interchangeable ways to express inequality ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- `==` tests equality case-sensitively while `=~` tests it case-insensitively (for example `EventSourceName =~ "microsoft-windows-security-auditing"`) ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Use `extend` for ad hoc computations inside a query, but use ingestion-time transformations or summary rules when you want data transformed or aggregated at ingestion time for more efficient queries ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Start from a table name rather than `search` whenever you can: it gives the query a clear scope, improves performance and the relevance of results, while `search "Cryptographic"` alone sweeps every table and is slower; `search in (SecurityEvent) "Cryptographic"` restricts the sweep ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- `summarize count() by ObjectName` groups by one dimension, whereas `summarize count() by ObjectName, CounterName` creates one group per unique combination of the two values ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- `summarize avg(CounterValue) by Computer` mixes different performance counters and produces meaningless numbers; group by `Computer, CounterName` so each counter is averaged separately ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- Summarizing directly by `TimeGenerated` would create a group for every millisecond because the values are unique; use `bin(TimeGenerated, 1h)` to bucket a continuous value into manageable time units ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- In the **Columns** sidebar, dragging a column into **Row Groups** gives collapsible groups of the returned rows, while **Pivot Mode** builds a pivot table such as one row per `Url` with `max(DurationMs)` so you can sort by the slowest URL ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Sharing and export options in the **Share** menu: **Copy link to query** (shareable only with people who already have access to the same workspace), **Copy query text**, **Copy results** (select rows, then right-click **Copy** or `Ctrl+C`), **Export to CSV - all columns** or **Export to CSV - displayed columns**, **Export to Power BI (as an M query)** or **Export to Power BI (new Dataset)**, and **Open in Excel**, which needs Excel installed locally ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- The **Save** menu saves the query or pins a visual to a dashboard; the **Queries** pane on the left holds built-in example queries, for example **Response time trend** in the **Applications** category, loaded into the editor with **Load to editor** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))

## Gotchas

- Duplicate rows in results usually come from retry logic in the pipeline that occasionally re-delivers a small percentage of telemetry, or from having both the Log Analytics agent and Azure Monitor Agent installed and collecting the same data — in that case configure the workspace so the data collection rule no longer collects what the Log Analytics agent already sends ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- The `Level` column of `SecurityEvent` is a String type, so numeric comparisons fail until you cast it, for example `SecurityEvent | where toint(Level) >= 10` ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/get-started-queries))
- The two source pages describe combining the time picker with an in-query time filter differently: the Log Analytics tutorial says the union of the two ranges is applied, while the query fundamentals page says the smaller of the two ranges applies — so avoid depending on both at once and verify the effective window in your own workspace ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- The results **search box** only filters what is already displayed in the browser; it does not change the KQL and does not re-fetch data from the server ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Grouping with **Row Groups**, or sorting and filtering in the results pane, reorganises the data your query already returned; rerunning the query goes back to the server with your original query and undoes the client-side arrangement ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- A blank line in the editor separates queries, and each separated query runs independently, so loading an example query beneath an existing one does not merge them ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- A **No chart available** message means the query returned nothing suitable for charting; include a `summarize` with a `bin(TimeGenerated, ...)` clause, then switch to the **Chart** view and pick a **Chart type** such as **Line** in the **Chart formatting** sidebar ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- An empty **Filter** tab means filter values were not loaded for the current results: run a query first, then use the refresh or reload option on the filter tab ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- **Pivot Mode** does not appear until you open the **Columns** sidebar to the right of the results pane and then select **Pivot Mode** ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- If the **AppRequests** table is missing from the **Log Management** solution, the workspace has no Application Insights data configured — use the demo environment or connect an Application Insights resource to the workspace ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- A query returning zero results usually means the selected time range holds no data or the filter is too narrow — widen the range to **Last 7 days** and remove filters to confirm the data exists ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- In the demo environment you cannot create alert rules and **Copy link to query** / **Copy query text** fail, because the demo has no unique URL and does not save queries ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-tutorial))
- Cross-cluster join and the Python and `sql_request` plug-ins are not supported in Azure Monitor, so a query that relies on them must be rewritten using the Azure Monitor-specific `workspace()`, `app()` or `resource()` operators ([Learn](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-query-overview))
