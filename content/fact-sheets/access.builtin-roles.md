# Manage built-in Azure roles

## Key concepts

- Azure RBAC is the authorization system that sits on top of Azure Resource Manager and controls who can do what, and where, inside Azure resources. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A role assignment always has exactly three parts: a security principal, a role definition, and a scope. Access is granted by creating a role assignment and revoked by removing it. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- The security principal can be a user, a group, a service principal, or a managed identity, and any of those four can receive a role assignment. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A role definition is a bundle of permissions written as four arrays: `Actions`, `NotActions`, `DataActions`, and `NotDataActions`. High-level examples are Owner; narrower service examples include Virtual Machine Contributor. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- There are four scope levels: management group, subscription, resource group, and individual resource. They form a parent-child chain, so a role assigned high up also applies to everything below it. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Azure RBAC is additive: effective permissions equal the sum of every applicable assignment. Someone with Contributor at subscription scope plus Reader on one resource group still behaves as Contributor for the whole subscription, so the narrower Reader grant adds nothing. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Group membership is transitive, so a user inherits permissions from any group that has an assignment, even when that user belongs only through a nested group. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Effective permissions are calculated by subtraction: `Actions - NotActions` yields effective management permissions and `DataActions - NotDataActions` yields effective data permissions. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Evaluation order matters for troubleshooting: a token is issued with transitive group memberships, the REST call goes to ARM, ARM collects matching role assignments and deny assignments, a matching deny assignment blocks the call immediately, otherwise roles are narrowed and matched to the action, and only then are any assignment conditions evaluated. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Role definitions, role assignments, and deny assignments are held globally and replicated to every region, so access to a resource never depends on where that resource or the user is located. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Built-in roles are the ready-made role definitions Microsoft ships, assignable to users, groups, service principals, and managed identities; when none of them fits the need, the answer is an Azure custom role. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- The built-in catalog is grouped into categories such as Privileged, General, Compute, Networking, Storage, and Web and Mobile, and each entry shows a one-line description plus a stable GUID role ID. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Using Azure RBAC costs nothing extra; it is included in your Azure subscription. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))

## Settings and limits

- Owner, ID `8e3af657-a8ff-443c-a75c-2fe8c4bcb635`, manages everything including creating Azure RBAC role assignments. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Contributor, ID `b24988ac-6180-42a0-ab88-20f7382dd24c`, manages all resources but is deliberately blocked from assigning Azure RBAC roles, managing Azure Blueprints assignments, and sharing image galleries. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Reader, ID `acdd72a7-3385-48ef-bd42-f606fba81ae7`, is the only role in the General category and grants visibility of every resource with no ability to make changes. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Role Based Access Control Administrator, ID `f58310d9-a9f6-439a-9e8d-f62e7b41a168`, grants access management only through Azure RBAC role assignments and does not cover other access mechanisms such as Azure Policy. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- User Access Administrator, ID `18d7d88b-d35e-4fb5-a5c3-7773c20a72d9`, grants the ability to manage user access to Azure resources. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Reservations Administrator, ID `a8889054-8d42-49c9-bc1c-52486c10e7cd`, can read and manage all reservations across the tenant. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Virtual Machine Contributor, ID `9980e02c-c2be-4d73-94e8-173b1dc7cf3c`, creates and manages VMs and disks, installs software, resets the VM root password, and manages local user accounts, all through VM extensions. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Network Contributor, ID `4d97b98b-1d4f-4787-a291-c67834d212e7`, manages network configuration but grants neither access to those networks nor permission to deploy or manage virtual machines. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Storage Account Contributor, ID `17d1049b-9a84-46fb-8f53-869881c3d3ab`, manages storage accounts and reaches account keys, which allows Shared Key authorization; Storage Account Key Operator Service Role, ID `81a9662b-bebf-436f-a333-f67b29880f12`, only lists and regenerates those keys. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Storage Blob Data Contributor, ID `ba92f5b4-2d11-453d-a403-e96b0029c9fe`, reads, writes, and deletes blob containers and blobs, while Storage Blob Data Reader, ID `2a2b9908-6ea1-4ae2-8e65-a410df84e7d1`, only lists and reads. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Several catalog entries are labelled preview and can change, including Virtual Machine Data Access Administrator (preview), ID `66f75aeb-eabe-4b70-9f1e-c350c4c9ad04`, VM Restore Operator, Desktop Virtualization Virtual Machine Contributor, Storage Connector Contributor, and Storage DataShare Contributor. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- The maximum number of custom roles is 5,000 per tenant, or 2,000 per tenant in Microsoft Azure operated by 21Vianet, which is the first sign you should be reusing built-in roles instead. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- A custom role can declare at most 2,000 entries in `AssignableScopes`, cannot use root scope `/`, and cannot contain a `*` wildcard in that list, which stops a role editor from widening their own reach. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- A custom role may use one `*` wildcard per action string and only one management group in `AssignableScopes`, and ARM does not verify that the management group exists. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Custom role naming and description limits: the display name must be unique across the tenant, recommended maximum 256 characters and absolute maximum 512; the description recommends 512 and allows up to 2,048 characters. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Permission strings are case-insensitive, and the recommended style is to match the casing shown in Azure resource provider operations. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Creating, updating, or deleting a custom role needs `Microsoft.Authorization/roleDefinitions/write` on every scope listed in `AssignableScopes`; Owners and User Access Administrators are the usual built-in roles that hold it. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Viewing a custom role needs `Microsoft.Authorization/roleDefinitions/read` at that scope, and every built-in role makes custom roles available for assignment. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))

## Compare and choose

- Choose Owner rather than Contributor whenever the person must hand out access; Contributor manages resources fully but cannot create role assignments, so it cannot delegate. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Choose User Access Administrator when the task is broad access management, and Role Based Access Control Administrator when access must be managed strictly via Azure RBAC assignments rather than other mechanisms such as Azure Policy. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Choose Reader for monitoring and reporting that needs no writes; Contributor is the smallest built-in role that allows resource changes without granting role assignment. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Prefer a narrow service role over Contributor when the job is service-specific: Network Contributor for networks, DNS Zone Contributor for zones and record sets, or Storage Blob Data Contributor for blob data. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- For blob access pick by need: Reader for list and read, Contributor for read/write/delete, and Storage Blob Data Owner for full blob access including assigning POSIX access control. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Split responsibilities across Virtual Machine Contributor and Network Contributor because neither covers the other: VM Contributor gets no VNet or storage account management, and Network Contributor cannot deploy VMs. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Use a custom role only after reviewing the built-in list, and build it by copying an existing built-in role and trimming or adding actions rather than starting from scratch. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Reference roles by their GUID ID in scripts and automation instead of by name, because a rename leaves the ID unchanged and keeps automation working. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Azure RBAC directory admin roles are a different family; for tenant administrator roles such as directory administrator, look at the Microsoft Entra built-in roles instead of this catalog. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))

## Gotchas

- The classic exam trap: Contributor is described as "full access" yet cannot assign Azure RBAC roles, manage Azure Blueprints assignments, or share image galleries, so it is not a substitute for Owner. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- You cannot use a narrow role to subtract permissions. Because the model is additive, assigning Reader below Contributor changes nothing, and only a deny assignment can block an action that a role otherwise allows. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Deny assignments are evaluated first and are absolute, so a principal can be blocked even when Owner or Contributor is assigned. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A role assignment with conditions is only granted when the condition evaluates true; the action must already be permitted by the role at the requested scope, otherwise conditions are never reached. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A custom role that contains `DataActions` cannot be assigned at management group scope. You may list one management group in `AssignableScopes` and then assign the role at the subscriptions inside it, but not at the management group itself. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Wildcards such as `Microsoft.CostManagement/exports/*` are compact but also swallow every permission Microsoft adds later to that namespace, so Microsoft recommends listing `Actions` and `DataActions` explicitly. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Deleting a custom role that still has assignments fails with the message `There are existing role assignments referencing role (code: RoleDefinitionHasAssignments)`, so remove the assignments first, including eligible Microsoft Entra PIM assignments. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Deleting Azure RBAC data is global and immediate: the assignments are removed everywhere and every principal that relied on them loses access. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Renaming a custom role never changes its role ID, so role assignments keep pointing at the same definition, while scripts written against the name can break. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles))
- Roles marked preview in the built-in catalog, such as Virtual Machine Data Access Administrator (preview) and VM Restore Operator, are explicitly subject to change and should not be treated as stable. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles))
- Azure RBAC covers Azure Resource Manager and data plane services that integrate with it; granting data access means granting data actions such as reading blobs inside a storage account, not just managing the account. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Role assignments can be created with the portal, CLI, PowerShell, SDKs, or REST APIs, so a portal-only workflow is not required and the same role ID works across every tool. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
