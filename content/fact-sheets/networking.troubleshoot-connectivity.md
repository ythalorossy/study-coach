# Troubleshoot network connectivity

## Key concepts

- **IP flow verify** is a Network Watcher capability that tells you whether traffic would be permitted or blocked, in either direction, for an Azure virtual machine, based on the security and admin rules in force. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- It weighs NSG rules together with Azure Virtual Network Manager admin rules, which makes it useful for traffic aimed at other Azure resources, out to the internet, and into on-premises environments. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Every NSG touching the VM's network interface counts, whether it was attached at NIC level or at subnet level, and Virtual Network Manager rules on the VM's virtual network are applied as well. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- You supply six inputs: direction of travel, protocol, local IP, remote IP, local port and remote port. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- The answer comes back as **Access allowed** or **Access denied**, plus the name of the rule responsible and a link to its network security group so you can adjust it. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- **Next hop** reports, for a destination IP address, the kind of next hop, that hop's IP address and the ID of the route table involved. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- If a user-defined route produced the match, you get the route table holding it; when no such route applies, the route table is reported as **System Route**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- The next hop types returned are **Internet**, **VirtualAppliance**, **VirtualNetworkGateway**, **VirtualNetwork**, **VirtualNetworkPeering**, **VirtualNetworkServiceEndpoint**, **MicrosoftEdge** and **None**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- It exposes broken route design: traffic pushed toward an on-premises network or a network virtual appliance instead of where you intended, which is a classic cause of lost connectivity. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- **Connection troubleshoot** bundles the main connectivity checks into a single run, cutting Mean Time To Resolution (MTTR). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Its findings include reachability against several destination kinds (VM, URI, FQDN, IP address), configuration issues that block reachability, latency (minimum, maximum, average), a graphical topology view from source to destination, and the count of probes that failed. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- From the output you can tell whether the fault sits in the platform or in your own configuration, and each finding points to actionable guidance. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- The agentless experience (preview) means you no longer install the Network Watcher agent VM extension on Windows or Linux VMs; the diagnostics run over Azure platform APIs instead. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))

## Settings and limits

- IP flow verify requires a Network Watcher instance in the same subscription and region as the target VM, plus the RBAC permissions that Network Watcher capabilities need. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Only TCP and UDP rules can be exercised by IP flow verify; ICMP traffic rules need NSG diagnostics instead. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Rules attached to virtual machine scale sets fall outside IP flow verify's scope; examine those with NSG diagnostics. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- When one of the built-in default rules is the deciding factor, no link back to the network security group is offered. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Connection troubleshoot can check TCP or ICMP connections only. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Sources may be virtual machines, virtual machine scale sets, Azure Bastion instances or Application gateways v2; gateways enrolled in the Private Application Gateway deployment are excluded. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Destinations may be virtual machines, fully qualified domain names (FQDNs), uniform resource identifiers (URIs) or IP addresses. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- `ConnectionStatus` reports **Reachable** or **Unreachable**, and `AvgLatencyInMs`, `MinLatencyInMs` and `MaxLatencyInMs` are returned only when the check succeeded. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- `ProbesSent` and `ProbesFailed` are each capped at 100. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- `Hops[].Type` is one of **Source**, **VirtualAppliance**, **VnetLocal** and **Internet**, and for internet hops `Hops[].ResourceId` reads **Internet**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Each hop issue carries `Origin` — **Inbound** means the fault is on the link arriving at the current hop, **Outbound** means it is on the link leaving the current hop, **Local** means it is on the current hop itself — plus `Severity` of **Error** or **Warning** and `Type` of **CPU**, **Memory**, **GuestFirewall**, **DnsResolution**, **NetworkSecurityRule** or **UserDefinedRoute**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- `NextHopAnalysis.NextHopType` values are **HyperNetGateway**, **Internet**, **None**, **VirtualAppliance**, **VirtualNetworkGateway** and **VnetLocal**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- The diagnostic profile accepts source and destination of `*`, **IP Address/CIDR** or **Service Tag**, destination port of `*` or one port in the 0–65535 range, protocol of `*`, **TCP** or **UDP**, and direction of **Outbound** or **Inbound**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Security rule analysis returns `SecurityRuleAccessResult` of **Allow** or **Deny**, the `AppliedTo` NIC or subnet the NSG sits on, the matched rule name and action, the NSG ID, and per-rule booleans for source, source port, destination, destination port and protocol matches. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- `SourcePortStatus` and `DestinationPortStatus` are **Unknown**, **Reachable**, **Unstable**, **NoConnection** or **Timeout**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- The route table identifier in the response reads **System Route** when the returned route corresponds to no user-created route. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Problems it can surface include saturated VM CPU, saturated VM memory, guest OS firewall rules blocking traffic, hostname lookups that fail, misconfigured or absent routes, NSG rules that block traffic, a socket that cannot be opened at the chosen source port, missing ARP entries on Azure ExpressRoute circuits, and hosts that are not listening on the target ports. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- The fault types returned about a connection are CPU, Memory, GuestFirewall, DNSResolution, NetworkSecurityRule and UserDefinedRoute. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Error codes include `AgentStopped` (Network Watcher agent on the source VM stopped or unresponsive), `NetworkSecurityRule` (an NSG rule refusing inbound or outbound traffic), `UserDefinedRoute` (a UDR steering traffic to a `None` next hop, i.e. a blackhole), `RouteMissing`, `Platform`, `NetworkError` and `SystemError`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- VM lifecycle errors are `VMNotAllocated`, `VMStarting`, `VMStopped`, `VMStopping`, `VMDeallocating`, `VMDeallocated` and `VMRebooting`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Probe errors include `DNSResolution`, `InvalidResponseFromServer`, `DNSResponseValidationFailed`, `StatusCodeValidationFailed`, `HeaderValidationFailed`, `ContentValidationFailed`, `NoListenerOnDestination`, `SocketError` (`SocketBindFailed`, `ListenFailed`) and `SourcePortInUse` (source port still in **TIME_WAIT**). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Path errors include `GatewayNotProvisioned`, `VirtualHubNotProvisioned`, `PeeringInfoNotFound`, `VnetAccessNotAllowed` (`AllowVNetAccess` set to false), `AllowGatewayTransitNotEnabled`, `UseRemoteGatewaysNotEnabled` and `BasicILBNotSupportedWithGlobalPeering`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Routing errors include `UDRLoop` (next hop IP matches the current hop IP), `IPForwardingNotEnabled` (NVA NIC without IP forwarding), `MultiNICsInSameSubnet`, `BGPRoutePropogationDisabled`, `ARPMissing`, `DIPProbeDown`, `StandardILBOutboundInternetNotAllowed` and `NoRouteLearned`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))

## Compare and choose

- Suspected NSG or Virtual Network Manager rule blocking traffic → **IP flow verify**, because it names the matched rule and the NSG so you can edit it. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Suspected routing problem → **next hop**, because it shows the next hop type, its IP address and the route table for the destination. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- End-to-end "can A reach B" question needing latency, topology and root-cause analysis → **connection troubleshoot**. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Need to evaluate ICMP rules, or rules applied to a virtual machine scale set → **NSG diagnostics**, since IP flow verify covers only TCP/UDP and single-VM NIC rules. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Need per-hop evidence of where traffic fails (NSG, UDR, DNS, guest firewall, CPU, memory) → **connection troubleshoot**, since it returns hops with issues, severities and types. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Next hop answers "where would this traffic go", not "is it allowed" — it never evaluates NSG or admin rules. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/next-hop-overview))
- IP flow verify is a static rule simulation: it does not test live connectivity, latency, or whether a host is listening on the port. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
- Connection troubleshoot is the only one of the three that validates that a process listens at the destination (`NoListenerOnDestination`) and that the hostname resolves (`DNSResolution`). ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))

## Gotchas

- The agentless experience is currently in preview, so features and functionality may change before general availability. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Historically every connectivity test needed the Network Watcher agent VM extension on the source VM; agent-related failures still surface as `AgentStopped` and `SocketError`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- With a TCP ping, a guest firewall that has no allowing rule can answer the ping by itself, so the ping never reaches the target IP/FQDN and nothing is logged; if a rule does allow the target, the server's reply travels back through the firewall and appears in the network rules log. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- VMs in a Standard internal load balancer backend pool have no default outbound internet path, unlike Basic ILB backends, so expect `StandardILBOutboundInternetNotAllowed`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Several NICs of one VM in the same subnet can cause asymmetric routing and unpredictable traffic (`MultiNICsInSameSubnet`), especially with weak host send or receive enabled. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- A peering with `AllowVNetAccess` set to false blocks traffic from crossing the peering boundary (`VnetAccessNotAllowed`), while the hub side needs `AllowGatewayTransit` and the spoke side needs `UseRemoteGateways`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- A route pointing to a `None` next hop is a blackhole reported as `UserDefinedRoute`, and a route whose next hop equals the current hop is a loop reported as `UDRLoop`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- A deallocated or stopped VM cannot answer at all, so `VMNotAllocated`, `VMDeallocated` and `VMStopped` describe states rather than misconfigurations. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- A source port left in **TIME_WAIT** by an earlier test can make the next test fail with `SourcePortInUse`. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/connection-troubleshoot-overview))
- Don't expect a link to the network security group from IP flow verify when a default rule decided the outcome — the link is provided only for the NSG that holds the matched custom rule. ([Learn](https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview))
