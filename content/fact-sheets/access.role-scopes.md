# Assign roles at different scopes

## Key concepts

- A role assignment combines three things: a security principal, a role definition, and a scope. Creating it grants access; deleting it revokes access. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- The security principal is the requester: a Microsoft Entra user, group, service principal (app), or managed identity. Any of them can hold a role. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- The role definition (the "role") lists the actions allowed — read, write, delete. Azure supplies built-ins from broad (**Owner**) to narrow (**Storage Blob Data Reader**); if none fits, you build an Azure custom role. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Roles hold two permission families: control-plane actions for managing the resource object, and data actions for the data inside it (read blobs or queue messages in a storage account). ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Scope is the set of resources access applies to, and there are exactly four levels: management group, subscription, resource group, resource. Roles can be assigned at any of them. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- The levels nest parent-child — management group → subscription → resource group → resource — each one more specific. Lower levels inherit what higher levels grant, so a tight scope limits the damage if the principal is compromised. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Management group is the broadest level, sits above subscriptions, supports hierarchies of its own, and reaches every subscription inside the group. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- A scope is a slash-separated string on the command line and appears as the resource ID in the portal. Fixed segments: `/subscriptions`, `/resourcegroups`, `/providers`; placeholders: `{subscriptionId}` (a GUID), `{resourceGroupName}`, `{providerName}`, `{resourceType}`, `{resourceSubType1}`, `{resourceSubType2}`, `{resourceName}`. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Management group scope skips the subscription segment: `/providers/Microsoft.Management/managementGroups/{managementGroupName}`. Examples: subscription `/subscriptions/00000000-0000-0000-0000-000000000000`; resource group adds `/resourceGroups/Example-Storage-rg`; resource adds `/providers/Microsoft.Storage/storageAccounts/azurestorage12345/...`. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- A role assignment is an ARM extension resource hanging off the resource it applies to; its name is that resource's ID plus `/Microsoft.Authorization/roleAssignments/{roleAssignmentId}`. Because the scope is always the extended resource's ID, ARM templates normally omit scope and derive it from the assignment's `id`. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Scopes for a management group, subscription, or resource group need only a name plus the subscription ID. A resource scope takes more work: read the **Resource ID** on the properties page, or temporarily assign a role at the resource and list assignments in Azure PowerShell or Azure CLI to copy the **Scope** property. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Listing assignments shows the properties to verify one: **RoleDefinitionName** (e.g. `Storage Blob Data Reader`), **Scope**, **ObjectType** (e.g. `User`), **SignInName**, **CanDelegate**, **Condition**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Azure RBAC is additive: effective permissions equal the sum of applicable assignments, never a subtraction. **Contributor** at subscription plus **Reader** on a resource group means **Contributor** subscription-wide, so the **Reader** assignment changes nothing. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Group nesting is transitive — a user in a group that belongs to another group holding the assignment inherits those permissions. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Evaluation order: token with group memberships → REST call → ARM gathers matching role and deny assignments → a deny assignment blocks → assignments narrowed to that user or its groups → action matched against `Actions` minus `NotActions` and `DataActions` minus `NotDataActions` → assignment conditions checked last. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Role definitions, role assignments, and deny assignments are stored globally and replicated everywhere, so access doesn't depend on the resource's or user's region. Deleting RBAC data deletes it globally and access disappears immediately. Using Azure RBAC costs nothing extra. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))

## Settings and limits

- To assign an Azure role you need `Microsoft.Authorization/roleAssignments/write`, for example from **Role Based Access Control Administrator** or **User Access Administrator**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Portal path: open the scope (**Management groups**, **Subscriptions**, **Resource groups**, or one resource) → **Access control (IAM)** → **Role assignments** tab → **Add** > **Add role assignment**. Without the permission the option is disabled. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- The **Role** tab splits roles into **Job function roles** (general Azure management or service-specific) and **Privileged administrator roles** (**Owner**, **Contributor**, **User Access Administrator**, **Role Based Access Control Administrator**). ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Filter with the **Search** box (role name or description) and the **Type** and **Category** filters; **View** in the **Details** column shows a role's permissions. **Copilot can help pick role** describes the need in a dialog and proposes roles you apply with **Select permissions** then **Select role**, or browse via **Recommend other roles**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- On the **Members** tab pick **User, group, or service principal**, click **Select members**, search the directory by display name or email, and confirm with **Select**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- For workload identities use the **Managed identity** option, then **Select members** in **Select managed identities** and choose a user-assigned or system-assigned identity; system-assigned identities can be found by Azure service instance. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- The **Description** box is optional; add the **Description** column with **Edit columns** to see it later in the list. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- The **Conditions** tab appears only for roles that support conditions, and its layout varies by role; a condition is an extra check on the assignment for finer control. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- **Owner**, **Role Based Access Control Administrator**, and **User Access Administrator** get the delegate condition: under **What user can do** choose **Allow user to only assign selected roles to selected principals (fewer privileges)**, then **Select roles and principals**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- The storage data roles (**Storage Blob Data Contributor**, **Storage Blob Data Owner**, **Storage Blob Data Reader**, **Storage Queue Data Contributor**, **Storage Queue Data Message Processor**, **Storage Queue Data Message Sender**, **Storage Queue Data Reader**) instead offer **Add condition** to filter on storage attributes. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- The **Assignment type** tab needs a Microsoft Entra ID P2 or Microsoft Entra ID Governance license and shows up only for management group, subscription, and resource group scopes — never for a single resource. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- **Eligible** means the user must activate first (multifactor authentication, business justification, or approver approval); **Active** means no activation step. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Workload and app identities can't be made eligible, because they cannot perform activation steps — give them **Active** instead. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- **Assignment duration** is **Permanent** (always allowed to use the role) or **Time bound**, where you set **Start date and time** and **End date and time**. Future start dates are allowed, and the longest eligible duration is set by your Privileged Identity Management (PIM) policy; **Time bound** is disabled if PIM forbids permanent assignments. Users with eligible or time-bound assignments need a valid license. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- **Configure PIM Policy** sets expiration options and activation requirements (approval, multifactor authentication, Conditional Access authentication context). The feature is rolling out in stages, so the tab may be missing in your tenant. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- To change an assignment later, click the **State** link in the list (e.g. **Eligible time-bound** or **Active permanent**) to open **Edit assignment**, change settings, **Save** — changes can take a while to appear. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Finish on the **Review + assign** tab: review, then **Review + assign** again, and the principal holds the role at the scope you opened. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))

## Compare and choose

- Scope breadth: management group for many subscriptions centrally, subscription for one billing boundary, resource group when a team owns a set of resources (e.g. **Website Contributor** for one group only), resource for the tightest grant such as one storage account, virtual network, or blob container. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Getting a resource scope: copy **Resource ID** from the properties page (fast, no side effects), or temporarily assign a role there and read the **Scope** in PowerShell/CLI output (works for deep resources such as a container inside a blob service). ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Control plane or data plane: to manage resources pick a role like **Contributor** or **Virtual Machine Contributor**; to work with the data inside a service pick the matching data role. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Least privilege: prefer a job function role at the smallest workable scope, and keep privileged administrator roles to as few holders as possible. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Delegating role assignment: **Owner** and **User Access Administrator** can assign any role; **Role Based Access Control Administrator** concentrates on role assignments and conditions instead of resource ownership. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Just-in-time or standing: **Eligible** + **Time bound** for privileged roles that must be activated and expire; **Active** + **Permanent** when you skip PIM and the principal should always hold permissions. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Principal type: **User, group, or service principal** for people and apps, **Managed identity** for Azure resources — and remember managed identities or service principals can only be **Active**. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Condition type: the delegate condition for the three privileged roles, storage attribute conditions via **Add condition** for the blob and queue data roles. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))

## Gotchas

- Narrowing scope never cancels inherited access: with **Contributor** at subscription, a **Reader** assignment on one resource group is pointless because permissions only add up. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A deny assignment is evaluated before any role, so it blocks the action even when an allow-role grants it. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- A role assignment ID is not a scope — the ID carries the extra `/providers/Microsoft.Authorization/roleAssignments/{roleAssignmentId}` suffix, the scope stops at the resource or resource group. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- Mind the case of scope strings: the format block shows fixed segments in lowercase (`/subscriptions`, `/resourcegroups`, `/providers`) while examples use `resourceGroups`, so copy the **Resource ID** rather than retyping it. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview))
- The **Role assignments** tab lists assignments made at that scope only — inherited permissions from a parent scope apply but aren't listed there. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- A greyed-out **Add role assignment** means you lack `Microsoft.Authorization/roleAssignments/write` at that scope, not a portal fault. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- No **Conditions** tab, or an unexpected layout, means the chosen role has no conditions or a different kind; conditions are evaluated after the role match, so an allowed action still fails when the condition isn't satisfied. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- **Assignment type** and the **State** column edits don't exist at resource scope, and PIM updates may lag behind what you saved. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
- Deleting RBAC data is a global delete — principals lose access everywhere at once, whatever region the resource sits in. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview))
- Azure RBAC roles are not Microsoft Entra ID administrator roles; an Entra admin assignment manages the directory, not Azure resources at a scope. ([Learn](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-portal))
