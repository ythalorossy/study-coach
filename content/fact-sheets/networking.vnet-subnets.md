# Create and configure virtual networks and subnets

## Key concepts

- Azure Virtual Network is the fundamental private-network building block: it lets Azure resources such as virtual machines communicate with each other, with the internet, and with on-premises networks, using familiar datacenter networking concepts. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- A virtual network and all of its subnets span every availability zone in the region, so you never create a VNet per zone; a zonal VM can go in any zone without VNet zone planning. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Using Azure Virtual Network itself costs nothing; you pay normal prices for the resources you deploy inside it, such as VMs. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Resource-to-resource traffic inside a VNet works three ways: deploy the resource into the VNet (AKS, VM scale sets, App Service Environment), reach Azure services such as Storage and SQL Database over virtual network service endpoints, or connect VNets with virtual network peering. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Virtual network peering links two VNets that can sit in the same or in different Azure regions, letting resources on either side communicate. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- On-premises reach comes from point-to-site VPN (one computer, few or no network changes), site-to-site VPN (your on-prem VPN device to an Azure VPN gateway in the VNet), or Azure ExpressRoute (private partner circuit, never over the internet). ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Filter traffic between subnets with network security groups and application security groups (rules on source/destination IP, port, protocol) or with a network virtual appliance, a VM running a function such as a firewall or WAN optimization. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Routing between subnets, peered VNets, on-premises networks, and the internet works automatically; override those defaults with custom route tables or with BGP routes learned via VPN gateway or ExpressRoute. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Inbound access to a resource needs a public IP address or a public load balancer, and an internal-only standard load balancer gives no outbound path until you define one. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Default outbound internet access is being retired: the portal, and API versions released after March 31, 2026, create new VNets with private subnets (`defaultOutboundAccess` set to `false`), so their VMs need an explicit outbound method such as a NAT gateway, a public IP or a public load balancer. Existing VNets keep their earlier behaviour. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access))
- Private integration with Azure services comes in three forms: dedicated instances deployed into the VNet, Azure Private Link to a single service instance, or service endpoints that keep the service's public endpoint but restrict it to your VNet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- A VNet belongs to exactly one subscription and one region, and every resource connected to it must be in that same subscription and region, though peering can bridge VNets across both. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Moving a VM between VNets is not an in-place operation: you delete and recreate the VM in the target VNet, keeping its disks if needed. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))

## Settings and limits

- Portal creation path: search **Virtual networks** → **+ Create**; the **Basics** tab holds **Subscription**, **Resource group** (with **Create new**), **Name**, and **Region**, and the **IP Addresses** tab holds the address spaces and the first subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- **Name**: the VNet name must be unique within the selected resource group and cannot be changed after creation; a subnet name must be unique within the VNet and is also immutable after creation. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- **Resource group**: an attached resource may sit in the same or a different resource group, and a VNet can later be moved with the **Move** option next to **Resource group**, **Location**, or **Subscription**, but every connected resource must move with it. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- **IPv4 Address space**: one or more non-overlapping CIDR ranges, private (RFC 1918) or public; whatever you choose is reachable only from inside the VNet, from interconnected VNets, and from on-premises networks connected to it, and Microsoft recommends ranges your organization owns. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Ranges you can never add: `224.0.0.0/4` (multicast), `255.255.255.255/32` (broadcast), `127.0.0.0/8` (loopback), `169.254.0.0/16` (link-local), and `168.63.129.16/32` (Azure internal DNS, DHCP, and Load Balancer health probe). ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- The portal demands at least one IPv4 address range and at least one subnet at creation, even though the platform doesn't require subnets; you can add more subnets later. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- **Subnet address range** must lie inside the VNet address space and must not overlap other subnet ranges; the smallest is `/29` (8 addresses), but the first and last are reserved for protocol conformance plus three for Azure service use, so only 3 are usable. A VPN gateway requires its own gateway subnet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Subnet options: **Add IPv6 address space** for dual-stack (IPv6 isn't fully supported by all services yet), **Private Subnet** (Preview) to block default outbound access for new VMs, and existing **NAT gateway**, **Network security group**, and **Route table** — each of which must exist in the same subscription and location as the VNet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- **Service endpoints** are enabled per service from the **Services** list and Azure sets the endpoint location automatically; for Azure Storage it also configures endpoints in Azure paired regions for regional failover, and you must additionally enable subnet access on each resource of that service (for example each Storage account you want to allow). ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- **Subnet delegation** grants one service explicit permission to create its own service-specific resources in the subnet during deployment (zero, one, or many delegations), and **Network policy for private endpoints** applies **Network security groups** and/or **Route tables** to every private endpoint on the subnet once enabled. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- **DNS servers** are **Default (Azure-provided)** or **Custom**: default DNS auto-registers resource names and private IPs and resolves within one VNet only, while custom DNS (up to the per-VNet limit) resolves across VNets; servers are queried in listed order, not round-robin, and a NIC's own DNS settings override the VNet's. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Editing the address space: add a non-overlapping CIDR range, shrink a range only while it still covers all associated subnet ranges, or widen it (for example `/16` to `/8`); to remove a range you must first delete every subnet (and its resources) inside it, and a new range can't overlap a peered VNet or on-prem space. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Tooling: `az network vnet create/list/show/update/delete` with Azure CLI `2.0.31`+ (`az --version`), and `New-AzVirtualNetwork`, `Get-AzVirtualNetwork`, `Set-AzVirtualNetwork`, `Remove-AzVirtualNetwork` with the `Az.Network` module `1.0.0`+ (`Get-Module -ListAvailable Az.Network`); CLI `--address-prefixes` replaces previous ranges instead of adding to them. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Permissions: **Network contributor** or a custom role with `Microsoft.Network/virtualNetworks/read`, `Microsoft.Network/virtualNetworks/write`, `Microsoft.Network/virtualNetworks/delete`, plus for subnets `Microsoft.Network/virtualNetworks/subnets/read`, `/write`, `/delete`, `/join/action`, `/joinViaServiceEndpoint/action`, and `Microsoft.Network/virtualNetworks/subnets/virtualMachines/read`. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Most Azure networking limits already sit at their maximum; specific ones can be raised through a networking quota request. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))

## Compare and choose

- Filtering: use **network security groups** for rule-based allow/deny inside the VNet; choose a **network virtual appliance** (Azure Firewall, WAN optimization) when NSG rules aren't powerful enough. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Routing: choose a **route table** for explicit per-subnet next hops (for example forcing traffic through an NVA); use **BGP** only when routes come from on-premises via VPN gateway or ExpressRoute. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Private access to Azure services: **dedicated instances** for full control in your own VNet, **Azure Private Link** to reach one service instance privately, or **service endpoints** to keep the public endpoint but lock it to your VNet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- On-premises connectivity: **point-to-site VPN** for a single developer machine, **site-to-site VPN** for the whole on-prem network over an encrypted internet tunnel, **ExpressRoute** when traffic must stay off the internet. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Peering vs VPN vs ExpressRoute: peering is VNet-to-VNet inside Azure (same or different region, even different subscriptions), while VPN and ExpressRoute are for on-premises networks. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Service endpoints vs Private Link: a service endpoint keeps the service's public IP and adds VNet-scoped firewalling, while Private Link exposes the service on a fully private IP. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-overview))
- Default vs custom DNS: pick **Default (Azure-provided)** for zero-config name resolution inside one VNet; pick **Custom** for cross-VNet resolution, private DNS zones, or DNS filtering. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- One subnet vs many: split subnets so each tier can carry its own NSG, route table, or delegation, since Azure routes between subnets automatically but those controls apply at subnet scope. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))

## Gotchas

- Overlapping ranges are the classic blocker: if your VNet range overlaps another VNet or an on-prem network, the two can never be connected by peering or VPN, so plan address space up front. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- A `/29` subnet sounds like eight addresses but yields only three usable ones — size subnets for growth and leave room for Azure's five reserved addresses. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Start subnet names with a letter: services such as Azure Application Gateway can't deploy into a subnet whose name begins with a number. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Enabling a service endpoint on an existing subnet rewrites routes on every NIC: the default `0.0.0.0/0` route with next hop type **Internet** becomes the service prefix with next hop type **VirtualNetworkServiceEndpoint**, which can terminate open TCP connections, so don't do it during critical work. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- The endpoint isn't considered enabled until traffic to the service has picked up the new route on all NICs in the subnet; confirm with the effective routes view. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Subnet delegations can't be added or removed while resources of the delegated service are already deployed in the subnet — remove those resources first. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- A subnet's address range can only be changed while the subnet is empty; if resources exist, move them to another subnet or delete them first. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- You can delete a subnet only when it holds no resources, and a VNet only when no resources are connected to any of its subnets. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- If adding, changing, or deleting a subnet fails, check for blocking connections: gateway connections, gateways, IPs, virtual network peerings, and an App Service Environment (ASE). ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-subnet))
- Changing VNet DNS servers doesn't update running resources: VMs, Azure Firewalls, and Application Gateways keep the old DNS settings until restarted. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- Removing a custom DNS server from one VNet's list only removes it from that VNet; it stays registered in Azure for your other VNets. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
- VNet and subnet names are permanent — renaming isn't supported after creation, so choose names that follow your naming conventions from the start. ([Learn](https://learn.microsoft.com/en-us/azure/virtual-network/manage-virtual-network))
